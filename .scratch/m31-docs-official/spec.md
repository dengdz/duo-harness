# M31（0.27.0）文档官方化——「官方说明文档形态」

Status: ready-for-agent（工单待拆，见 issues/；大纲确认是全部交付工单的硬关卡）

## Problem Statement

- **通篇开发过程叙事**：文档站五段骨架（01-入门 / 02-指南 / 03-高级 / 04-架构 / 05-参考，共 13 篇）虽然成形，但口吻是里程碑流水账而非产品说明——《运行Demo》开头即「状态：M1+M2 一条命令演示全链路可用；M3 聊天 REPL……」；首页「文档之外」直挂 research/（参考项目考古）与 agents/（agent 工程设施）等内部材料。一个从 GitHub 上 `java -jar` 跑起来的 1.0 用户，读到的第一句话是项目组的开发编年史。
- **指南层严重单薄**：02-指南仅 1 篇《组装你的第一个 agent》。权限审批、会话恢复、斜杠命令、模型档位、导出检索、子代理、hooks、MCP 接入——这些已交付能力没有任何一篇「我想做 X 该怎么操作」的指南页，官方说明文档的灵魂层缺席。
- **参考层有洞**：config.yml 全量字段、CLI 启动参数与快捷键、Web 界面使用说明均无专篇，部署者只能翻源码与散落文档。
- **硬联动**：1.0 判定标准第三项「文档三层齐备」必须以大改后的文档站为核对对象（ADR-0033 钉死口径）——本文档期不完成，M32 收口的核对即作废。

## Solution

三批一条主线（范围与排序以 [ADR-0033](../../docs/adr/0033-M31文档官方化立项决策.md) 为准；版图第三改：文档官方化插为 M31 = 0.27.0，收口顺移 M32 = 1.0.0）：

**口吻重写批**：现有 13 篇逐篇去里程碑叙事，改产品文档口吻。首页产品简介 + 快速开始前置；《运行Demo》改写《快速开始》（`java -jar` 一条命令前置，mvn 源码形态与 headless 降为次要小节——现状相反）；架构章保留设计叙事、剥离历期编号；03-高级三章（M29 刚交付、锚定源码）预计微调。

**指南层新增批**：02-指南从 1 篇扩到约 8 篇，每篇 = 「我想做 X 怎么操作」：权限与审批 / 会话管理与恢复 / 斜杠命令 / 模型与思考档位 / 导出与检索 / 子代理 / hooks / MCP 接入（与《MCP 深入》分工：指南讲配置与使用，高级讲机制）。

**参考层新增批**：3 篇——config.yml 全量字段参考 / CLI 参考（启动参数 + REPL 快捷键 + 斜杠命令清单）/ Web 界面使用说明。

**执行形态**：大纲确认制沿用（M29 先例）——全站大纲与篇目清单先行（工单 01）→ 用户确认 → 逐篇交付、成篇即审即验；顺序：口吻重写批 → 指南批 → 参考批 → 首页/架构收尾。随批立《产品文档口吻规范》（落 `docs/agents/`，不进公开导航），作为后续每篇审查的引用尺。

## User Stories

### 口吻重写批

1. 作为刚从 GitHub Release 下载 fat-jar 的新用户，我想要一篇《快速开始》（装 JDK 21、写 config.yml、`java -jar` 一条命令跑起来），以便五分钟内完成第一次对话。
2. 作为想从源码跑的新用户，我想让 mvn 源码形态与 headless 用法作为快速开始的次要小节存在，以便主路径不被构建细节淹没。
3. 作为文档站新读者，我想让首页以产品简介 + 快速开始入口开场，以便 10 秒内判断这个项目是什么、怎么跑。
4. 作为文档站读者，我想让 research/（参考项目考古）与 agents/（工程设施）退出站内导航，以便看到的全是与我使用产品相关的内容。
5. 作为文档站读者，我想让全部正文不含里程碑叙事（M 期号、验收流水、状态注记），以便读到的都是「产品现在怎么用」。
6. 作为对架构感兴趣的读者，我想让架构章保留「为什么这样设计」的叙事但剥离历期编号引用，以便理解设计而不必知道开发史。
7. 作为进阶读者，我想让 03-高级三章与 05-参考六篇在口吻核对后与全站一致（M29 交付物锚定源码，预计微调），以便全站口吻统一。

### 指南层新增批

8. 作为部署者，我想要一篇权限与审批指南（规则引擎、审批卡操作、只读免审、计划模式），以便按我的安全偏好配置审批行为。
9. 作为日常用户，我想要一篇会话管理与恢复指南（创建/列表/恢复/标签绑定、空会话语义），以便换设备或重启后找回工作现场。
10. 作为日常用户，我想要一篇斜杠命令指南（按场景分组讲 /compact /export /model /effort /permission 等），以便不看源码知道每个命令干什么、什么时候用。
11. 作为多模型用户，我想要一篇模型与思考档位指南（/model 切换与白名单、/effort 档位映射、不支持时的降级标注），以便按任务选模型与思考深度。
12. 作为日常用户，我想要一篇导出与检索指南（/export 交付清单与变更摘要、/search 会话检索），以便把成果带走、把历史找回。
13. 作为进阶用户，我想要一篇子代理指南（任务分解、知识可见性 opt-in、并发调度），以便把大任务拆给子代理并行干。
14. 作为自动化用户，我想要一篇 hooks 指南（用户级配置、工具两事件、载荷字段），以便在工具调用前后挂自己的脚本。
15. 作为想接 MCP 服务器的部署者，我想要一篇 MCP 接入指南（config 写法、启动连接、状态面确认——配置与使用层），以便照着配就能用上第一个 MCP 工具；机制深入仍去《MCP 深入》。

### 参考层新增批

16. 作为部署者，我想要 config.yml 全量字段参考（llm/web/mcp/governance/hooks 等全部段的字段、缺省值、约束），以便不翻源码完成任何配置。
17. 作为终端用户，我想要 CLI 参考（启动参数、REPL 快捷键、斜杠命令清单一张表），以便用命令行时随手查。
18. 作为浏览器用户，我想要 Web 界面使用说明（会话侧栏、消息流、审批/提问/计划卡、状态面、思考折叠卡、产物预览卡），以便每个界面元素知道是什么、怎么用。

### 流程与质量

19. 作为用户，我想在全站动笔前先审大纲与篇目清单（逐篇列明改造点/新增小节/引用锚点），以便方向跑偏在动笔前拦住。
20. 作为维护者，我想要一份《产品文档口吻规范》（用户任务视角、里程碑叙事禁入正文、术语对齐术语表），以便 1.0 后任何新文档有可引用的尺子、旧口吻不回流。
21. 作为验收者，我想逐篇拿到成稿并亲手验收（构建通过 + 内容目测），以便交付质量由我判定而非代理自证。

## Implementation Decisions

九问 grill 裁定（2026-10-01，全记录见 [ADR-0033](../../docs/adr/0033-M31文档官方化立项决策.md)；本节为执行细则）：

- **大纲先行确认制**（沿用 M29 先例）：全站大纲与篇目清单（含每篇改造点/新增小节/引用锚点）落 `.scratch/m31-docs-official/outline.md` → 用户确认后才进逐篇交付；每篇一工单、成篇即审查即验收。
- **篇目骨架**（工单 01 大纲的起点，用户已确认）：口吻重写 13 篇（首页 index、《运行Demo》→《快速开始》、02-指南 1 篇、03-高级 3 篇微调、04-架构 2 篇、05-参考 6 篇核对）；指南新增约 8 篇；参考新增 3 篇。
- **《快速开始》形态反转**：`java -jar` 一条命令前置（JDK 21 + `~/.duo/config.yml` `llm` 段样例 + 运行双呈现位），mvn 源码形态与 headless 降为次要小节；原《运行Demo》的 M1/M2 机制演示叙事剥除——机制演示入口（DemoMain 等）若保留仅一句话指针。
- **内部材料处置**：research/、agents/ 退出站内导航与首页「文档之外」，文件本体不动（agent 工程设施仍按既有路径消费，domain.md 契约路径不可挪——duo-tracker 硬约束）；文档站不承担考古职责，旧叙事材料直接删除不存档。
- **指南/高级分工**：MCP 接入指南 = config 写法、启动连接、状态面确认（使用层）；《MCP 深入》= 隔离边界、生命周期、命名规则（机制层）。指南篇之间同理——操作路径优先，机制一句话点到、链接到高级/架构章。
- **示例活体引用**（M29 先例）：所有命令、配置样例、界面描述锚定真实装配文件与当前版本行为，可复制可执行；不为文档新写 demo 模块。
- **口吻规范**：几十行，落 `docs/agents/`（受众 = 未来写文档的 agent 与维护者，不进站内公开导航）；三主干：用户任务视角组织 / 里程碑叙事禁入正文（历史归 CHANGELOG 与 ADR）/ 术语对齐术语表；随工单 01 同批产出，后续每篇审查引用。
- **执行顺序**：大纲确认 → 口吻重写批 → 指南批 → 参考批 → 首页/架构收尾（首页最后改，收拢全站新口吻与新增篇目入口）。
- **记账口径**：文档站大改为用户可见变更——按批（非逐篇）在 CHANGELOG 0.27.0 未发布段记账（红线 6）；口吻规范属工程设施不记账。

## Testing Decisions

- **接缝全复用既有，零新接缝**（最高接缝原则，M29 文档线同构）：
  - **构建接缝**：vitepress build 通过 = 每篇工单的机械闸门。注意 `ignoreDeadLinks: true`（ADR-0005，.scratch 链接有意容忍）故无死链闸门——新增篇目内链与活体引用在各工单 Checklist 做链接自查（同 M29 三章先例，不为本期新建对账测试设施）。
  - **验收接缝**：逐篇用户亲手验收（构建通过 + 内容目测裁定），done 的定义按 issue-tracker（缺用户验证 Status 停 in-progress）。
  - **内容对账接缝**：命令与配置样例逐条对当前版本实测或源码锚定（活体引用纪律）；口吻规范产出后，重写批各篇按规范三条主干自查。
- **只测外部行为**：文档的可验证面 = 构建成功、链接可达、命令可复跑、描述与实际界面/行为一致；不测 vitepress 内部。
- **回归红线**：文档站构建跨工单保持通过；domain.md / issue-tracker.md 两个契约文件位置不动、内容仅按规范增补；research/ 与 agents/ 文件本体零改动。

## Out of Scope

- 流式思考展示、查阅组卡嵌套、工具名协议化渲染等 backlog 视觉/前端项（各自挂账，不因文档期扩面）。
- 演示入口（DemoMain 等）的 jar 形态适配——承诺外维持挂账（ADR-0033 范围排除节）。
- 文档站工具链更换（仍 vitepress，ADR-0005 有效）；暗色主题、站点视觉重设计（M29 视觉裁定延续，本期限内容与口吻）。
- research/、agents/ 材料的内容整改或迁移（仅退出站内导航）。
- 1.x 版本策略声明、具名候选终审、判定四项核对——全部属 M32 收口期（ADR-0033 版图第三改）。
- 新功能开发（本期为纯文档期，代码零改动——发现文档与代码不符时，文档按代码现状写，行为争议开 bug 台账）。

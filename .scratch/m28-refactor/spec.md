# M28（0.23.0）规范化重构——「代码优雅化」

Status: ready-for-agent

## Problem Statement

- **挂账压顶**：M27 审查移交 13 条硬连点 + javadoc 出入一件（[扫描册](../m27-plugin-review/hardwired-scan.md) H-01~H-16 编号），其中装配一个 agent 要传 14~17 个散参、WebFace 单文件 1812 行、cwd 取值同一行代码散落 22 处、三呈现位接线抄三遍——每加一个功能就是 +1 参、+2 重载、三处锁步（M23 headless 首版漏挂管线超时/审计回答者的事故根因）。代码能跑，但离「优雅」渐行渐远。
- **「优雅化」无证据不成账**：重构最容易扯皮——改到什么程度算完、凭什么说变好了。没有改前改后的度量对照，就没有可判定的完成判据。
- **立项口径两处失真**（2026-09-28 启动 grill 实测，已依 [ADR-0030](../../docs/adr/0030-M28规范化重构立项决策.md) 勘误注回 [ADR-0029](../../docs/adr/0029-M27至1.0版图重排第二弹.md)）：装配参数实测 chatAgent 全参重载 14 参（立项「15 参」；全仓最大装配点为命令注册接线 17 参）、user.dir 同形实测 22 处（立项「19+ 处」）。

## Solution

重构执行期的里程碑（与 M27 的审查形态相对；范围与排序以 ADR-0029 为准，裁定细则以 [ADR-0030](../../docs/adr/0030-M28规范化重构立项决策.md) 为准），五步一条线：**采基线 → 出对账册 → 分域重构 → 量对照 → 验收发版**。

1. **采基线**：四项度量（最大文件行数 top10、装配点参数个数、user.dir 同形计数、重复代码组计数）改前量一次留底。
2. **出对账册**：设计模式对账册——命令分发族 / provider 映射 / 装配层三方向的「该用未用点」扫描成册、逐条裁改/不改；不重复 M27 已扫的 H-01~H-16。
3. **分域重构**：八件必做按域推进——装配域（参数对象化 + 接线模板化 + 能力接口化）→ 呈现位域（注册表化 + 服务改名）→ Web 域（WebFace 拆分 + fileRefs 服务化）→ 取值源消重 → javadoc 认事实。
4. **量对照**：四项度量改后再量一次，出前后对照表。
5. **验收发版**：四轴审查 + 用户手动验收 + 发版 0.23.0。

## User Stories

### 装配域（H-09 / H-04 / H-01）

1. 作为维护者，我想让装配一个 agent 只传一个参数对象而非 14 个散参，以消掉「每加功能 +1 参 +2 重载 + 三处锁步」的事故根因。
2. 作为维护者，我想让 CLI / Web / headless 三处呈现位接线共享同一套装配模板，以避免 headless 首版漏挂管线超时与审计回答者的事故重演。
3. 作为维护者，我想让 agent 执行链对功能域的依赖走能力接口而非具体类直引，以便「功能插件在场自动生效」而非「不传参即 null 挂空」。
4. 作为维护者，我想让两处 `instanceof` 具体工具类的下探改为工具声明式能力接口，以便工具换实现或第三方替换时不再静默失效。

### 呈现位域（H-03 / H-13）

5. 作为第三方呈现位实现者，我想让呈现位身份由注册表发放而非写死两个常量，以便未来新呈现位零内核改动接入。
6. 作为插件开发者，我想让子代理宿主服务改名为 `host`，以消除与呈现位域 presenter 词汇的撞车，避免未来呈现位域发布同名服务时真冲突。
7. 作为插件开发者，我想让改名与删常量在插件扩展点清单等文档同一批改动里更新，以便文档读者拿到的是新契约而非过期 API。

### Web 域（H-10 / H-12）

8. 作为维护者，我想让 WebFace 按职责拆成同包协作文件（门面 / 入口栅栏 / 标签会话 / SSE 与事件投影 / 端点处理器），以使单文件回到可读体量且行为零变化。
9. 作为第三方插件开发者，我想让 fileRefs 服务走服务注册表（provide 发布 + 消费方 optionalInject）而非装配期自建直传，以便第三方能替换或补全文件引用实现。
10. 作为验收者，我想让 Web 全部既有测试与 17 个端点行为在拆分后原样通过，以证拆分是搬家不是重写。

### 取值源与重复消解（H-15 / Data Clumps）

11. 作为维护者，我想让 cwd 取值收敛到 core 模块的单一取值源，以便「可配 cwd」这类未来变化只改一处。
12. 作为维护者，我想让汉字判定与路径解析各收敛为一份实现，以消三处同构与双实现的锁步维护。

### javadoc 认事实（PluginSnapshot）

13. 作为插件开发者，我想让 PluginSnapshot 的 javadoc 与实际行为一致（快照 name 一律为插件类全名），以便不被注释误导。

### 模式对账册

14. 作为维护者，我想要一份设计模式对账册（命令分发族 / provider 映射 / 装配层的策略-工厂该用未用点逐条定性），以便「优雅化」有可对账销号的靶子。
15. 作为维护者，我想让对账册裁定「要改」的条目编入工单实现并有测试作证，以便审查不止于纸面。

### 度量与验收

16. 作为验收者，我想拿到改前改后的四项度量对照表，以便「优雅化」有数字证据而非口头宣称。
17. 作为验收者，我想亲手跑三呈现位（CLI / Web / headless）与 demo 统计插件全程，以确认重构没伤任何既有体验。
18. 作为维护者，我想让全仓 140 个测试类与 CI 在每张工单收口时全绿，以便小步重构永不带病前进。
19. 作为维护者，我想让 M27 的行序契约 fail-fast 与 demo「零既有行改动」基线全程保绿，以便重构不回炉刚验收的面。
20. 作为后续会话，我想让 H-06 / H-07 的评估结论（不修 + 理由）记档，以便呈现位解耦域与计划模式插件化在后续立项时有依据留底。

## Implementation Decisions

八问 grill 裁定（2026-09-28，全记录见 [ADR-0030](../../docs/adr/0030-M28规范化重构立项决策.md)；本节为执行细则）：

**八件必做（含四项 spec 期裁定）**

- **H-09 装配参数对象化 + 接线模板化**：三处装配大参（chatAgent 14 参 11 重载、ToolCallingAgent 14 参 10 重载、registerCommands 17 参、WebFace.start 13 参 5 重载）改 record 参数对象；重载族收缩为「每装配族至多一个全参形态 + 少量具名便捷重载」；三呈现位接线提公共模板，差异面（各自的工具/命令/回答者）参数化。手写静态工厂即可，不引 builder 库。
- **H-04 执行链依赖倒挂**：与参数对象化同批做——执行链的功能域字段（附件变体、图片投递、只读 bash 探测、记忆册、AGENTS.md 链）改能力接口 + 缺席语义，方向是「插件在场自动生效」。
- **H-01 类型下探改能力接口**：两处 `instanceof` 具体工具类改工具声明式能力（capability 接口），装配层按能力记账不按具体类。
- **H-03 呈现位注册表化（破坏性变更已许可）**：删 `PRESENTER_CLI/PRESENTER_WEB` 常量（全仓 24 处引用一次改齐），身份由注册表发放；headless 自造 PRESENTER_ID 的绕行同步收编为正规注册；扩展点清单同 diff 更新。
- **H-13 服务改名（spec 期裁定新名）**：`SubagentHost.SERVICE_NAME "presenter"` → **`host`**——服务语义即「子代理宿主」，与类名一致，把 presenter 一词还给呈现位域；服务名 = 视图方法名逐字契约，SERVICE_NAME、视图接口方法、消费方 inject 声明一次改齐。
- **H-10 WebFace 拆分（spec 期裁定切法）**：同包按职责拆五块——门面（生命周期 + 装配）、入口栅栏（Host/Origin/token 三级校验）、标签会话（TabContext 绑定与轮次线程局部）、SSE 与事件投影（客户端、心跳、游标、fail-closed 宽限）、端点处理器（17 端点 + route 声明表）；包私有协作，route 表声明式形态保留，行为零变化。拆后 web 域最大文件 ≤600 行。
- **H-12 fileRefs 服务化**：装配期自建直传改 provide 发布 + 消费方 optionalInject（扫描册已给修法，修法轻）。
- **H-15 + Data Clumps 消重**：`Path.of(System.getProperty("user.dir"))` 22 处收敛到 core 单一取值源；汉字判定三处、路径解析双实现各合并为一份。
- **PluginSnapshot javadoc 认事实**：注释改为「name 一律为插件类全名」；行为修正（name 用 yml id）归装载域 1.0 后，本期不越界。

**评估条裁定（spec 期，Q1 授权范围内裁，可推翻）**

- **H-06（CLI 私有事件/工具认知）不修记档**：修法需要新设计「事件呈现协议」（事件自描述、元数据驱动呈现），属设计类活，撞步子红线「不重新设计」；与 H-02 同归呈现位解耦域挂账（backlog）。
- **H-07（计划模式域内嵌）不修记档**：计划模式插件化是再架构非重构；其同根病灶（装配层按具体类记账）由 H-01 能力接口化部分消化。计划模式插件化挂后续域。

**步子大小红线（四条，全期生效）**

1. 拆分只做同类职责切分，不重新设计；
2. 越界冲动记档不修——对账单外的发现一律入 backlog；
3. 9 项独占面（M27 boundary.md）不碰；
4. M27 刚验收面不回炉——demo「零既有行改动」接入与行序契约 fail-fast 为不动面。

**度量口径（不引工具，脚本统计）**

- ① 最大文件行数 top10（改前 1812 行居首）；② 装配点参数个数（改前最大 17；目标：全仓最大装配点 ≤8 参，全参重载每装配族仅 1 个）；③ user.dir 同形计数（22 → 1 个取值源）；④ 重复代码组计数（汉字判定 3 处、路径解析 2 处、接线三连抄 3 份 → 各 1 份）。基线单随首个工单落 `.scratch/m28-refactor/`。

**产物归宿**

- spec 与工单、度量基线/对照表、模式对账册：`.scratch/m28-refactor/`。
- ADR-0030 已落 `docs/adr/`（含 ADR-0029 勘误注，已随立项 diff 落盘）。
- 改名与删常量的文档同步：`docs/05-参考/插件扩展点清单.md` 同 diff 更新。

## Testing Decisions

接缝方案：**无新接缝，全部沿用既有**——重构的完成证明恰是「行为零变化时既有 140 测试类全绿」，唯一成规模的新代码是参数对象与拆分文件，其行为面已被既有测试覆盖。

- **好测试的标准**：只测外部行为（命令可执行、端点响应契约、装配后服务可见），不断言内部实现细节；断言沿用 JUnit 原生 Assertions（全仓无 AssertJ/Mockito）。
- **装配相关测试**：断言插件装配类异常一律沿 cause 链收集消息匹配（duo-workflow 经验，M28 装配测试大批量出现的重犯面）；注意 cli 行 apply 即 REPL 主循环的阻塞语义（M27 修复 v2 教训），测试环境 Boot 前 System.setIn 空流先例照用。
- **行为零变化的证据**：既有测试套即行为基线——Web 10 类（含行序契约 WebPluginRowOrderContractTest）、example 11 类（含 DualPresenterAffinityTest、headless 装配）、agent 43 类（含 TwoLevelInboxTest 等呈现位路由）拆分后原样通过即证。新增小单测仅限取值源等纯函数（按既有单测形态，先例 M24-08 提取件）。
- **每工单收口判据**：全仓 `mvn verify` 绿 + 前沿两 grep 机械自检（duo-workflow 经验）。
- **验收 = 用户亲手跑**（duo-acceptance 三件套）：验收件 = CLI REPL 一轮对话 + Web 页面对话与审批 + headless 跑通 + demo 统计插件（/toolstats 报表与模型调工具）；度量对照表与模式对账册随验收一并出示。

## Out of Scope

- **H-06 呈现位私有事件/工具认知**——评估裁定不修（需事件呈现协议设计），与 H-02 同归呈现位解耦域挂账。
- **H-07 计划模式插件化拆分**——评估裁定不修（再架构非重构），挂后续域。
- **H-11 模块依赖逆挂、H-14 静态单例**——扫描册原判 M28+，本期不进。
- **装载域一切**——H-08 装载 FQCN/批量装载、H-16 Boot 复用面、PluginSnapshot 行为修正，1.0 后。
- **端点扩展点（插件加 HTTP API）**——H-10 只拆分不设计扩展点，归后续域。
- **前端工具名协议化渲染、视觉打磨**——M29 视觉期。
- **度量工具进构建**（PMD/CPD 等）——ADR-0029 已拒绝，维持。
- **理解关卡补考**——不排期、用户主动发起（ADR-0029 横切口径）。

# BUG-20260912-05 · DeepSeek 思考模式要求回传 reasoning_content（HTTP 400）

**Status**: closed（2026-09-12 用户重新验收通过，M5 两大场景全绿）

## 症状（建档时记录）

- 发现于：M5 工单 03 用户手动验收（tool_call_id 修复后）
- 原样引用：

```
你> 读一下 notes.txt
  [调工具] mcp__files__read_file {"path": "notes.txt"}
  [工具结果] agent 演示的文件内容
  [调工具] mcp__files__write_file {"path": "output.txt", "content": "测试"}
  [工具错误] 工具 "mcp__files__write_file" 执行被拒绝: 被审批策略拒绝（策略: always-deny）
  [错误] LLM 调用失败: HTTP 400 - The `reasoning_content` in the thinking mode must be passed back to the API.
```

- 复现方式：思考模型（deepseek-flash）+ Function Calling 链中第 3 轮 LLM 调用（两次工具结果回填后）。

## 排查记录

- 假设 1：tool 消息缺 tool_call_id（同上一次）→ 验证：本轮 tool 消息已带 tool_call_id（序列化修复已生效），前两轮 LLM 调用均成功 → **排除**
- 假设 2：DeepSeek 思考模式要求 assistant 消息的 reasoning_content 回传 → 验证：DeepSeek V3.2 文档明确工具调用场景下 thinking 模型的 reasoning_content 必须传回 API；适配器只捕获 delta.content，reasoning_content 被丢弃 → **成立**

## 根因

思考模型（deepseek-flash 等）的流式响应在 `delta.reasoning_content` 携带思考过程；工具调用链中，DeepSeek 要求把 assistant 消息的 reasoning_content 传回 API。适配器的 ChatChunk 只有 text、聚合结果 LlmTurn 也无 reasoning 字段——思考内容从第一轮就被丢弃，第三轮请求必然缺字段。

## 修复记录（实施于 2026-09-12）

1. `LlmTurn` 加 `reasoningContent`（可空）组件 + 2 参兼容构造；`aggregateTurn` 用 StringBuilder 按序聚合 `delta.reasoning_content` 增量（非思考模型为 null）
2. `ChatMessage` 加第 5 组件 `reasoningContent`（可空）+ 4 参兼容构造；仅 assistant(tool_calls) 消息回传时携带
3. `ToolCallingAgent.send`：`pendingReasoning` 逐轮跟踪（每轮 streamTurn 返回后更新），`withReasoning()` 把它附加到请求中最近一条 assistant(tool_calls) 消息（DeepSeek 只校验最近一轮）
4. `OpenAiCompatAdapter.requestBody`：assistant 工具调用消息有 reasoningContent 时输出 `reasoning_content` 字段（user/tool 消息永不输出）
5. 附带清理：适配器重复的 `Consumer` import

## 验证

- 新增测试 4 个：
  - `OpenAiCompatAdapterTest.streamTurnCapturesReasoningContent`——思考增量分帧聚合，textSink 不收思考内容
  - `OpenAiCompatAdapterTest.streamTurnOmitsReasoningWhenAbsent`——非思考模型字段为 null
  - `OpenAiCompatAdapterTest.assistantReasoningContentSerializesToRequest`——仅 assistant(tool_calls) 消息输出 `reasoning_content`
  - `ToolCallingAgentTest.reasoningFromToolRoundIsPassedBackOnNextRequest`——第 2 轮请求的 assistant 消息携带第 1 轮返回的思考内容
- `mvn -o test` 全量回归：0 失败 0 错误，BUILD SUCCESS
- 待用户手动验收：M5 场景一（读文件成功闭环）+ 场景二（写被拒后模型自行解释），思考模型下不再出现 400

## 防复发

- 真实 provider 协议字段（如思考模式扩展字段）在 mock 测试里天然缺失——「mock 验证机制、真实 provider 验证协议」的差距第三次出现。M5 收官后把"真实 provider 冒烟"固化进验收件清单
- 新增协议字段时先查 provider 文档的请求/响应两侧约束（本例响应侧捕获缺失 + 请求侧回传缺失，两侧都要补）

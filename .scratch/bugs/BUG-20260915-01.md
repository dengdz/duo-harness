# BUG-20260915-01 · workspace-write 档区内写不走放行短路——静默等 Web 卡片像"卡死"

**Status**: closed

## 症状（用户验收报告原样）

M12-02 验收第 4 步（workspace-write 默认档，区内新建写）：

```
你> 用 write 工具新建 hello-fs.txt，内容：你好
  [调工具] write {"path": "hello-fs.txt", "content": "你好\n"}
卡住了？
```

终端无 `[工具结果]`、无 `[待审批]`——静默悬挂（实际在等 Web 面回答卡片，兜底超时 10 分钟）。

## 排查

1. `[调工具]` 后无输出 → 卡在审批裁决段。demo 装配 web 行先于 cli 行（agent-demo.yml 注释：审批/提问由 Web 卡片优先呈现），`WebAnswerer` 先接住 ask 且不打印终端 → 终端静默属**回答者路由设计**，但不应有 ask 可路由。
2. 对照 spec 第 49 行"审批裁决经 WorkspacePolicy 档位——workspace-write 按 包含性 放行或 ask"：区内写应 **ALLOW 短路**，根本不进审批。实测却进了审批 → 档位裁决接线缺失。
3. 全代码 `\.decide\(` 检索：管线内唯一调用方 `ApprovalGate` 调的是 `ApprovalPolicyService.decide`；`WorkspacePolicy.decide()` **零调用方**（仅测试调用）——纯死代码，spec 联动从未落地。
4. `InteractivePolicy.decide` 无条件 `answers.ask(...)`，不查档位 → 一切 requiresApproval 工具（write/edit）必 ask。

## 根因

spec"权限预设与审批联动"只在工单 01 实现了判定函数（`WorkspacePolicy.decide`），**判定与审批管线的接线没有实现**；工单 02 checklist 写"档位裁决在策略层（工单 01）"含糊带过，实现方与审查方都未发现没有调用方。

## 修复

档位前置裁决插件（复用既有"approval"服务占位形态）：

1. `fs/WorkspaceGatePolicy implements ApprovalPolicyService`：先查 `WorkspacePolicy.decide(tool, argsPath)`——ALLOW 短路放行；ASK 委托内层策略（interactive 回答者瀑布）；路径缺失保守 ask（spec 原文语义）。
2. `fs/WorkspaceApprovalPlugin`：inject answers + workspace，发布 "approval" 服务 + PRE_EXECUTE 闸门（形态同 InteractiveApprovalPlugin）——yml 一行替换 InteractiveApprovalPlugin。
3. agent-demo.yml、CliPluginTest.Fixture 换挂新插件；补 gate 映射测试。
4. 验收对照表修正：demo 装配下 ask 由 **Web 卡片**呈现（web 先于 cli 是既定路由），终端 y/n 仅在纯 CLI 装配出现。

## 防复发

- spec 有"裁决经 X"字样的工单，checklist 必须落到"调用方在哪"的接线项，不能只写判定函数本身；审查时对新增判定 API 检索调用方。

## 验收验证（2026-09-15）

验收第 4 步实测：区内写 `[工具结果] Created file` 且决策日志 `结果=ALLOW 策略=workspace`——档位短路放行生效；越界写/read-only 档 ask 落 Web 卡片。closed。

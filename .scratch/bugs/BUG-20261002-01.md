# BUG-20261002-01 · /api/status 空响应——状态面自启动起五区块全「—」

**Status**: done（2026-10-02 M34 工单 01 修复：根因实钉 + optionalInject 补声明 + route 兜底；回归锁 WebPluginAssemblyTest 两用例绿）

## 症状（建档时记录）

- 发现于：M33 浏览器实测·工单 01 环境冒烟（隔离实例首启即现）
- 原样引用（curl 证据，2026-10-02）：

```
$ curl -sv -H "X-Duo-Token: <token>" http://127.0.0.1:62980/api/status
> Host: 127.0.0.1:62980
> X-Duo-Token: <token>
* Request completely sent off
* Empty reply from server
* Closing connection
```

  - 同刻对照端点全 200：`/api/sessions`（205B）、`/api/search?q=ls`（433B）、`/`（4031B）、`POST /api/stop`（409 忙时语义正常）
  - 变体：token 走查询参数 `?token=`、无 Origin 头、带 Origin 头——三种形态均 HTTP 000 / curl exit 52（连接被服务端无响应关闭）
  - 页面内 fetch 同报 `TypeError: Failed to fetch`（app.js:57 封装层）
  - 服务端日志零异常行（Exception/ERROR/WARN 全无）——静默失败
- 页面表现：状态面五区块（上下文 / 后台任务 / 连接器 / 插件六态 / 工具）自启动起全部渲染「—」与空表，实时刷新周期不恢复；截图见 `.scratch/m33-browser-audit/evidence/BUG-20261002-01-状态面空-冒烟通过面.png`（同帧左侧对话/工具卡/侧栏均正常工作）
- 复现方式：隔离实例启动（`DUO_HOME=/tmp/duo-m33/home java -jar duo-harness-1.0.0.jar /tmp/duo-m33/m33-smoke.yml`，web 单呈现位装配 + MCP echo 夹具）→ 任意时刻 `GET /api/status` → 空响应

## 排查记录（定位过程，逐步追加）

- 假设 1：tab 上下文缺席路径未兜底——`statusJson`（WebEndpoints.java:522-526）在 `face.tabs.resolveTab(exchange)` 返回 null 时返回 null，响应调用点对 null 无处理 → 写响应前异常/连接直接关闭，与「空响应 + 无日志」吻合 → 验证：源码实读 null 分支存在；同页其他 API 正常排除网络/栅栏面；异常静默符合「未走 WebEndpoints 各 handler 的 catch-and-500 形态」（对照 file-complete handler 的 error-log + 500 兜底）→ 结论：主假设成立度高的待证形态；**调用点 null 处理与 resolveTab 为何对已连接 tab 返回 null 未核**（修复批第一动作）
- 假设 2（待修复批排除）：web 单呈现位装配（无 cli 行）下 tab 注册链路缺环——本实例为首例 web-only 装配冒烟，历史上人工验收均为 web+cli 双位；若修复批在双位装配下不可复现，则病灶在「web-only 时 tab 生命周期」，仍是缺陷（降级形态不应断连）
- **假设 3（修复批实钉，2026-10-02，成立）**：MCP 行在场（connectorStatus 服务已发布）时，statusJson 连接器块 `hasService` 真 → `face.ctx.as(WebServiceViews.ConnectorStatus.class)` 被**插件声明闸门拒读**——WebPlugin.optionalInject() 未声明 connectorStatus（hasService 真 ≠ 可读，2026-09-22 记档同族）→ statusJson catch 后抛 IllegalStateException → `route()` 的 createContext lambda **无任何 try/catch** → 异常沿 JDK HttpServer 逃逸 → 连接裸关（空响应）+ 零日志。验证：M34 工单 01 回归锁 `statusServesConnectorSnapshotThroughPluginDeclarationGate` 修复前精确复现空响应（`HTTP/1.1 header parser received no bytes`，与 curl exit 52 同形态）；测试装配无 MCP 行 → CI 全绿的生产/测试分歧一并解释。假设 1/2 排除：resolveTab 两条 null 路径均先写 400/500（非空响应）；双位/web-only 装配均复现（与呈现位组合无关）

## 根因（定位后填写）

三层耦合（2026-10-02 M34 工单 01 实钉）：①**声明闸门拒读**——WebPlugin.optionalInject() 未声明 `connectorStatus`，MCP 行发布该服务后 statusJson 里 `hasService` 真、`as(WebServiceViews.ConnectorStatus.class)` 被内核「错误前移」拒（PluginException：服务未在依赖声明中）；②**statusJson 兜底升级**——catch(Exception) 后 throw IllegalStateException（意图上抛），但自身无日志；③**route 无兜底**——createContext lambda 无 try/catch，异常沿 JDK HttpServer 逃逸 → 连接裸关（空响应）+ 服务端零日志。三环缺一不成立：测试环境无 MCP 行（①不触发）且各 handler 有自己的 catch（③仅在 route 层缺）——故 CI 全绿而生产全盲。

## 修复方案（计划，改前填写）

已执行（M34 工单 01）：① WebPlugin.optionalInject() 补声明 `ConnectorStatusBoard.SERVICE_NAME`（根因修复——声明后闸门放行，连接器块可读）；② WebEndpoints.route() 加 try/catch 兜底——异常一律 log.error + 500「服务端处理失败」（防复发：请求级异常必落日志，绝不留连接裸关）。

## 修复与验证

- 改动：WebPlugin.java（optionalInject +1 声明、face() 包私有测试缝）、WebEndpoints.java（route 兜底 catch）
- 回归测试：WebPluginAssemblyTest 两用例——`connectorStatusDeclaredAsOptionalDependency`（声明断言）+ `statusServesConnectorSnapshotThroughPluginDeclarationGate`（端到端：MCP 首行发布形态全插件树启动 → GET /api/status 200 + 连接器快照；修复前精确复现空响应 `header parser received no bytes`）
- 防复发：回归锁入库（web 模块 102 测试全绿）；route 兜底使任何端点异常可见化（不再静默裸关）；备注——①「hasService 真 ≠ 可读」家族第三次出现（permission-rules / fileRefs / connectorStatus），下次新增服务消费方时 optionalInject 核对应作为提交前机械项；② A6 补充：WebPlugin.AnswerTimeoutMs=10 分钟为无断连最终兜底（HITL-05 挂 25 分钟未触发的口径疑点留观察）

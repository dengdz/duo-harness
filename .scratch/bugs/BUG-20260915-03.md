# BUG-20260915-03 · 流式中途刷新——已输出部分丢失，流结束才整段回来

**Status**: done（2026-09-16 用户验收通过——"从一数到 1000"刷新场景：已输出部分立即可见、101 无缝续接、收口覆盖无重复无碎片；随 M13-01 验收一并确认）

## 症状（建档时记录）

- 发现于：M13 工单 01（尾部窗口快照）用户手动验收；**0.7.0 既有缺口，非本次改动回归**
- 原样引用：
  > 我让它从一数到1000，我刷新，然后它能从断的地方继续，但是之前的会丢掉。我说的之前是，比如说我说让它从一数到1000，它从一开始数，我看到它到100的时候我刷新，它能够从101继续输出，但是1~100会丢掉，但是整个消息都结束完的时候，1~100又能看到了。
- 复现方式：Web 发"从一数到 1000" → 流式输出到 ~100 时刷新页面 → 刷新后从 101 续流、1~100 不见；整条消息输出结束后 1~1000 整段重现

## 排查记录（定位过程，逐步追加）

- 假设 1：M13-01 尾部窗口把前段 chunk 截掉了 → 验证：刷新时会话投影消息仅 1 条（user/message 在场；chunk 不投影、assistant/message 未落地），`tailWindow(50)` 未截断走起点 0 **全量回放**（本轮修复还专门保证前导事件不裁），chunk 事件帧实际已重发 → **排除**（会话很小，截断不是原因）
- 假设 2：前端回放门丢弃回放期 chunk，而进行中轮次无收口文本可渲 → 验证：app.js `if (event.type === 'assistant/chunk' && replayed) return;`（注释"历史碎片不回放"）无条件跳过边界帧前的一切 chunk；该轮 assistant/message 尚未落地 → **成立**
- 佐证（症状闭环）：流结束后 assistant/message（完整文本 1~1000）作为实时帧到达 → `finishAssistant` 整段渲染 → 1~100 重现，与"结束完又能看到"精确吻合
- 佐证（非回归）：`git show 0.7.0:duo-harness-web/src/main/resources/web/app.js` 第 369 行同款代码在场 → 0.7.0 即此行为，只在"流式中途刷新/断线重连"暴露，此前验收未覆盖该时序

## 根因（机制层）

回放门（BUG-20260913-04 引入的 replay/done 边界帧语义）把"边界帧前的 chunk 一律不渲染"当作防碎片化手段：已完成轮次随后被 assistant/message 收口覆盖、无感；但**流式进行中**的轮次其收口帧尚未落地——chunk 被丢后，该消息已输出部分在"刷新 → 流结束"窗口内不可见，直到收口帧整段补回。防碎片化（目的正当）与进行中轮次的可见性（未覆盖场景）被同一条无条件丢弃规则绑在了一起。

## 修复方案（计划，改前填写）

- **方案 A（推荐）**：回放门放行 chunk——历史轮次 chunk 流入 streamingBubble，随后 assistant/message 经 `finishAssistant` 清空重渲整段（既有收口覆盖逻辑天然防重；chunk 统一进同一 bubble，不复发 0913-04 的"独立气泡"碎片化）；进行中轮次已输出部分立即重现，实时 chunk 无缝续接同一 bubble。代价：大历史回放 chunk 逐个 `textContent +=` 的开销——M13-01 尾部窗口已限制窗口内事件量，必要时对 chunk 渲染做 scroll 节流。
- **方案 B**：只补渲"未收口末段"——回放期照旧收集 chunk，replay/done 时末段若无 assistant/message 收口才渲染。精确但前端状态机复杂化，尾部窗口下收益变小。
- 影响面：仅 app.js 回放门一处；SSE 协议、服务端零改动。
- 防复发预案：前端 JS 不在自动化测试范围（spec Testing Decisions）→ 验收对照表补"流式中途刷新"真实场景（本次缺口的直接来源）。

## 修复与验证

- **改动**（2026-09-15，用户裁定方案 A）：仅 app.js 三处，服务端与 SSE 协议零改动——
  1. 回放门放行 chunk：删"边界帧前 chunk 一律跳过"，回放期碎片照常流入 streamingBubble，assistant/message 收口时整段覆盖（既有防重逻辑）；进行中轮次刷新后已输出部分立即重现，实时 chunk 无缝续接同一气泡。
  2. chunk 分支不触发状态面刷新（回放可达千帧，逐帧 fetch /api/status 不可接受；5s 轮询兜底，语义无损失）。
  3. 顺带摘除死状态机 `replayed`/`isReplaying`（唯一消费者就是被删的跳过行，全仓 grep 无调用方）；scroll() 合并到 rAF（回放/流式逐帧强制 reflow 的缓解，方案 A 录档时预告的节流）。
- **验证**：node --check 过；前端 JS 无自动化（spec Testing Decisions）——浏览器视觉验证项：流式中途刷新已输出部分立即可见、收口整段覆盖无重复无碎片、历史回放正常。随 M13-01 验收执行。
- **防复发**：前端 JS 不在自动化测试范围 → 验收对照表（工单 01 验收件）固化"流式中途刷新"真实场景为常设验收点；回放语义改动必须对照 0913-04（碎片化）与本案（进行中可见性）两个方向同时检查——防碎片化不能以丢弃为手段。

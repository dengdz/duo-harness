# M32（1.0.0）收口盖章——「盖钢印」

Status: ready-for-agent（工单待拆，见 issues/——下一步 /to-tickets）

## Problem Statement

- **1.0 还没有权威答案**：版图（ADR-0029 → ADR-0033）到 M31 为止的工程与文档期已全部交付（0.22.0-0.27.0 六期），1.0 判定标准四项的核对对象全部就位，但「1.0」尚未盖章——当年列的具名候选没有一份逐项终审档案；1.0 明确不做哪些（移出项 + 1.0 后菜单）没有一次性明示；判定四项没有逐项出示证据；1.x 怎么发版、承诺什么，没有任何声明。使用者拿不到「1.0 意味着什么」的依据，维护者回看「当年想过的都去哪了」无档案可查。
- **版图终态未钉**：M32 是版图最后一期，之后项目进入无路线图状态，「盖章之后怎么办」若不写明，1.0 后第一件工作无流程可依。
- **一处陈账**：backlog「03-高级章节」条目仍挂「未实施」勘误注，实际三章已随 0.25.0 交付（CHANGELOG 在案）——1.0 前 backlog 应反映真实状态。

## Solution

五件纯手续（范围与裁定以 [ADR-0034](../../docs/adr/0034-M32收口盖章立项决策.md) 为准；代码零改动）：

1. **具名候选终审**：ADR-0007 候选清单逐项核对「已做（对应里程碑）/ 明确不做（出栈决议）」，出终审档案。
2. **移出项与 1.0 后菜单终审**：ADR-0024 移出项清单 + backlog「1.0 后菜单」逐条明示出栈；顺带销账 backlog 陈账（03-高级条目等）。
3. **1.0 判定四项出证据**：候选全清 / CI 绿常态（跨期复核）/ 文档三层齐备（核对对象 = M31 大改后文档站）/ 安全基线闭合——acceptance.md 四项各一节逐项出示证据（ADR-0033 预裁形态）。
4. **1.x 版本策略声明**：语义化版本（1.x 内向后兼容）+ 按需发版 + 对照系惯例一句；落 README 小节 + 文档站短页，决策理由随 ADR-0034。声明前做一轮轻量对照调研（ZCode 主、DSH 辅的版本策略声明惯例）。
5. **盖章 1.0.0**：CHANGELOG 落 1.0.0 段（择要并入判定四项证据结论）→ tag v1.0.0 → release.yml 自动挂 GitHub Release。

## User Stories

### 终审与证据

1. 作为维护者（未来的我），我想要一份具名候选逐项终审档案（每项：候选名、归宿——对应里程碑或出栈决议、凭证锚点），以便回看「当年想过的都去哪了」时有据可查。
2. 作为维护者，我想要移出项与 1.0 后菜单的明示出栈清单（每条：项名、当初为什么移出、1.0 后从菜单挑活的入口），以便 1.0 后开工时清楚边界与初衷。
3. 作为验收者，我想拿到判定四项各一节的证据核对表（每项：判据原文、证据——路径/命令/输出、结论），以便亲手核验 1.0 的成色而非听代理自证。
4. 作为部署者，我想让 CI 绿常态有跨期复核证据（近期 GitHub Actions run 清单与结论），以便相信主分支处于可用常态。
5. 作为维护者，我想让 backlog 陈账随终审顺手清账（「03-高级章节」等已交付未销账条目），以便 1.0 时点的 backlog 反映真实状态。

### 版本策略声明

6. 作为潜在使用者，我想在 README 看到 1.x 版本策略声明（向后兼容承诺、按需发版节奏），以便判断 1.0 是否可以依赖、升级会付出什么。
7. 作为文档站读者，我想要一篇版本与发布策略短页（语义化版本口径、发版形态、与 CHANGELOG/Release 的关系），以便不进 GitHub 也能知道发版规律。
8. 作为关注承诺依据的使用者，我想让声明附带对照系惯例说明（ZCode 主、DSH 辅怎么做版本策略的调研结论），以便确认承诺不是拍脑袋。
9. 作为维护者，我想让版本策略的决策理由与调研结论有 ADR 档案（ADR-0034），以便日后调整策略时知道当初为什么这么定。

### 盖章与发版

10. 作为关注项目的人，我想让 GitHub 上出现 v1.0.0 Release（jar 产物 + 发布说明），以便有明确的 1.0 下载锚点。
11. 作为 CHANGELOG 读者，我想让 1.0.0 段包含判定四项证据结论的择要，以便不翻验收档案也知道 1.0 凭什么盖章。
12. 作为拿 jar 的使用者，我想让 v1.0.0 的 jar 实测 `java -jar` 可跑（双呈现位 + headless），以便下载即用。

### 流程与验收

13. 作为验收者，我想逐件亲手验收（终审清单目测、证据核对表逐项过、README/文档站声明目测、Release 页面与 jar 实测），以便 done 由我判定。
14. 作为 1.0 后的维护者，我想让「之后怎么办」（轻量里程碑制延续、活从菜单按需挑）写进 ADR-0034，以便 1.0 后第一件工作知道按什么流程走。

## Implementation Decisions

五问 grill 裁定（2026-10-02，全记录见 [ADR-0034](../../docs/adr/0034-M32收口盖章立项决策.md)；本节为执行细则）：

- **纯手续期纪律**（沿 M31 先例）：代码零改动——本期动面仅 README、文档站、CHANGELOG、backlog、acceptance.md、ADR 注；发现文档与代码不符时按现状写，行为争议开 bug 台账。
- **终审事实基础**（均已预核，走手续）：具名候选 = ADR-0007 清单（ADR-0029 已核「全 done 或出栈」）；移出项 = ADR-0024 移出项清单；1.0 后菜单 = backlog 对应节约 15 条。终审只做逐项核对与出档案，不重开任何决议。
- **证据形态**（ADR-0033 预裁沿用）：acceptance.md 四项各一节（判据 / 证据 / 结论三段式）+ CHANGELOG 1.0.0 段择要并入；终审两清单（具名候选、移出项与菜单）作为证据附件同落 acceptance.md。
- **版本策略口径**：语义化版本——1.x 内向后兼容（新功能进 minor、修缺陷进 patch、破坏性变更才到 2.0）+ 按需发版 + 对照系一句。对照调研在声明工单内执行（ZCode 主、DSH 辅），结论写进声明正文；ADR-0034 落卷不回填。
- **声明落点**：README 一小节（快速开始/能力概览之后的门面段）+ 文档站参考层一篇短页（与「已知限制」并列的位置关系由工单期按 sidebar 结构定）；两处内容同源（短页为准，README 择要）。
- **盖章链路**：照旧自动化不特殊化——CHANGELOG 1.0.0 段 → tag v1.0.0 → release.yml 自动挂 Release（M30 起两轮验证稳定）；不手写公告。
- **1.0 后运转**：轻量里程碑制延续——活从 1.0 后菜单 / backlog 按需挑，每件仍走既有流程，不立新路线图（ADR-0034 版图终态）。
- **记账口径**：README 声明、文档站短页、1.0.0 发版均为用户可见变更——各工单同 diff 在 CHANGELOG 记账（红线 6）；1.0.0 段由盖章工单落日期。

## Testing Decisions

- **接缝全复用既有，零新接缝**（M31 同构且更纯——零代码）：
  - **证据接缝**：每项判据出示可复核的路径/命令/输出（证据先行）；CI 复核走 GitHub Actions 页面/API（本机无 gh CLI）。
  - **文档接缝**：文档站短页过 vitepress build 闸门；README 改动目测（不涉构建）。
  - **发版接缝**：tag v1.0.0 → Release 页面产出 jar，实测 `java -jar` 启动（M30 发版验收同款）。
- **只测外部行为**：证据可复核、声明可读、产物可下载可运行；不为手续期新建任何测试设施。
- **回归红线**：main 面 Java 源码与构建配置零 diff（本期动面仅 README / docs / CHANGELOG / .scratch / ADR）；文档站构建跨工单保持通过。

## Out of Scope

- 理解关卡补考：不排期、用户主动发起，不作为盖章前提（ADR-0029 横切口径，M32 grill 确认维持）。
- 1.0 后菜单任何条目的实施（本期只终审明示，不动工）。
- 演示入口（DemoMain 等）jar 形态适配——承诺外维持挂账（ADR-0033 范围排除节）。
- Release 公告文案手写/仪式化（ADR-0034 裁定照旧自动化）。
- 新功能、重构、依赖变更（纯手续期，代码零改动）。
- 1.x 路线图规划（1.0 后需要时再议，需新 ADR——ADR-0034 版图终态）。

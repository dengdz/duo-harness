# M27 预演三件——goal / schedule / agents[] 卡点推演

> 工单 03 产物。方法：以插件实现者身份走"今天做成插件"的路径，撞墙处即卡点；卡点按病丑判据对照回填扫描册，够 05 触发的点名移交。事实引用：[boundary.md](boundary.md)（独占面 C1-C9、扩展点 A-E）、[hardwired-scan.md](hardwired-scan.md)（H-xx）。
> 基线事实（01/02 已核实）：插件可听事件 = `plugin/status` + 工具三段瀑布 + 自定义事件；会话事件不可听、Session 非服务；收件箱与循环边界内嵌 agent 域、非服务。

## 预演一：goal 跨轮目标域

**需求回放**（1.0 后菜单原条目）：每 session 持久目标 + CAS 修订 + 人类权限门 + 自动续跑；与 todo 轮内清单正交。

**尝试路径**（作为插件作者逐段写）：

1. 存目标 → 插件自有文件（DuoHome 下）+ config record。✅ 无障碍。
2. 目标 CRUD 工具（set_goal / query_goal）→ 扩展点 C1 工具注册。✅ 无障碍。
3. 人类权限门 → 工具声明 ask 走审批。✅ 无障碍。
4. 跨轮追踪"目标完成了没有" → 需要感知**每轮结束** → 可听面没有 turn 边界事件（事件面事实卡：只有工具三段）。⛔ **卡点 α：turn 边界不可感知**（独占面 C3）。
5. 目标关联到会话 → 需要 session 身份；ToolExecution 载荷无会话引用（backlog 在册），Session 实例非服务（独占面 C4/C8）。⛔ **卡点 β：会话身份不可达**。
6. 目标未完成 → 自动开新轮注入"继续" → 收件箱是 ToolCallingAgent 内部两级队列、非服务；插件无任何"触发一轮"的入口。⛔ **卡点 γ：再触发无通道**（独占面 C3）。

**定性**：α/β/γ 同域——独占面 C3（循环边界）+ C4（会话事件面）。修复需 agent 循环挂点设计与会话服务化，**超出接口手术精度**，归宿 1.0 后。性质是"没有挂点"而非"接线写死"——不新增扫描册条目，boundary 独占面 C3/C4 即台账。

**今天能做的半边**：**goal 记录本插件**——存储 + CRUD 工具 + /goal 命令 + 权限门，全部现有插口；"自动续跑"缺席（人工续）。且因卡点 β，记录只能按 cwd 项目锚定而非按 session——半边价值打折，本期不做。

## 预演二：schedule 会话内定时提醒

**需求回放**：会话内定闹钟（"20 分钟后提醒我"），到点把提醒送进对话。

**尝试路径**：

1. /remind 命令 + set_reminder 工具 → 扩展点 D1/C1。✅ 无障碍。
2. 到点触发 → JDK ScheduledExecutor 插件内自持。✅ 无障碍——**时间域其实不需要内核调度服务**（Boot 一次性引导不妨碍插件自己带时钟）。
3. **提醒送进对话** → 三条路全断：
   - a. 收件箱注入 next-turn → 收件箱非服务（独占面 C3）。⛔ 断。
   - b. 触发新 turn（模型看到提醒自己复述）→ 无"触发一轮"入口。⛔ 断。
   - c. emit 自定义事件让界面显示 → 呈现位只对已知事件/工具有反应（H-02/H-06 私有认知），自定义事件无人消费。⛔ 断。
4. 会话切换/关闭后提醒归属 → session 身份不可达（同预演一卡点 β），提醒可能落到错误会话。

**定性**：核心缺口 = 收件箱未服务化 + 循环不可触发（独占面 C3），**超出接口手术精度**，1.0 后。正面论证：定时器半边自持即可——**收件箱一旦服务化，schedule 立即可行**，它是循环域挂点（C3 解冻）后的首个受益者；goal 还需 turn 边界，排其后。

**今天能做的半边**：提醒本（存储/工具/命令 + 到点打日志）——提醒无法送达对话，半残形态，**不建议做**（demo 已另选统计员，Q5 裁定）。

## 预演三：agents[] 声明式自启

**需求回放**：yml 声明一批插件（含各自配置）启动时自动装载；理想形态含 jar/目录 drop-in。

**尝试路径**（这条有惊喜——半数路是通的）：

1. 写 meta-plugin：config record 声明插件清单（类名 + 各自 rawConfig）→ apply 里逐个 `ctx.plugin(new X(), subConfig)`。✅ **可行**：编程挂载是公开 API（扩展点 A2/A3）；rawConfig 透传由内核绑定（Context.plugin 契约，Map/JsonNode 均可）；依赖排序由 inject 自动解决、无需手工排布；子插件进 snapshots 状态面可见。
2. 类从哪来 → 必须已在 classpath（C7/H-08）。⛔ **卡点 δ：类发现前置**——drop-in jar 不可行，声明式自启只覆盖"已编译进部署"的类。
3. Boot 的装载职责（行解析、problems 点名报错、disabled 语义）没有对插件开放的复用面 → meta-plugin 复刻这些 = 旁路 Boot 校验、造第二套装载语义。⛔ **卡点 ε：Boot 职责无复用面**（新发现，回填扫描册 H-16）。
4. 声明清单里若有呈现位类插件 → H-05 行序契约（web 先于 cli 等）不在依赖图内、meta-plugin 自身的挂载时机也受行序约束——**H-05 实证确证：批量挂载放大行序玄学**。
5. jar/目录 drop-in（理想形态）→ 即 H-08 本体，1.0 后。

**定性**：δ = H-08（病，修复出栈 1.0 后）；ε = 新增 H-16（丑，1.0 后装载设计域，与 H-08 同解）；**H-05 确证为"实质拖累"**——批量挂载场景下部署者既要懂行序玄学又要懂嵌套声明。**移交 05**：H-05 是预演出的唯一够判据的修复候选（"实质拖累挂载" + 修法在接口手术精度内：Boot 装载期行序契约 fail-fast 校验、点名违规行与契约来源）；最终圈定待 04 demo 卡点合并。

**今天能做的半边**：classpath 内插件的声明式批量挂载——**可行且零内核改动**。本预演的正面产出：agents[] 的"声明"半边不欠内核的债，欠的只是类发现（H-08）。

# C1 · 技能写作体系改造：mattpocock-skills 机制级对比分析与 duo 技能全量改写

Status: done（2026-09-25 用户终验确认收官——13 张工单全 done、机械核对全绿、统一推送完成；行为层路由/收口观察按 ADR-0027 Consequences ④ 持续，异常走 bug-ledger）

## Problem Statement

duo-harness 的 15 个自研技能（`.agents/skills/duo-*`）在实际运行中会被模型忽略或偏离预设流程。这不是猜测——仓库自己的流程档案留下了实证：

- duo-code-review 的变更历史自诊断（SKILL.md 变更历史 2026-09-22）：*"「顺序固定不跳步」是描述性条款、无机械校验点，跨会话后必然衰减"*——OCR 审查轮自工单 03 起滑移，豁免记录消失；
- duo-workflow experience.md：工单 01 提交被撤回后，工单 06 又出现 5 处调试残留；上一会话总结声称"CHANGELOG 已记"实际未落盘——**凭记忆声称完成**；
- M24 期间四轴审查的 brief 曾即兴手写导致派发偏差（名单手挑、规则手写、范围模糊），被迫以变更历史固化 brief 填空模板补救。

同一时期，mattpocock-skills 插件（37 个 SKILL.md）的技能在运行中表现出稳定的流程遵从性。初步对比（2026-09-23/24 两轮）把差异指向**机制层**而非措辞偏好：调用权分流、显式工具调用依赖、证据先行判据、独立用户检查点、成文的写作理论（writing-for-agents）与全库剪枝纪律。但该初步分析是轻量的——**不足以作为全量改写的依据**。

问题statement：duo 技能体系需要一个**独立、完整、以改写为目的**的机制级分析，以及依据它落地的全量改写——让 duo 技能获得 mattpocock 级别的"模型照着执行"的可靠性，同时保留 duo 已有的差异化资产（experience.md 经验回流、豁免治理、brief 填空模板）。

## Solution

C1（插入计划，术语表已落词条）以**改写为主**分四段交付：

1. **分析段**：两侧技能全量一手通读（Matt 37 + duo 16 + 元文档 4 份），产出机制级对比分析与《技能写作规范》建议稿，落 `docs/research/mattpocock-skills/`（锚点 = 插件版本 1.2.3）；
2. **决策段**：立 ADR-0027《技能写作规范：移植 writing-for-agents 与调用权分流》——分析完成后、改写开工前；
3. **改写段**：依据 ADR-0027 与分析结论，全量改写 15 个 SKILL.md + AGENTS.md 路由表（同 diff）+ docs/agents/domain.md 词汇治理；
4. **收口段**：统一重放演练（历史真实案例按新流程走一遍，对照行为），外加术语表「C1」等新词条的口径复核。

前一轮轻量分析（~/Downloads/skill-writing-analysis-20260924.md）降级为背景线索：它的对比维度与候选改写清单可作 C1 分析阶段的**输入假设**，但每一条结论必须在 C1 内重新独立推导与验证，修正以 C1 为准。

## User Stories

1. 作为技能作者，我要每个 description 的触发词前置且精简（≤60 字），以便模型触发匹配不被身份叙述稀释
2. 作为技能作者，我要 AGENTS.md 路由表与各技能 description 在同一 diff 内同步演进，以便两个路由视图永不分裂
3. 作为技能执行者（agent），我读到的跨技能引用是显式的工具调用指令（`Call the Skill tool with "duo-acceptance"`），以便目标技能被真实加载而非凭记忆执行
4. 作为技能执行者，流程类技能的每个阶段都以可出示证据的完成判据收尾（落盘路径、命令输出、文件存在性），以便"声称完成"可以被机械校验
5. 作为技能执行者，关键检查点（交用户确认、等待答复）是独立的阻塞步骤而非括号内提示，以便长上下文中不被跳过
6. 作为技能执行者，指令以正向动作序列表达（"出示四轴落盘路径"），而非三重否定的情态堆砌（"现场裁量豁免无效"），以便减少认知负荷与反向激活
7. 作为技能作者，我要每技能的变更历史迁出 SKILL.md（入 experience.md），以便技能正文保持零沉积
8. 作为技能执行者，duo-skill-evolution 的复盘流程瘦身到一屏以内，以便红线 8 的强制复盘真正每次被执行而非被跳读
9. 作为技能作者，我在写新技能或改老技能时有一部中文《技能写作规范》可依（指针/判据/领先词/否定/剪枝五支柱 + duo 正反例），以便不靠直觉写作
10. 作为未来会话的 agent，我在 docs/research/mattpocock-skills/ 能读到机制级对比分析的全文与锚点，以便理解 duo 技能写法背后的"为什么"
11. 作为技能作者，我用词有词汇表约束（工单/验收/收口等每词首选 + Avoid），以便跨技能协作不被同义词分散
12. 作为用户，元技能（duo-code-review / duo-acceptance 等）的改写以真实场景重放的行为差异作为验收证据，以便"改好了"不依赖文档级自审
13. 作为用户，C1 收口时有一次统一重放演练（历史真实案例按新流程重走），以便多张改动的组合效果被整体验证
14. 作为用户，改写不引入任何产品代码（Java）变更，以便 C1 与发版流程完全解耦
15. 作为技能执行者，流程的异常路径（坏基点/空 diff/服务缺席）写成显式的 fail-fast 步骤，以便失败发生在派发与深挖之前
16. 作为技能作者，frontmatter 的 YAML 值一律合法（含引号纪律），以便 discovery 不因解析失败静默丢技能
17. 作为未来会话的 agent，我开工任何 duo- 技能前读它的 experience.md 仍能读到全部历史经验（红线 8 机制不变），以便改写不损失"越用越好"的回流能力
18. 作为用户，改写后的技能仍保留豁免治理（双处记档 + 显式确认）与 brief 填空模板，以便可靠性与严格度同时保住
19. 作为技能执行者，skill-evolution 的进化判据是一句正向原则（"下次少犯一个已记录的错误"），以便复盘不退化为形式
20. 作为用户，C1 的全部产物（分析/规范/ADR/讲义）落盘在仓库内可达路径，以便后续会话与团队直接复用

## Implementation Decisions

以下每条均来自 2026-09-24 grill 会话的用户裁定，编号对应对话顺序：

1. **C1 定位 = 插入计划**（术语表已落「计划域/C1」词条）：不发版、不走版本分支、编号独立于 M 系列。
2. **以改写为主**：分析阶段独立重做结论并作为改写唯一依据；2026-09-23/24 两份轻量分析（~/Downloads）降级为背景线索与输入假设，不构成结论来源。
3. **分析产物归宿 = `docs/research/mattpocock-skills/`**（duo-research 域）：锚点 = 插件版本 1.2.3；源为插件缓存而非 git 检出，duo-research 的"拉最新 + 记锚点"适配为"核对插件版本未变"。
4. **ADR-0027 时点 = 分析完成后、改写开工前**：主题《技能写作规范：移植 writing-for-agents 与调用权分流》，含"调用权分流（frontmatter 硬隔离）以 harness 能力探测结果为准"的裁定框架——探测不支持时以正文点名文件+章节 + AGENTS.md 显式命令表兜底并记档。
5. **改写验收 = 行为级**：逐单真实场景试用（改哪类技能即重放哪类真实场景：审查/建档/推送/触发路由）+ C1 收口统一重放演练（从 .scratch/review-log.md、bug-log.md 挑有完整过程记录的历史案例）；**元技能自审（duo-code-review 审自身 diff）只保文风一致，不充当行为验收**。
6. **学习形态 = 无闸门**：讲义随分析报告交付（每课一个机制主题 + 双方原文对照），用户自行阅读。
7. **改写范围**：15 个 duo-* SKILL.md + 根 AGENTS.md 路由表（与 description 同 diff 双向同步）+ docs/agents/domain.md（词汇治理节）；`.duo/skills/release-notes`（演示技能）不在范围。
8. **改写内容清单（候选，最终以 C1 分析结论修正）**：description 三规则重写；跨技能引用改显式调用；收口/完成判据改证据先行；检查点独立成阻塞步骤；箭头链流程补 Done when；否定收敛为正向判据 + 至多一条硬护栏；变更历史迁出 SKILL.md；duo-skill-evolution 瘦身（328→≤120 行，输出模板不写死人格前缀——前缀由模型响应时按全局 AGENTS.md 规则套用）；fail-fast 预检；domain.md 词汇治理。
9. **保留的差异化资产（改写不得损失）**：experience.md + 红线 8 复盘回流；豁免治理（双处记档 + 用户显式确认 + 每次独立决定）；brief 填空模板；表格化分支；duo-java-review L0/L1/L2 渐进加载；判例节。
10. **术语表**：「C1（插入计划）」词条已落（计划域）；改写过程中新增词条（领先词、上下文指针等）随实现同 diff 追加。

## Testing Decisions

C1 的交付物是技能文档——**没有自动化测试可依赖，验收 seam 全部是行为级的**：

- **逐单重放 seam**（每张改写工单绑定一个真实场景）：
  - duo-code-review 改写 → 取一个真实未审小 diff，按新流程完整跑四轴，对照"新旧流程行为差异清单"作为验收证据；
  - duo-bug-ledger 改写 → 报一个真实小缺陷（如文档与实现不一致），按新流程走完建档→排查→归档；
  - duo-pre-push-checks 改写 → 一次真实推送按新证据表选检查；
  - AGENTS.md 路由 + description 改写 → 用真实口语说法触发路由，核对命中预期技能；
  - duo-skill-evolution 改写 → 下一次真实复盘按新模板走。
- **机械核对（文档级）**：frontmatter YAML 可解析（全部技能）；markdown 相对链接可达；AGENTS.md 路由表 ↔ description 触发词双向对账；domain.md 词汇表 ↔ SKILL.md 用词抽查；改写触及 docs/ 时跑 `npm run docs:build` 防死链。
- **不适用**：`mvn test` 全量回归（无产品代码变更）——但若改写过程误触 Java 文件，立即升级为全量回归并视为事故记档。
- **收口演练**：从历史档案挑 1 个有完整过程记录的真实案例（review-log 或 bug-log），按改写后全流程重放，输出"新旧行为对照"作为 C1 级验收件，用户手动确认。

## Out of Scope

- duo-java-review 的**规则条款本体**（L1 规则文件内容）——只做入口/工作流/措辞的结构适配，不增删阿里手册条款；
- 一切产品 Java 代码、yml 配置、pom——C1 与发版完全解耦（若误触即事故记档）；
- harness 侧为 `disable-model-invocation` 类字段做支持性开发——只探测、记档、按兜底方案落地；
- M25+ 新技能的编写（只受 ADR-0027 规范约束，不在 C1 内动工）；
- mattpocock-skills 源仓库的任何改动（只读参考）；
- 发版与版本分支操作（C1 不发版；全部产物直接落 main 的文档提交——技能与文档变更随各自工单提交，经用户确认）。

## Further Notes

- **工单拆分预期形态**（to-tickets 阶段细化）：分析组（Matt 侧机制精读重做 → duo 侧逐技能对照 → 对比报告 + 讲义落 docs/research/）→ ADR-0027 → 改写组（按技能族出票，每票绑定重放 seam）→ 收口组（统一重放演练 + 术语表/导航终对账）。
- **重放演练案例选取标准**：过程记录完整（有排查/审查全轨迹）、场景单一代入性强、不涉真实密钥或外部服务。
- **与既有里程碑的关系**：C1 产物（写作规范 + ADR-0027）是 M25 起新技能的前置约束；M25 启动前 C1 必须收口。
- **风险记档**：description 全量重写 = 触发行为整体变更——改写单独立成 commit 保证可整体回滚；改写后预留一个真实使用周期观察触发命中，异常再修。

# 技能写作规范

本文是 duo 技能（`.agents/skills/duo-*` 的 SKILL.md）与根 AGENTS.md 路由表的写作与改写标准：M25 起新技能写作的前置约束，C1 改写组（工单 05–11）的执行依据。决策依据 [ADR-0027](../adr/0027-技能写作规范移植与调用权分流.md)；机制语义争议的终审依据是 `docs/research/mattpocock-skills/` 三件套（机制清单 / 对比报告 / 讲义）的原文锚点。文风层面（命题完整性、契约保留、注释规范）沿用 duo-prose-standard 技能的既有条款，本文不重复。**示例锚点说明**：正反例引用的是 C1 改写前的技能现状快照（原文行号见对比报告 §2），技能随改写演进后按节名定位现行形态，反例如已改写即成历史例证。

写作前先读一遍总则；逐支柱对照条款与正反例；收尾用附录的机制面覆盖表自查。

## 总则：技能是机制，不是文案

模型照着执行的程度由**机制**决定——结构（谁能否达、材料在哪一层）、判据（何时算完成）、指针（怎么措辞）——不由措辞的恳切程度决定。以下两条预算贯穿全文：

- **常驻负载**：description 与 AGENTS.md 路由行每一回合都在花上下文，逐字剪；duo 无 harness 级调用权隔离（ADR-0027 探测记档），全部技能常驻可见，剪枝的收益直接等于触发准确性。
- **认知负荷**：靠人记住"何时敲哪个命令"的成本，由 AGENTS.md 显式命令表一处承担——技能正文不再复述"本技能不可自动触发"之类散文声明，改为判据承担（支柱一）。

信息层级三级：步骤内联（正文按序执行）→ 文内参考（表格、判例，按需查阅）→ 外置参考（`references/` 文件，指针后加载）。只在部分分支触达的内容一律下移，正文只留每条路径都要走的步骤。

## 支柱一：上下文指针与 description 三规则

### 1.1 description 三规则与预算

规则：**领先词前置**（首词即技能本体，中英并列锚点如"收口（wrap-up）"）；**身份句删除**（正文 H1 已携带）；**触发按概念收敛**（写"任何'现实与预期不符'的陈述"，不罗列口语变体），触发词独立成句放尾部。预算：AGENTS.md 显式命令表内技能 ≤60 字，模型触发技能 ≤80 字。

> 反例（duo-bug-ledger/SKILL.md:3，约 220 字全库最长）：身份 + 建档流程叙述 + 七种触发说法 + 与 diagnosing-bugs 的分工，全部塞进常驻上下文——分工说明属正文，流程叙述属步骤，都在错误的层。
>
> 半正例（duo-pre-push-checks/SKILL.md:3，94 字）：体量与触发短语前置均已达标，尾部仍罗列口语变体（"推一下""跑测试"）、无中英并列锚点——全库最接近达标的现存形态。目标形态样例见讲义课 4 附录（docs/research/mattpocock-skills/讲义.md）。

### 1.2 调用权：命令表唯一门禁，判据承担强制力

规则（ADR-0027 决策二）：AGENTS.md 显式命令表是用户门禁的唯一所在，表内命令的技能把门禁写成正向判据步骤——"流程到达该段时：出示命令名并停止，等用户键入"；全部 duo 技能 frontmatter **不写** `disable-model-invocation`（ZCode 解析器白名单五键不含它，写了无隔离效果、反而击穿 safeToAutoLoad 展示语义）；流程关键门（定级、验收、收口、复盘）的强制力由完成判据承担——跳步在收口核对与复盘处可检出。

> 正例（duo-workflow 的提交前核对清单节）：动 git 前的三步核对写成可执行的判据序列（验收件就绪 / 版本上下文 / 分支归属），每步可核对。
>
> 反例（duo-workflow 改写前的 :16，快照见对比报告 §2.2）："设计访谈段模型不可自动触发，提示用户显式调用：/grill-me"——门禁语义放在正文散文里，模型读到时无结构性强制力。

### 1.3 跨技能引用：显式调用，点名路径

规则：让 agent 此刻去跑另一个技能，一律写显式调用指令——`Call the Skill tool with "duo-acceptance"`；引用规范、配置等本体文件，点名文件与节——"读 `docs/agents/issue-tracker.md` 的模板节并按其执行"；"用法以该技能为准"与 `../../../` 深层相对链接都属弱指针（目标材料不在上下文，等于凭记忆执行），改写为上述两种形态之一。（全库暂无正例——对比报告矩阵 M2 为 ✗ 项，改写组 05–11 落地后回填。）

> 反例（duo-code-review 改写前的 :15，快照见对比报告 §2.13）："调用 mattpocock `code-review` 技能的 Standards 子代理，用法以该技能为准"——弱指针全库最大实证，其自身变更历史（现迁 experience.md）记录了后果："描述性条款、无机械校验点，跨会话后必然衰减"。同型反例：duo-tracker/SKILL.md:10–11 的三级外链。

### 1.4 路由表同步

规则：根 AGENTS.md 路由表与各技能 description 是同一路由的两个视图，增删触发分支同一 diff 改两处；description 改写单独成 commit，保证触发行为整体可回滚。

> 正例（duo-workflow/SKILL.md:62）："路由同步：根 AGENTS.md 的路由表与各技能 description 是同一路由的两个视图——增删触发分支必须同一 diff 改两处。"——本条即由此升格为全库规范。

### 1.5 frontmatter 纪律

规则：frontmatter 只写 `name` 与 `description` 两键；description 含半角冒号、引号或长句时用 YAML 引号或 `|` 块标量包裹，保证可解析——frontmatter 非法等于技能对 discovery 静默消失。

> 正例（duo-release-workflow/SKILL.md:3–8）：多行 description 用 `|` 块标量合法折行。
>
> 反例形态（当前 15 个技能实测无此雷，属未踩雷而非有防线）：未加引号的 `description: XX: YY` 会被 YAML 解析为映射嵌套，解析失败即技能不出现。

## 支柱二：完成判据与证据先行

### 2.1 每步带完成判据

规则：每个步骤、每条流程链节点以"完成判据："收尾，写**可判定**的条件（能区分 done 与 not-done），并带**工作量要求**（"每张工单含三要素"逼出彻底劳动，"整理工单"不能）。箭头链流程图必须逐节点展开为带判据的步骤。

> 正例（duo-acceptance/SKILL.md:18）：`完成判据：命令在干净检出上复制粘贴即可执行成功`——三件套四步各带判据，全库范本。
>
> 正例（duo-project-structure/SKILL.md:32）："同一 diff 完成，缺一即拆分未做完"——工作量式判据。
>
> 反例（duo-workflow 改写前的 :14，快照见对比报告 §2.2）："流程：设计访谈 → spec/ADR → 拆工单 → 逐单实现 → 审查 → 验收 → 版本合并"——七节点零判据，每个节点何时算完成全凭临场裁量。

### 2.2 证据先行

规则：凡声称"已落盘 / 已运行 / 已同步"的完成，判据写成**出示证据**——落盘路径、命令与输出、grep 结果；形容词不承载判据，用字面示例锁定。

> 正例（duo-doc-standards/SKILL.md:50–56）：导航对账固化为两条命令 + 两数关系判定——"故固化为命令而非口头纪律"。
>
> 正例（duo-acceptance/SKILL.md:44）：`"详细"由示例锁定，不以形容词为准`——同一条款自带反例修复。
>
> 反例（duo-code-review 改写前的自诊断，快照见对比报告 §2.13）：跨会话衰减的根因即"凭记忆声称完成"——修复手段（"先 grep 实证再写"）已在其 experience.md，本条将其升格为全库判据写法。

### 2.3 状态行与状态机

规则：带生命周期的产物（工单、档案、研究条目）定义 Status 值域与迁移条件，迁移判据绑定证据；流程内的判定结果（定级、判粒度）同样落痕，可复查。

> 正例（duo-bug-ledger/SKILL.md:27）：档案模板 Status 行内置值域 `reported → investigating → fix-planned → fixing → verifying → done`；duo-acceptance/SKILL.md:40 把 done 定义绑定到用户确认。
>
> 反例（duo-workflow L1–L3 定级）：判级结果只在对话中口头出现，无落盘位置——复查时无法回答"当时为什么判 L2"。

### 2.4 子代理 brief 填空

规则：派子代理的技能先写 brief 填空模板（基点 / 文件名单来源 / 规则清单来源 / 范围口径 / 输出与词限 / 固定指令），派发前逐项填写，禁止即兴手写；子代理无法访问主上下文，brief 携带它需要的全部材料原文。

> 正例（duo-code-review 的 brief 填空模板节）：六要素逐项填写，brief 从轴定义机械派生（M24 工单 09 事故的防复发，出处见该技能 experience.md 变更历史节）。
>
> 反例（duo-code-review 改写前的变更历史，现迁 experience.md）：工单 09 事故根因即"brief 为即兴手写自由文本，未从轴定义机械派生"——名单手挑、规则手写、范围模糊。

## 支柱三：检查点阻塞化

规则：交用户决策的动作是**独立步骤**，带 Wait 语义（"出示清单，等用户答复；未获答复不进入下一步"），检查点前置推荐答案让用户一词可答；不该阻塞的检查点（AFK 场景、用户不在场）**显式声明不阻塞**并给理由；决策归属分清——事实自查、决策问人。检查点埋进括号或子项等于不存在。

> 正例（duo-acceptance/SKILL.md:28）："给出命令与对照表，等结果。用户实测现象优先于任何测试绿灯"——阻塞 + 证据优先双语义。
>
> 反例（duo-comprehension/SKILL.md:14）："课程清单先给用户过目确认（可增删），再开讲"——检查点嵌在第一步第 3 子项的括号里，长上下文中被跳过的概率显著高于独立步骤。

## 支柱四：领先词与词汇一致

### 4.1 领先词

规则：用预训练已有的紧凑概念做**领先词**（三件套、最窄测试、收口、硬闸门），一词锚定一类行为；同一概念全库一个词，不换同义说法；弱词压不住默认行为时换更强的词（"详细"→"字面示例"），不堆修饰。

> 正例（duo-acceptance 三件套、duo-pre-push-checks 最窄测试）：一词在多技能间稳定复用，读到词即激活整套行为。
>
> 反例（duo-acceptance/SKILL.md:44 记录的坑）：曾用形容词"详细"承载判据——弱词是 no-op，修复即改用字面示例锁定。

### 4.2 词汇一致

规则：SKILL.md 与 AGENTS.md 的用词受术语表约束——首选词 + _Avoid_ 清单；新概念词条随实现的同一 diff 落术语表（技能写作词条见术语表「技能写作域」）。

> 正例（本规范同 diff 的术语表「技能写作域」）：工单、收口等 8 词条各带首选与 _Avoid_——词条落表即约束生效。
>
> 反例：工单 / ticket / issue 三词曾在 duo-tracker（配置文件名 issue-tracker.md、表格"补状态"）、duo-workflow（"拆工单"）、duo-code-review（"工单审查报告"）间混用——触发匹配与跨技能协作被同义词分散（对比报告 M9 行）。

## 支柱五：否定收敛与剪枝

### 5.1 否定收敛

规则：指令写成正向动作序列（现在做什么），默认不出现禁令；每技能硬护栏至多一条（真正无法正向表述的红线），且紧跟正向目标；"反模式（不要做）"节改写为"每步完成判据"节。

> 正例（duo-trim-cot-leakage/SKILL.md:39–49）："不是泄漏的（保留规则）"整节正向列举什么保留、按字面执行——同一约束的反向形态（"不要误删"）从未出现。
>
> 反例（duo-bug-ledger/SKILL.md:82–87）："反模式（不要做）"四条禁令；duo-code-review 改写前的豁免条款三重否定（快照见对比报告 §2.13："现场裁量豁免无效，沿袭先前工单的豁免同样无效"）——全库认知负荷最高的单句，改写方向："出示两处记档路径与用户确认记录，缺一即未豁免"。

### 5.2 单一事实源

规则：一个含义只在一处权威存在；规则的本体在它的家（AGENTS.md、配置文件、上游技能），技能正文引用不复制；同一分工说明不留两份。

> 正例（duo-release-workflow/SKILL.md:115）："红线的唯一权威是根 AGENTS.md——本流程不抄录副本，与红线相抵触即停"；duo-tracker/SKILL.md:25："改内容直接改文件本身，不在任何 skill 里留副本"。
>
> 反例（duo-bug-ledger）：与 diagnosing-bugs 的分工说明在 description（:3）与正文（:12）两处重复。

### 5.3 环境即真相源

规则：环境能查到的（package.json、目录布局、命令 help、CHANGELOG 版本段）不在技能里复述；只记录环境查不到的——未成文惯例、决策理由、踩过的坑。

> 正例（.duo/skills/release-notes/SKILL.md:9）："发布说明的唯一事实来源是 CHANGELOG.md 的对应版本段"。
>
> 反例（duo-skill-evolution/SKILL.md:24–25）：复述 AGENTS.md 红线 8 与 Stop hook 机制全文——全局规则的家在 AGENTS.md，技能里一句"触发与兜底见根 AGENTS.md 红线 8"即够。

### 5.4 no-op 猎杀

规则：逐句问"这行删掉后行为会变吗"——不会变即是 no-op，整句删除；约束模型默认已遵守行为的句子是典型 no-op；对领先词同样适用，弱词换强词而非加修饰。（全库现存正例待改写组落地回填；本条款的反例即其正向改写样例。）

> 反例（duo-skill-evolution/SKILL.md:289–291）："不要过度进化 / 不要过度文档化 / 不要过度修订"三连——约束的正是默认行为，正向改写为一句："进化以'下次少犯一个已记录的错误'为唯一收益标准"。

### 5.5 体量与沉积治理

规则：**变更历史的家是该技能 references/experience.md**，SKILL.md 零历史节；示例、长参照、检索模式外置 `references/`（渐进式披露）；模板与正文写具体文件路径与代码片段的位置改写为概念表述（它们腐烂最快），决策密集片段（状态机、schema、类型形状）例外，注明来源并裁剪到只剩决策；正文重复出现的段落（示例复述规则、换皮重讲）删除。

> 正例（duo-java-review/SKILL.md:24–51）：L0 入口 / L1 按模块规则文件 / L2 输出时辅助文件的三层披露——全库最完整的层级实现；duo-trim-cot-leakage 的示例与检索模式集外置 references。
>
> 反例（duo-code-review 改写前 :71–110 的六段变更历史约 40 行，现迁 experience.md；duo-skill-evolution 全文 328 行，两个完整使用示例 :230–281 与正文规则大面积换皮重复）：沉积在正文的陈旧层。

## 失败路径 fail-fast

规则：坏输入（坏基点、空 diff、缺配置）在派发与深挖**之前**失败并报错；前置缺失时给用户指令（"请先运行 /setup…"），不自己绕过；造不出证据就停在环上，列出已试路径与所需补充；不知道就声明不知道并问；依赖未决事项的步骤显式推后。

> 正例（duo-research/SKILL.md:32）："git pull --ff-only 失败时报告原因，不擅自 rebase/merge"；duo-release-workflow/SKILL.md:12 引导态守卫："仓库或构建体系尚未建立时，不硬套流程——先与用户确认初始化方案"；duo-pre-push-checks/SKILL.md:62："停下来修复或说明阻塞原因，不要'先推了赌 CI 不一样'"。
>
> 反例（duo-workflow 三级分流）：三级判定均无"判定不了级怎么办"的兜底步——L1/L2 边界争议时无出路（对比报告 M10 行）。

## 保留资产（新写与改写不得丢失）

以下机制是 duo 体系的差异化资产，改写时逐项对照本清单验收：experience.md 经验回流与红线 8 复盘；豁免治理（双处记档 + 用户显式确认 + 每次独立决定）；brief 填空模板；表格化分支；duo-java-review 的 L0/L1/L2 渐进披露；判例节（duo-project-structure）。

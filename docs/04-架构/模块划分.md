# 模块划分

> 状态：门面建设中。`duo-harness-core` 的最小插件闭环已可用（编程 API）；`duo-harness-tools`、`duo-harness-example` 尚未创建（M1 工单 06/07）。

## 三模块与依赖方向

| 模块 | 角色 | 依赖 |
|---|---|---|
| `duo-harness-core` | 容器内核：插件加载、config 绑定、可逆副作用、服务注入、事件分派、依赖驱动生命周期、配置驱动 boot | Jackson（databind + dataformat-yaml）、SLF4J api |
| `duo-harness-tools` | 工具域骨架：ToolDefinition 注册 + 三段执行管线（pre-execute 准入 / execute 本体 / post-execute 结果治理），以 "tools" 服务发布 | core |
| `duo-harness-example`（规划） | 示例插件与 boot 入口 Demo | core + tools |

依赖方向单向：core ← tools ← example，功能模块之间不互相依赖。版本由根 pom 的 dependencyManagement 统一管理，子模块不写版本号。

## core 的包边界

- `dev.duo.harness.core.api`——内核对插件作者的全部契约：`Plugin`（apply 入口 + config 类型声明）、`Context`（plugin 挂载 / effect 注册 / dispose）、`PluginHandle`（实例句柄）、`Disposable`、异常类型。接口静态工厂 `Context.root()` 创建根作用域。
- `dev.duo.harness.core.internal`——实现（`DefaultContext` 等），不对外暴露；包名即"勿用"契约。

## 关键语义

> 状态更新：core 全量落地（工单 01-05）；tools 骨架落地（工单 06）；example 待工单 07。

- **同步加载**：`Context.plugin()` 阻塞至 apply 返回；失败同步抛出且不留残留副作用（ADR-0002 的同步模型在 M1 的体现）。
- **逆序回滚**：作用域销毁按注册逆序执行全部副作用；子插件实例的销毁是其父作用域的普通副作用，级联自然发生。
- **config 绑定**：原始配置（Map / JsonNode）经 Jackson 绑定到插件声明的 config record，失败抛 `PluginConfigException`（点名插件与字段路径）——错误前移到加载时刻。严格模式：record 的全部组件必须显式提供，缺字段即绑定失败（引用类型不会静默补 null）。
- **事件分派五模式**：emit（广播，监听器异常隔离并记 warn）、parallel（每监听器一虚拟线程，失败聚合为主异常 + suppressed）、serial / bail（顺序投票，首个非 null 返回值为终值并终止链；同步模型下两者等价，bail 保留 DSH 词汇）、waterfall（洋葱管线：监听器收 `(args, next)`，可改写参数、包装返回值、不调 next 即否决内层与终端）。监听器表挂在根作用域全树共享——任意作用域注册、任意作用域派发可见；注册即所在作用域的副作用，插件停止自动摘除。
- **服务注入**：`ctx.provide(name, instance)` 发布具名服务（同名冲突点名报错，先注册方保留）；`ctx.as(视图接口)` 返回动态代理，方法名即服务名、调用时惰性解析（服务替换后无需重新取视图）。注册表键为（服务名, 作用域）二阶结构，当前仅默认作用域（isolate 预留）。插件用 `Plugin.inject()` 声明依赖：未声明读取被点名拒绝（错误前移）、依赖缺失时插件挂起（PENDING）不跑 apply、`awaitStartup()` 阻塞至激活或失败；服务注销（或提供方插件停止）自动停止依赖它的活跃插件——级联传导。
- **依赖驱动生命周期（六态 + epoch）**：插件实例在 PENDING（等依赖）→ LOADING → ACTIVE / FAILED 之间迁移，依赖消失进 UNLOADING 后**回 PENDING**（服务回归自动重启）、dispose 进 DISPOSED 终态。epoch = 依赖服务实例集合的指纹——变化（消失/回归/换实现）驱动实例复查迁移，"换实现自动重启"与"注销竞态误停化解为多余重启、最终一致"均由此实现。状态迁移经 `plugin/status` 事件广播（供 Demo 与状态页），`PluginHandle.state()` 提供六态快照。启动失败不再阻断 `plugin()` 调用：错误统一经 handle（`awaitStartup()` 重抛 / state=FAILED），同步与异步唤醒路径语义一致。
- **配置驱动 boot**：`Boot.from(yml)` 读单文件配置（行结构：`id`（必填，审计点名锚点）/ `name`（插件类 FQCN，公共无参构造）/ `config` / `disabled`），逐行经编程 API 装载——行序无加载语义（依赖驱动保证）。收尾审计点名：FAILED 行带原始错误、PENDING 行列缺失服务清单、类不可加载点名；任何失败整树回滚后抛 `BootException`（阶段标签：读配置 / 解析 / 激活）。`disabled: true` 行保留在配置中但不加载实例。一次性引导：改配置重启生效，运行时热重载（HMR）不在范围。`Context.hasService(name)` 提供存在性查询（不返回实例，不构成 inject 纪律的绕行）。
- **工具域三段管线**：`ToolsPlugin` 挂树即发布 "tools" 服务（`ToolsService`：`register(registrant, def)` 注册即注册方作用域的副作用——插件停止自动注销；`execute(name, args)` 走三段 waterfall，载荷 `ToolExecution` 贯穿全程）。三段：`tools/pre-execute`（准入：监听器 `deny(reason)` 不调 next 即否决，默认放行）→ `tools/execute`（around 本体：终端即工具 execute，超时/重试类包装挂此段）→ `tools/post-execute`（结果治理：可改写结果或转错误形态）。工具异常收敛为 error 结果不上抛（错误是治理结果不是系统故障）；未知工具点名抛 `ToolNotFoundException`。

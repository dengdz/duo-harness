# 技能编写指南

> 状态：对齐 0.25.0（教程体裁，机制锚点经源码核实）。读者定位：**不翻源码就能写出合规技能的插件开发者**。写作标准本体是[技能写作规范](../05-参考/技能写作规范.md)——规范是标准，本章是操作路径与机制侧补齐，互链不照搬；术语以[术语表](../05-参考/术语表.md)技能域与「技能写作域」词条为准。写作规范的决策依据见 [ADR-0027](../adr/0027-技能写作规范移植与调用权分流.md)（移植五支柱与调用权分流兜底），热加载的决策依据见 [ADR-0025](../adr/0025-M23执行与CLI体验三裁定.md)（M23 工单 09）。本章全部机制描述（四发现根顺序、frontmatter 解析、2s/200ms 窗口、digest 去重等）均对照 `duo-harness-agent` 模块的 `SkillRegistry` / `SkillTool` / `SkillsPlugin` / `CommandsRegistry` 源码逐一核实；源码与旧表述不一致处以源码为准。

技能是 duo-harness 里门槛最低的扩展形态：**不写一行 Java、不动一行装配，放对一个文件就生效**。本章沿「是什么 → 放在哪 → 怎么写 → 怎么被用 → 怎么改怎么生效」五步走完全链路。

## 1.1 技能是什么

技能（Skill）是一个 SKILL.md 定义的**模型可加载指令包**，两个构件：

- **frontmatter**（可选）：`---` 包裹的 YAML 头，解析器只认 `name` / `description` 两键；
- **指令正文**：frontmatter 之后的全部内容——**正文即指令全文**，模型加载后严格遵循执行。

它不是代码插件。插件是 Java 类，随 yml 装配行走生命周期；技能是纯文本，落进发现根即被扫描——两者的扩展点与生命周期机制完全不同（插件侧见[插件配置参考](../05-参考/插件配置参考.md)与[插件扩展点清单](../05-参考/插件扩展点清单.md)）。

### 全链一句话：发现 → 名录进系统提示 → 按名加载全文

把这句话拆开，是三段各司其职的机制：

1. **发现**：启动时 `SkillsPlugin` 按四个发现根（见 1.2）扫描，解析出全部合法技能，发布为 "skills" 服务。
2. **名录进系统提示**：`SkillsPlugin` 把技能清单聚合成一行一技能的 prompt 片段（格式固定：「可用技能（需要时用 skill 工具按名加载指令后遵循执行）：」+ 每技能一行 `- 名字：description`），注册进 prompt 注册表，每轮请求随 system 提示注入。**常驻上下文的只有这一行 description**。
3. **按名加载全文**：模型判断当前任务匹配某个技能的 description 时，调用 `skill` 工具（入参只有技能名），该技能的正文以工具结果进上下文；用户也可以直接敲 `/技能名` 直调（见 1.4）。

名录与正文分离是技能的上下文经济学：你可以拥有几十个技能，每个只在名录里花一行；几十上百行的正文只有真正用到的那个才进上下文。这也是 description 值得逐字抠的原因——**它是技能唯一的常驻门面，模型能不能在对的时机想起它，全看这一行**（怎么写见 1.3 支柱一）。

全链一图（各环节的机制在 1.2 / 1.4 / 1.5 展开）：

```
四个发现根 ──启动扫描──▶ SkillRegistry（"skills" 服务）
                             │
                             ├─ 名录片段（一行一技能）──▶ prompt 注册表 ──每轮组装──▶ system 提示
                             │                                            │
                             │                              模型判断任务匹配 description
                             │                                            │
                             └─ skill 工具 ◀────────按名调用（name）────────┘
                             │
                             └─ 正文以工具结果进上下文，模型遵循执行
```

### 与相邻机制的边界

写作前分清四个「给模型注入指令」的相邻机制，避免放错层：

| 机制 | 是什么 | 何时选它 |
|---|---|---|
| **技能** | 按名加载的指令包，名录常驻、正文按需，进模型历史 | 可复用的任务流程与规范（本章主题） |
| **斜杠命令** | 插件代码注册的 harness 操作，不进模型历史 | 操作 harness 本身（`/new`、`/permission`、`/compact`） |
| **AGENTS.md 链** | 每轮现发现现读的约定注入（64KB 预算），最前 meta_user 通道 | 全局/项目级约定与路由表（技能的家不在 AGENTS.md 正文，路由行才在） |
| **prompt 片段** | 插件经 prompt 注册表贡献的常驻提示 | 面向所有任务的全局指令（技能名录本身就是一段片段） |

### 拿什么讲：16 个 duo-\* 技能就是活体

`.agents/skills/` 下的 16 个 duo-\* 技能（duo-workflow、duo-acceptance、duo-code-review、duo-bug-ledger、duo-doc-standards、duo-java-review、duo-pre-push-checks、duo-project-structure、duo-prose-standard、duo-release-workflow、duo-research、duo-skill-evolution、duo-skill-lint、duo-tracker、duo-trim-cot-leakage、duo-comprehension）全部是目录包形态，典型结构：

```
.agents/skills/duo-workflow/
├── SKILL.md                    # 入口：frontmatter + 指令正文（约 72 行）
└── references/
    └── experience.md           # 经验沉淀：变更历史、踩过的坑（红线 8 复盘的家）
```

- 16 个中 15 个带 `references/experience.md`。根 AGENTS.md 红线 8 是这套形态的运行纪律：执行任何 duo- 技能前先读它的 experience.md；技能收尾经 duo-skill-evolution 复盘，进化点回流 experience.md——**SKILL.md 只放稳定指令，经验沉淀不进正文**（这也是[技能写作规范](../05-参考/技能写作规范.md) 5.5 节「变更历史的家」条款的活体）。
- 孤例是 duo-java-review：规则文件外置于 `reference/` 目录（阿里规范分模块规则文件，L0/L1/L2 渐进式披露形态），且没有 experience.md。**新技能请按 15 个多数派的 `references/`（复数）惯例放**，别抄这个孤例的目录名。
- 更小的入门范本是 demo 技能 `.duo/skills/release-notes/`（发现根 1 上的项目私有技能），正文只有四条规则，五分钟读完。
- 各技能的触发路由（「你说什么 → 走哪个技能」）见根 AGENTS.md 路由表——它与各技能 description 是同一路由的两个视图（同步纪律见 1.3 收尾自检）。

### 与子代理技能名录的边界（如实记现状）

[ADR-0017](../adr/0017-子代理知识可见性模板opt-in.md) 已裁定：子代理模板可经 `withSkills` / `withAgentsMd` 两个可选布尔字段 opt-in 携带技能名录与 AGENTS.md，缺省 `false`。**但该裁定尚未实现**——当前子代理的 system 只含框架基线与模板专属提示，不含技能名录（[已知限制](../limitations.md) M15#4 挂账，实现归后续里程碑）。落到写作上的含义：今天凡是打算派给子代理执行的材料（项目约定、规范条文），必须由父 agent 放进任务描述原文——技能名录此刻帮不上子代理。

延伸阅读：`skill` 工具的模型可见面见[工具目录 §skill](../05-参考/工具目录.md)；运行任一 REPL 即可观察两条加载路的效果（启动见[快速开始](../01-入门/快速开始.md)）。

## 1.2 放在哪：发现根与优先级

技能放对地方才会被发现。发现根（Discovery Root）按优先级降序共四个，`SkillRegistry.defaultRoots` 写死此序：

| 序 | 发现根 | 归属 | 典型用途 |
|---|---|---|---|
| 1 | `<项目根>/.duo/skills` | 项目 | 项目私有技能、demo 技能（release-notes 在此） |
| 2 | `<项目根>/.agents/skills` | 项目 | 行业标准位置——duo 全部 16 个 duo-\* 技能在此 |
| 3 | `~/.duo/skills` | 用户 | 个人跨项目技能 |
| 4 | `~/.agents/skills` | 用户 | 行业标准位置的个人技能 |

扫描规则逐条（每条都是 `SkillRegistry.scan` 的实现语义，不是愿望）：

- **项目根以 `.git` 向上定位**：从当前工作目录逐级向上找第一个含 `.git` 的目录；一路到文件系统顶都没找到，项目根即 cwd 本身。技能发现与 AGENTS.md 注入共用这个定位逻辑，两边的「项目根」永远一致。
- **同名先到先得**：四根按序扫描，先扫到的同名技能注册后，后面根的同名条目整条跳过（不看内容）。注意同名判定与禁用表都按**技能名**（frontmatter 的 `name`，缺省目录名/文件名主干）——文件叫 `a.md`、frontmatter 写 `name: b`，注册名就是 `b`。场景演示：

  ```
  <项目>/.duo/skills/release-notes/     ← 根 1：仓库内置 demo
  ~/.duo/skills/release-notes/          ← 根 3：你照着 demo 改的个人版
  ```

  扫描从根 1 开始，`release-notes` 在根 1 命中注册，根 3 的个人版**整条跳过**——先到先得按的是根序，不是创建时间。两个推论：想覆盖用户级技能，在项目根放同名即可；反过来，**项目根技能无法被用户级同名覆盖**（项目永远先扫）——想临时换掉 demo 技能，直接改根 1 的文件，或进禁用表后再建自己的版本。
- **禁用表整名跳过**：装配行的 `config.disabled` 命中者整名跳过，哪个根都不加载：

  ```yaml
  # agent-demo.yml 节选（真实装配）
  - id: skills
    name: dev.duo.harness.agent.skills.SkillsPlugin
    config:
      disabled: []          # 禁用的技能名列表，如 ["release-notes"]
  ```

- **对环境宽容**：目录不存在静默跳过（四根不必都存在）；条目非法（目录缺 SKILL.md、正文空白、YAML 解析失败）静默跳过。宽容是刻意的——技能是环境数据，缺一个不该炸整个装配。对比：插件代码注册同名命令是装配期 fail-fast（`CommandsRegistry` 点名报错），环境数据与代码装配是两套哲学。
- **双形态**：目录包 `<名>/SKILL.md` 与单文件 `<名>.md` 都合法，加载语义完全一致（`SkillRegistryTest` 两种形态各自锁定）。真实实例对照：

  | | 目录包（16 个 duo-\* 全是此形态） | 单文件 |
  |---|---|---|
  | 真实实例 | `.duo/skills/release-notes/` | 本仓库无活体（测试锁定语义） |
  | 名缺省取 | 目录名 `release-notes` | 文件名主干 |
  | 可携带参考文件 | 可以（`references/` 与正文同包） | 不能——要外置材料就得用目录包 |
  | 适合 | 有 frontmatter、有 references 的正式技能 | 一发入魂的小技能 |

  单文件形态长这样（frontmatter 可省）：

  ```markdown
  <!-- ~/.duo/skills/tone.md —— 名取主干 tone，整文即指令正文 -->
  回复用户时用中文，语气克制专业，不堆形容词。
  ```

  选型口诀：**只要有 `references/` 外置材料或正式 frontmatter 的打算，直接用目录包**——单文件后续升级为目录包要挪文件、改发现路径，一步到位更省事。

- **确定性**：同一根内条目按文件名排序后依次扫描，加载结果与文件系统返回顺序无关，同名竞争的胜者可预期。

怎么选根：**项目约定、流程类技能放项目 `.agents/skills`**（随仓库走，团队共享）；**项目私有、不想提交的放项目 `.duo/skills`**（优先级更高，可覆盖同名）；**个人惯用、跨项目的放 `~/.duo/skills` 或 `~/.agents/skills`**。想做「临时替身」实验，在更高优先级的根放同名技能即可，不必动原技能（根 1 已是最优先——替身它只能直接改它或禁用它，见上）。

运行验证不翻源码：启动 REPL（见[快速开始](../01-入门/快速开始.md)）后问模型「你能看到哪些技能」——名录即扫描结果；往任一发现根放一个最小技能，最迟约一个心跳窗口（见 1.5）后它就出现在名录里。术语与优先级语义的权威表述见[术语表「发现根」词条](../05-参考/术语表.md)。

## 1.3 怎么写：SKILL.md 解析与五支柱教程化

### 解析器认什么：先知道边界，再动笔

`SkillRegistry.parseMarkdown` 的四条契约：

1. **frontmatter 可选**：文件以 `---` 开头且能找到闭合 `---` 才按 frontmatter 解析；没有 frontmatter 时整文即正文，名取主干。闭合 `---` 缺失不报错——整文（含开头那行 `---`）按正文处理，名回落主干。
2. **只认 `name` / `description` 两键**：其他键一律忽略（不报错、不进任何面）。`name` 缺省取目录名/文件名主干；`description` 缺省为空串——名录里该技能只列名字、不带冒号说明。
3. **空白正文非法**：正文 strip 后为空（纯空白文件）的条目跳过；名字 strip 后为空同样跳过。
4. **YAML 解析失败即静默消失**：frontmatter 语法非法（最常见：description 含半角冒号又没加引号，被 YAML 读成嵌套映射）→ 该条目不加载、不报错。**「改了 description 技能就没了」的唯一机制成因在此**。

写作时的前置自查就一句：写完先确认技能还出现在名录里（问模型或看装配状态面），再谈写得好不好。

最小可解析骨架（形态示例，标明判据写法；每节的真实范本见下文）：

```markdown
---
name: my-skill
description: 收口（wrap-up）：流程末段的完成核对。触发：收尾 / 阶段结束 / 要总结。
---

# my-skill：一句话标题

第一步：<祈使句，每条路径都要走的动作>。
- 完成判据：<可判定 done 与 not-done 的条件，强形态出示证据>。

第二步：<涉及用户决策的动作独立成步>。
- 出示 <清单/证据>，等用户答复；未获答复不进入下一步。
```

真实 frontmatter 长什么样——duo-workflow 逐字摘录：

```markdown
---
name: duo-workflow
description: 开发总入口：三级分流（L1 大需求/L2 功能 bug/L3 微调）与各级收口（wrap-up）判据。触发：加功能、修 bug、实现效果、调整页面、微调。
---
```

这条 description 实测 77 字，在模型触发档 ≤80 字预算内；首词「开发总入口」即技能本体，尾部「触发：」独立成句——三规则的达标形态（逐规则见下）。

### 五支柱逐一「怎么做到」

以下每条都给操作路径；条款全文与正反例池在[技能写作规范](../05-参考/技能写作规范.md)，不在此照搬。

#### 支柱一：description 三规则怎么落

description 是常驻上下文，每一回合都在花预算。落笔四步：

1. **首词放领先词**，中英并列锚点（如「收口（wrap-up）」「三级分流」）——首词即技能本体，模型扫名录按它定位。
2. **删身份句**——「本技能用于……」类句子不要，正文 H1 已携带身份。
3. **触发按概念收敛**、独立成句放尾部——写「触发：加功能、修 bug」，不罗列口语变体（「帮我加个」「改一下」是词面不是概念，罗列只会烧预算且盖不全）。
4. **字数预算核对**：AGENTS.md 显式命令表内技能 ≤60 字、模型触发技能 ≤80 字，用 `wc -m` 量，不目测。

> **反例**（构造，新手最常见形态）：`description: 你是一个严谨的代码审查专家，擅长发现代码中的问题。`——身份句开场（正文 H1 才是身份的家）、无领先词、零触发概念，模型无从判断何时该想起它，白白花每一回合的预算。
>
> **正例**（duo-bug-ledger frontmatter 逐字摘录）：`bug 全生命周期建档留痕：报问题即建档，排查逐步落盘，归档进台账。触发：任何"现实与预期不符"的陈述、报错、验收失败，或 bug 修复提交前。`——首词即本体；触发按概念收敛，「任何"现实与预期不符"的陈述」一句话盖掉全部口语变体。真实历史反例形态见[规范 1.1 节](../05-参考/技能写作规范.md)（duo-bug-ledger 改写前约 220 字全库最长，快照见对比报告 §2.9）。

#### 支柱二：完成判据怎么立

每个步骤以「完成判据：」收尾，写**可判定**的条件——读的人（模型）能据此区分 done 与 not-done，并带**工作量要求**（「每张工单含三要素」逼出彻底劳动，「整理工单」不能）。强形态是**证据先行**：判据写成出示证据——落盘路径、命令与输出、grep 结果，形容词不承载判据。两条硬性转写：箭头链流程图（「访谈 → spec → 实现 → 验收」）必须逐节点展开为带判据的步骤——七节点零判据是规范点名的最大反例形态；审查/参考型技能的判据可为一句话总判据，判据密度按技能类型分档。

> **反例**（构造，新手常见）：`第三步：整理工单，确保所有内容都完善无误。`——「整理」「完善无误」全是形容词，done 与 not-done 无法区分，执行深度全凭临场裁量（规范 2.1 节的历史反例同型：duo-workflow 改写前七节点流程图零判据）。
>
> **正例**（duo-acceptance :20、duo-project-structure :32 逐字摘录）：`完成判据：命令在干净检出上复制粘贴即可执行成功`（可执行判据）；`同一 diff 完成，缺一即拆分未做完`（工作量式判据）。带生命周期产物再加一层：Status 值域与迁移条件绑定证据（duo-bug-ledger 档案模板的 `reported → … → done` 状态机，见规范 2.3 节）。

#### 支柱三：检查点怎么阻塞

交用户决策的动作写成**独立步骤**，带 Wait 语义。句式模板：「出示 X，等用户答复；未获答复不进入下一步」。两个加分动作：检查点**前置推荐答案**让用户一词可答；不该阻塞的场景（AFK、用户不在场）**显式声明不阻塞**并给理由——声明与沉默是两回事。决策归属分清：事实自查（读文件、grep）自己做，决策问人。

> **反例**（真实历史，规范点名）：duo-comprehension 改写前的「课程清单先给用户过目确认（可增删），再开讲」——用户确认嵌在第一步的括号里，长上下文中被跳过的概率显著高于独立步骤。
>
> **正例**（duo-acceptance :30 逐字摘录）：`给出命令与对照表，**等用户答复**——未获答复不进入收尾。用户实测现象优先于任何测试绿灯；发现问题回实现修复，不得以"测试是绿的"反驳（唯一硬护栏）。`——独立阻塞步骤 + 证据优先双语义 + 全篇唯一硬护栏，一处把支柱三和支柱五都示范了。

#### 支柱四：领先词怎么选

领先词是锚定一类行为的紧凑概念词。选词三问：

1. 预训练里已有这个概念吗？——有（三件套、收口、最窄测试）才当领先词，自造词要硬配英文锚点反而增加负荷。
2. 同一概念全库是否只用这一个词？——换同义说法就把触发匹配与跨技能协作打散。用词受[术语表「技能写作域」](../05-参考/术语表.md)约束：首选词 + _Avoid_ 清单，写「工单」不写 ticket，写「收口」不写「完成」。
3. 弱词压得住默认行为吗？——压不住换更强的词，不堆修饰。

> **反例**（真实教训，duo-acceptance 自记）：曾用形容词「详细」承载日志判据——弱词是 no-op，模型各自裁量什么叫详细；修复即换强词锁定。
>
> **正例**（同一文件修复后，duo-acceptance :44 逐字摘录）：`## 日志长什么样（字面示例）`——用「字面示例」一词锚定「贴真实输出，不以形容词描述」整类行为。跨技能复用见「三件套」（duo-acceptance）与「最窄测试」（duo-pre-push-checks description 逐字摘录：`按变更类型选最窄测试 / 编译 / 文档校验，全绿才推`）——一词在多技能间稳定复用，读到词即激活整套行为。

新概念词条随实现的同一 diff 落术语表——词条落表即约束生效。

#### 支柱五：否定收敛怎么措辞

指令写成**正向动作序列**（现在做什么），默认不出现禁令；硬护栏全篇至多一条（真正无法正向表述的红线），且紧跟正向目标；「反模式（不要做）」节改写为「每步完成判据」节。

> **反例**（构造，新手常见）：`不要在没读过文件的情况下编辑文件，不要跳过测试直接提交，也不要过度设计。`——三连禁令，其中「不要过度设计」约束的是默认行为（典型 no-op）。正向改写：`编辑前先 read 该文件（读前写闸门）；提交前出示全绿的测试输出`——禁令变动作序，每条可核对。
>
> **正例**（duo-trim-cot-leakage :39 逐字摘录）：`## 不是泄漏的（保留规则）`——整节正向列举什么保留、按字面执行，同一约束的反向形态（「不要误删」）全篇从未出现。

配套两条剪枝纪律：

- **no-op 猎杀**：逐句自问「这行删掉后行为会变吗」——不会变即是 no-op，整句删除；约束模型默认已遵守行为的句子是典型 no-op。
- **单一事实源与环境即真相源**：一个含义只在一处权威存在，规则的本体在它的家（AGENTS.md、配置文件），技能正文引用不复制；环境能查到的（CHANGELOG、目录布局、命令 help）不进技能。真实正例：release-notes 的「发布说明的唯一事实来源是 CHANGELOG.md 的对应版本段」。

信息层级三级是支柱五的展开：步骤内联（每条路径都要走）→ 文内参考（表格、判例）→ 外置 `references/`（只在部分分支触达，指针后加载）。层级安排的术语是**渐进式披露**。两条沉积治理：**变更历史的家是该技能 `references/experience.md`，SKILL.md 零历史节**；跨技能 operative 引用写显式调用——`Call the Skill tool with "duo-acceptance"`，引用规范本体写「读 `<路径>` 的 `<节>` 并按其执行」，禁用「用法以该技能为准」类弱指针。

### frontmatter 纪律与调用权

- description 含半角冒号、引号或长句时，用 YAML 引号或 `|` 块标量包裹——真实正例是 duo-release-workflow 的多行 description（块标量合法折行）。frontmatter 非法 = 技能对发现静默消失（本节开头的契约 4）。
- **duo 技能 frontmatter 只写两键，不写 `disable-model-invocation`**——[ADR-0027](../adr/0027-技能写作规范移植与调用权分流.md) 探测记档：该键不在解析白名单，写了没有隔离效果、反而击穿展示语义。「哪些技能不许模型自动触发」的门禁方案见 1.4。

### 收尾自检（清单只引不抄）

- 机械核对走 [duo-skill-lint](../../.agents/skills/duo-skill-lint/SKILL.md) 的 **11 项核对清单**——frontmatter 两键、description 字数与三规则、路由对账、否定性保证清单、完成判据、显式调用、引用断链、数量词重数、词汇 Avoid、检查点阻塞、末尾换行。**新技能入 AGENTS.md 路由表之前全项通过——路由表是入口，先整改后接入**。
- 机制覆盖自查对[规范附录的 15 机制覆盖表](../05-参考/技能写作规范.md)：你用到的机制主题（调用权分流、完成判据、用户检查点、领先词、剪枝纪律、状态机……）是否都有条款承载。
- **路由同步**：根 AGENTS.md 路由表与各技能 description 是同一路由的两个视图，增删触发分支**同一 diff 改两处**（红线 3）；description 改写单独成 commit，触发行为整体可回滚。

## 1.4 怎么被用：两条加载路与治理语义

### 模型侧：`skill` 工具

模型看到的工具面（[工具目录 §skill](../05-参考/工具目录.md)）：入参**只有 `name` 一个必填串**，参数 schema 逐字摘录：

```json
{"type":"object","properties":{
  "name":{"type":"string","description":"要加载的技能名（见系统提示中的可用技能清单）"}},
 "required":["name"]}
```

调用后该技能的指令全文以**工具结果**进上下文，尾注固定一句「（请遵循以上技能指令完成用户任务。）」——工具本体就是一次注册表按名查询加文件内容返回，无副作用。第一推动力是 1.1 说的名录：模型「知道有哪些技能可用」完全来自 system 提示里那几行 description。

未知名不猜：报错点名可用技能（`未知技能: X（可用: a, b, c）`），模型据此自纠换名重试——写错名的代价是一轮重试，不是静默失败。

### 用户侧：`/技能名` 直调

用户敲 `/技能名`（可携带输入，如 demo 里的 `/release-notes 0.3.0`）走呈现位共享分发入口（`CommandsRegistry.dispatch`），顺序固定三级：**命令注册表 → 技能直调 → 未知命令报错附可用清单**。前两级语义不同：

- 命中**命令注册表**：命令在呈现位进程内同步执行，不进模型历史（落 `command/run` / `command/done` 审计事件）——命令是「操作 harness」（`/new`、`/permission`）。
- 命中**技能**：该技能正文注入本轮（携带的输入拼在「用户输入：」之后），模型直接按技能行事——技能是「替用户说话」，照常进模型历史。两张表平行维护，语义分界就是进不进历史（[ADR-0020](../adr/0020-斜杠命令与运行中治理.md)）。
- 两级都未命中：报未知命令，附可用命令清单与可用技能清单——与模型侧未知名同款自纠设计。

呈现位差异：这条分发入口（命令注册表 → 技能直调 → 未知报错）是 CLI 与 Web **共享的同一份代码序**（`CommandsRegistry.dispatch` 单入口），`/技能名` 在终端 REPL 与 Web 输入框行为一致——命中即注入进模型历史，模型按技能行事；差异只在呈现形态（终端回显注入 / Web 以输入框消息进历史）。命令适用面标记（ANY/CLI/WEB）只作用于命令注册表那一级，技能直调不受适用面限制。

### 门禁：显式命令表是唯一所在

「哪些技能不许模型自动触发」在 duo 没有字段开关（ADR-0027 探测记档：调用权杠杆在解析器侧缺位，写了也不生效），分流按语义兜底——**根 AGENTS.md 显式命令表是用户门禁的唯一所在**。当前表内六命令（`/grill-me`、`/grill-with-docs`、`/to-spec`、`/to-tickets`、`/implement`、`/handoff`）的强制力不写散文声明，而是写成**正向判据步骤**：「流程到达该段时：出示命令名并停止，等用户键入」——跳步由收口核对与复盘检出（「结构不可能」在 duo 降级为「判据可检出」，这是 ADR-0027 明示的兜底形态与残余风险）。给流程类技能写门禁时照此形态。

### 审批语义：缺省放行，不豁免管线

`skill` 工具未覆写 `requiresApproval`，接口缺省 `false`——**加载技能不弹审批卡**。但缺省放行不等于豁免：它走与所有工具同一条三段管线，其余治理段照常生效（[ADR-0012](../adr/0012-本机工具族与权限预设.md) 立的本机工具治理面）：

- **guard 单调否决**照常可用——guard 挂全局、时机在审批之后本体之前，返回理由即拒绝且无法翻回；
- **管线缺省超时**照常——`tools/execute` 段兜底超时（缺省 120s）对 skill 工具同样生效（本地文件读通常瞬间完成，超时是兜底不是常态）；
- **结果治理**照常——`tools/post-execute` 的改写/拦截监听器对工具结果生效；skill 工具未声明输出契约，按宽松透传处理。

「弹卡 / 不弹卡」对照（审批卡的唯一入口是 ask——工具声明 `requiresApproval=true` 或 pre-execute 监听器声明需审批）：

| 调用场景 | 弹审批卡？ | 依据 |
|---|---|---|
| `skill` 工具加载技能 | 不弹 | 工具缺省 `requiresApproval=false`，无人声明 ask |
| 越界 write / 任何 bash（非 danger 档） | 弹卡（终端 y/n 或 Web 卡片） | 工具声明需审批，按三档权限预设裁决（ADR-0012） |
| guard 拒到 `skill` 调用 | 不弹卡，直接拒绝并署名 guard | guard 是单调否决不是 ask——没有「待人答」的悬置态 |
| 声明需审批但审批策略缺位 | 不弹卡，按「未配置即拒」拒绝 | fail-closed——交互缺失永不等于默许 |

装配视角收个尾：技能面由 `skills` 装配行提供（1.2 的 yml 片段），它消费 `tools` 与 `prompts` 两个服务——把这一行注释掉重启，`skill` 工具与名录一起消失（[组装你的第一个 agent](../02-指南/组装你的第一个agent.md) 第三步的同款实验）。双呈现位（CLI 与 Web）共用同一 agent 域，两条加载路在两边行为一致。

## 1.5 怎么改怎么生效：热加载

M23 起技能支持热加载（M23 工单 09，[ADR-0025](../adr/0025-M23执行与CLI体验三裁定.md)；术语见[术语表「技能热加载」词条](../05-参考/术语表.md)）——**改 SKILL.md 不用重启进程**。`SkillsPlugin` 装配时经 `SkillRegistry.startWatch` 接线，一条平台守护线程跑 watch 循环（按 ADR-0002 对虚拟线程的保守隔离裁定，长生命周期阻塞任务用平台线程），机制四件事：

1. **watch 什么：四根及其父目录**。WatchService 注册每个发现根**与其父目录**——注册父级是为了捕捉根目录的首次创建（`.duo/skills` 尚不存在时，「建目录」这个事件被父级看见，根建好后根自身的注册接管根内条目）。watch 循环每轮结束补注册新出现的根；目录删除导致的失效 key 被从防重表摘除、目录重建后可重注册——不复位/不摘除就是「该根永久失聪」，这是实现里明确防的两个坑。
2. **窗口与去抖：2s 心跳 + 200ms 合并**。watch 轮询窗口 2 秒：事件到达即时处理；窗口内无事件的超时轮**同样触发重扫**——macOS 轮询式 WatchService 在多目录注册下实测会吞修改事件，心跳兜底保证修改感知。事件后等 200ms 去抖：编辑器保存常一次性产生多个文件事件，合并为一轮重扫。无变更的重扫快速短路，心跳轮零成本。
3. **变更怎么生效：digest 有变才重发、只重发一次**。重扫后技能内容有变（增删改）即整表替换并递增 revision（内容级变更计数，缓存失效信号）；**名录是否重发由清单片段的 sha256 digest 判定**——摘要有变才回调 `SkillsPlugin` 重发，且每轮至多一次（digest 未变不重发）。重发采用**先挂新片段再摘旧**的次序，刷新窗口期名录不缺失；技能全删同样清空名录，不留陈旧清单。落到使用体感：**新增技能文件、改正文、改 description 都不重启即生效，最迟延迟一个心跳窗口（约 2 秒）**。
4. **降级：watch 不可用就启动扫描 + 警告**。WatchService 创建失败时降级为启动扫描，日志警告「技能变更需重启生效」，不阻断技能发现——能力缺失是可观测的降级，不是故障。

一次热加载的完整时序（以「往 `<项目>/.duo/skills/` 新建 `my-skill/`」为例，数字均为源码常量）：

| 时刻 | 发生什么 |
|---|---|
| T+0 | 保存 `my-skill/SKILL.md`——根已在 watch 注册表，创建事件进队列 |
| T+0~ | watch 循环取出事件，睡 200ms 去抖——窗口内的后续事件（编辑器一次保存常写多个事件）合并 |
| T+0.2s | 排干积压并复位 watch key → `refreshFrom` 重扫：`my-skill` 入表、revision 递增；名录片段 sha256 digest 变化 → 回调 `SkillsPlugin` |
| T+0.2s | 先挂新名录片段、再摘旧片段（刷新窗口期名录不缺失）；本轮重发到此为止——digest 未变的后续轮不再重发 |
| T+0.2s 起 | 下一轮请求的 system 提示即含 `my-skill` 一行——名录已更新，模型按名可加载 |

全程不超过一个心跳窗口（2 秒）。若平台吞掉了创建事件（macOS 轮询式实现在多目录注册下会吞修改类事件），最迟下一个 2 秒超时轮的**无事件重扫**兜底——上限仍是一个心跳窗口，这正是「2s 心跳」存在的理由。

两个已知边界（如实记，勿绕过）：

- **`~/.agents` 整链新建不感知**：watch 注册父级的前提是父级目录已在场——用户主目录下 `.agents` 整条链都不存在时，首次新建整链根不触发热加载，重开会话可见（[已知限制](../limitations.md) M7#2 残留挂账）。根已存在、只往里放文件不受此限；项目 `.duo/skills`、`.agents/skills` 一般在仓库内，天然不受此限。
- **装配改动仍需重启**：热加载只覆盖技能文件本身；改 yml 装配（如禁用表 `disabled`、摘掉 `skills` 行）属行级配置热重载，是另一条挂账中的能力（[已知限制](../limitations.md) 遗留 #1）。

验证方法（不改一行 Java）：往任一发现根放一个最小技能文件，约一个心跳窗口后问模型「你能看到哪些技能」，名录应已含它；改它的 description 再问，名录行应更新；把它加进 `disabled` 重启，名录应不再出现。

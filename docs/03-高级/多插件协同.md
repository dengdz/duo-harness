## 3.1 插件模型速览

一切从 `Plugin<C>` 接口开始（`dev.duo.harness.core.api.Plugin`，ADR-0001）。它只有四个方法，两个必答、两个可选：

```java
public interface Plugin<C> {

    /** 硬依赖：全部就绪才启动，任一消失即停止（缺省无依赖）。 */
    default Set<String> inject() { return Set.of(); }

    /** 可选依赖：就绪则用、缺失不拦（ADR-0019，缺省无可选依赖）。 */
    default Set<String> optionalInject() { return Set.of(); }

    /** 声明 config 类型；返回 null 表示不接受配置。 */
    Class<C> configType();

    /** 插件本体：装配点。副作用挂 ctx，回收由内核保证。 */
    Disposable apply(Context ctx, C config) throws Exception;
}
```

四条骨架语义，每条都值得在动手前记住：

- **config 严格绑定**：`configType()` 声明的 record 就是配置契约。yml 的 `config:` 块由 Jackson 绑定到它——未知字段、类型不符、缺字段都**启动即 FAILED 并点名插件与字段路径**，绝不静默纠正或填默认值凑合（ADR-0003）。声明了 config 类型却不提供 `config:` 块，同样绑定失败。
- **apply 是装配点**：注册服务、监听器、工具、命令、子插件……一切副作用都在这里经 `ctx` 施加。`apply` 抛任何异常只导致**本插件实例**失败并被清理，不传染兄弟插件。
- **副作用可逆**：`ctx.effect(...)` 注册的回收逻辑在作用域销毁时**按注册逆序**执行；经 `ctx` 注册的服务、监听器、工具、命令同时也都是作用域副作用——**插件停止即自动注销**，不依赖你记得处理返回值（ADR-0001 的根约定："能力是可逆的副作用"）。
- **六态可观测**：任何时刻 `ctx.snapshots()` 给出全部插件的六态即时视图，这是 Web 状态面插件表的数据源：

```
PENDING --依赖全就绪--> LOADING --apply 成功--> ACTIVE
LOADING --apply/绑定失败--> FAILED（终态）
ACTIVE --依赖指纹变化--> UNLOADING --回滚完成--> PENDING（回归等待，可自动重启）
任意 --dispose--> UNLOADING --> DISPOSED（终态）
```

配错长什么样，看 example 模块里最小的带配置插件 `GreetingPlugin`：

```java
public final class GreetingPlugin implements Plugin<GreetingPlugin.Config> {

    /** config record：yml 的 config 段绑定到这里（严格模式全字段必填）。 */
    public record Config(String prefix) { }

    @Override
    public Class<Config> configType() { return Config.class; }

    @Override
    public Disposable apply(Context ctx, Config config) {
        ctx.provide(GreetingService.SERVICE_NAME,
                (GreetingService) name -> config.prefix() + ", " + name + "!");
        return null;
    }
}
```

对应 yml 行 `config: { prefix: "你好" }`。把 `prefix` 拼错成 `preifx`，重启即 FAILED、审计点名到字段路径——错误在启动时暴露，而不是运行到一半才悄悄走默认值。

> 为什么是自研容器而不是 Spring/ServiceLoader：容器语义围绕"可逆副作用 + 依赖驱动启停"生长，DI 框架的生命周期模型对不上，ServiceLoader 的"发现即全装"与配置树持有发现权冲突——见 [ADR-0001](../adr/0001-自研插件容器内核.md) 与[设计主线 §主线一](../04-架构/设计主线.md)。装配失败的排查路径（FAILED 点名 / PENDING 列缺失服务 / 整树回滚）见[插件配置参考 §出错怎么看](../05-参考/插件配置参考.md)。

## 3.2 从零写一个插件：tool-stats 全程

`duo-harness-stats` 是 M27 为"第三方插件能不能挂得上"专门做的验收 demo（ADR-0029）：一个独立 Maven 模块，**三个类**构成最小完整形态——

| 类 | 职责 |
|---|---|
| `ToolStatsPlugin` | 插件骨架 + 四个扩展点的全部接线 |
| `ToolStats` | 纯计数器（LongAdder 并发安全，无框架依赖） |
| `StatsViews` | 消费服务的视图接口集合（见 3.3） |

能力三件：监听工具执行按工具名累计调用与失败；`/toolstats` 命令现场出文本报表；`tool_stats` 查询工具给模型侧用。下面把 `ToolStatsPlugin` 的四个扩展点逐个接线讲清。

### 第一步：inject() 声明依赖——错误前移

```java
@Override
public Set<String> inject() {
    return Set.of(ToolsService.SERVICE_NAME, CommandsRegistry.SERVICE_NAME);
}
```

要往工具域和命令域注册东西，就声明消费 `tools` 与 `commands` 两个服务。这是**硬依赖**：全部就绪才启动；装配里漏挂了对应行，插件停在 PENDING，boot 审计列明缺失的服务名——**缺服务不启动、错误前移到启动期**，免写任何"先判断再动手"的防御代码，也免写启动顺序。

### 第二步：ctx.on(POST_EXECUTE)——只观察不改写

```java
@Override
public Disposable apply(Context ctx, Void config) {
    ToolStats stats = new ToolStats();

    // 结果治理段计数（挂接即作用域 effect，插件停止自动摘除；只观察不改写）
    ctx.on(ToolsService.POST_EXECUTE,
            (WaterfallListener<ToolExecution, Boolean>) (exec, next) -> {
                stats.record(exec.toolName(), exec.resultIsError());
                return next.invoke(exec);
            });
    // ...
}
```

`tools/post-execute` 是工具三段管线的瀑布挂点（详见 3.4）。统计插件的立场是**只观察不改写**：记完数照常 `next.invoke(exec)` 把调用透传给内层——一个监听器想"偷看"还是想"拦截"，分界就在这一行调不调 `next`。

统计口径有一处诚实声明：计入的是**进入执行段**的调用——pre-execute 否决与审批挂起不经过结果治理段、不计；`tool_stats` 自己的查询调用同样被计数（统计者也被统计）。

### 第三步：tools.register——零参 schema 与实现诚实一致

```java
ToolsService tools = ctx.as(StatsViews.ToolsView.class).tools();
tools.register(ctx, new ToolDefinition() {
    @Override public String name() { return TOOL_NAME; }          // "tool_stats"
    @Override public String description() {
        return "工具使用统计查询：返回自插件挂载起各工具的调用次数与失败次数";
    }
    /** 零参数查询：schema 与实现诚实一致（无 properties）。 */
    @Override public JsonNode parameters() {
        var schema = JsonNodeFactory.instance.objectNode();
        schema.put("type", "object");
        schema.set("properties", JsonNodeFactory.instance.objectNode());
        return schema;
    }
    @Override public Object execute(ToolExecution execution) { return stats.toJson(); }
});
```

三个要点：`parameters()` 返回的 schema 是模型看到的调用契约，**别声明自己不实现的参数**；`register(ctx, …)` 传的是插件自己的 `ctx`——注册即作用域副作用，插件停止工具自动注销；注册进的是全局工具域，模型与本地工具一视同仁地看到它。

### 第四步：commands.register——ANY + busySafe 执行中可敲

```java
CommandsRegistry commands = ctx.as(StatsViews.CommandsView.class).commands();
// busySafe=true：纯内存只读，不触会话/上下文，agent 执行中可立即响应
commands.register(ctx, new CommandDefinition(COMMAND_NAME,
        "工具使用统计：按工具名输出调用次数与失败次数",
        CommandScope.ANY, true, context -> stats.toTable()));
```

命令名不带斜杠（`toolstats`，用户敲 `/toolstats`）；`CommandScope.ANY` 表示 CLI 与 Web 双面可用；`busySafe=true` 是关键裁定——这个命令纯内存只读、不触会话，agent 执行中也能立即响应；若声明 false，运行中会被明确回应"执行中，需等待空闲"（fail-closed，ADR-0020）。

### 接入：一共两行，零内核改动

插件写完，接入装配只要两行——example 模块的 pom 依赖一行：

```xml
<!-- M27 demo：工具统计插件（第三方插件形态范例，ADR-0029）——接入行之一 -->
<dependency>
  <groupId>dev.duo</groupId>
  <artifactId>duo-harness-stats</artifactId>
  <version>${project.version}</version>
</dependency>
```

加 `agent-demo.yml` 装配行一行：

```yaml
  # 工具统计插件（M27 demo，ADR-0029）：独立模块 duo-harness-stats——第三方插件
  # 形态范例，监听工具执行计数、/toolstats 命令 + tool_stats 查询工具。
  # 接入仅两行（example 依赖一行 + 本行），零内核改动；不装本行即零感知
  - id: tool-stats
    name: dev.duo.harness.stats.ToolStatsPlugin
```

装载是 `Boot.from(yml)` 按 `name` 的 FQCN 反射实例化（须有公共无参构造）。**不装这行即零感知**：类在 classpath 里躺着，不加载、不注册、不出现在任何清单。yml 装载全链路有测试兜底——`duo-harness-stats` 的 `BootYmlTest` 用三行 yml（tools / commands / tool-stats）走真实 `Boot.from`，断言快照里 `ToolStatsPlugin` 为 ACTIVE、工具域里 `tool_stats` 已注册。

最后看依赖方向：`duo-harness-stats` 的 pom 只依赖 `core`、`tools`、`agent`（拿 `CommandDefinition`），方向严格是 **stats → agent/tools → core，无任何反向**——内核不知道 stats 存在，tools/agent 也不知道。这正是"第三方挂得上"的结构证明：所有接线都走 3.1/3.3 的公开扩展点。扩展点全景（能挂什么、哪里挂不上）见[插件扩展点清单](../05-参考/插件扩展点清单.md)；`tool_stats` / `/toolstats` 的用户侧说明见[工具目录 §工具统计插件](../05-参考/工具目录.md)。

## 3.3 服务协同：provide / inject / optionalInject

插件之间不直接引用，协作全部走服务注册表（[设计主线 §主线一](../04-架构/设计主线.md)）。三个动词构成全部语法：`provide` 发布、`inject`/`optionalInject` 声明许可、`ctx.as(视图接口)` 读取。

### provide：发布具名服务

`ctx.provide(name, instance)` 把实例登记进全局注册表。两条纪律：

- **同名互斥**：同一服务名在默认作用域内只允许一个提供方，重复发布点名报错（点名先注册方）。harness 的内置服务保留裸名（`tools`、`prompts`、`approval`……），**第三方服务名必须加前缀**——这是撞名禁忌的制度化。
- **发布即副作用**：注销器自动挂进作用域，插件停止服务自动注销；依赖它的挂起插件被唤醒，依赖它的活跃插件被停止（依赖指纹翻动，见下）。

**服务名用 camelCase**——这不是风格偏好而是机制约束：视图代理按方法名解析服务名，方法名天然是驼峰。仓库为此付过两次学费（duo-workflow 经验档在册）：后台任务注册表首发为连字符 `"background-tasks"`、M24 的权限规则首发 `"permission-rules"`，都在视图接口取用时启动报错，分别修复为 `backgroundTasks` / `permissionRules`。经验档的机械核对项：**新服务发布前先 grep 既有 `SERVICE_NAME` 形态；SERVICE_NAME 常量与消费方视图接口方法名并排摆放、逐字一致后才编译**。

### 视图接口：方法名即服务名

消费方不拿实例，而是向内核要一个视图接口的动态代理：

```java
/** greeting 服务的视图接口（方法名即服务名）。 */
public interface GreetingView {
    GreetingService greeting();   // 方法名 "greeting" = SERVICE_NAME 逐字
}
```

`ctx.as(GreetingView.class)` 返回代理，**方法名即服务名**，调用时惰性解析到注册表当前实例——服务替换后无需重新获取。这套约定的好处是第三方视图接口自带在插件 jar 里，加服务不改 core（ADR-0001 决策一）。

greeting 三件套把服务协同的最小闭环摆全（都在 `duo-harness-example` 的 `example.greeting` 包）：

```java
// 契约：三处共用的身份约定
public interface GreetingService {
    String SERVICE_NAME = "greeting";
    String greet(String name);
}

// 提供方：apply 里 provide（见 3.1 的 GreetingPlugin 全文）
ctx.provide(GreetingService.SERVICE_NAME,
        (GreetingService) name -> config.prefix() + ", " + name + "!");

// 消费方：inject 声明 + 视图读取
public final class GreetingClientPlugin implements Plugin<Void> {
    @Override public Set<String> inject() { return Set.of(GreetingService.SERVICE_NAME); }
    @Override public Disposable apply(Context ctx, Void config) {
        GreetingService greeting = ctx.as(GreetingView.class).greeting();
        ctx.emit(DemoMain.DEMO_LOG_CHANNEL, "消费者经视图获得: " + greeting.greet("世界"));
        return null;
    }
}
```

提供方、消费方、契约接口三件套，加上 `StatsViews` 的 `ToolsView.tools()` / `CommandsView.commands()`——**视图接口方法名与服务名逐字一致**是 ADR-0019 的读取纪律，test 侧也经 `ctx.as(...)` 复用同一套视图。

### inject vs optionalInject：硬依赖与可选降级

`inject()` 的语义是**全部就绪才启动，任一消失即停止**：缺服务时插件 PENDING 挂起等依赖，boot 审计点名缺失清单。适合"没有它我就是不完整"的依赖（`ToolStatsPlugin` 离开 `tools` 无处注册）。

`optionalInject()`（ADR-0019 决策 7-8）是**就绪则用、缺失不拦**：缺失不阻塞启动；在场的可选服务参与依赖指纹，服务出现/消失触发**双向自动重载**——升级（出现即接上）与降级（消失即摘除重装配）对称，重载时 `apply` 以当时的在场性重新接线。仓库内两个先例：

- **CLI 纯对话装配**：`CliPlugin` 硬依赖五个核心服务，`workspace`、`memory`、`permissionRules`、`connectorStatus` 等七个全是可选注入——boot yml 去掉 `fs-tools` 行，CLI 照常启动聊天，`/permission` 降级提示"未挂载"（ADR-0019 决策 9 的验收用例）。
- **`WorkspaceApprovalPlugin`**：硬依赖 `answers` + `workspace`，`optionalInject("permissionRules")`——规则服务在场就加前置裁决，缺席审批链照常工作；代码里配 `ctx.hasService(...)` 判存后接线。

读取许可有一条红线：**未经 `inject()`/`optionalInject()` 声明的服务名，`ctx.as(...)` 读不到**——动态代理解析时点名拒读（错误前移）。这也是 M24 踩过的真坑：消费方用 `hasService` 判存却忘了声明 `optionalInject`，拒读异常被 try-catch 吞成"视为缺席"，规则面静默未装配（duo-workflow 经验档在册）。判存可以，声明先行。

### 撞名与互斥：approval 三选一

同名互斥不只是防御，也是**替换机制**：审批策略服务 `approval` 内置三个实现——`WorkspaceApprovalPlugin`（档位裁决）、`ApprovalPlugin`（always-deny / auto-approve 白名单）、`InteractiveApprovalPlugin`（无档位全 ask）——都发布同一个服务名，**三选一挂载**；同装两个即启动点名冲突。`agent-demo.yml` 的注释把这事写在装配行旁边：

```yaml
  # 档位审批（ADR-0012）：workspace-write 档区内写放行、越界/read-only 档 ask——
  # ask 交回答者瀑布（web 行在前 → 卡片优先呈现；纯 CLI 装配为终端 y/n）
  # ——与 ApprovalPlugin（always-deny / auto-approve）、InteractiveApprovalPlugin
  # （无档位全 ask）三选一挂载
  - id: approval
    name: dev.duo.harness.tools.fs.WorkspaceApprovalPlugin
```

服务名全表（谁发布、谁消费）见[插件扩展点清单 §服务名全表](../05-参考/插件扩展点清单.md)。

## 3.4 事件与钩子协同

### 事件面：五式与边界

插件间的事件协作走 `Context` 的事件面。模式有五个名字，落到 API 是四个方法——**bail 与 serial 同指投票式**（ADR-0001 按五种分派模式计数，`Context` 上的方法名是 `serial`，术语表的独立词条叫 bail）：

| 式 | 方法 | 语义 |
|---|---|---|
| 广播 | `emit(event, args)` | 同步按注册序逐个调用，忽略返回值；监听器异常隔离不传染 |
| 并发广播 | `parallel(event, args)` | 每监听器一个虚拟线程，等待全部；失败聚合上抛 |
| 投票（bail） | `serial(event, args)` | 首个非 null 返回值即终值并终止链，全员弃权返回 null |
| 瀑布 | `waterfall(event, args, terminal)` | 洋葱管线：可改写载荷、不调 next 即否决，先注册者为最外层 |
| 监听 | `on(event, listener)` | 普通监听器与瀑布监听器分表注册，互不影响 |

监听器表全树共享：任意作用域注册、任意作用域派发均可见，且注册即作用域副作用（插件停止自动摘除）。

**可听/不可听的事实边界**（[插件扩展点清单 §事件面事实](../05-参考/插件扩展点清单.md)）：插件听得到 `plugin/status`（状态迁移广播）、工具三段瀑布、插件间自定义事件；**听不到全部会话事件**——user/assistant 消息、todo、压缩点只写会话 JSONL 并通知会话私有监听器，不经事件总线（[已知限制 M27-1](../limitations.md)）。插件最接近"会话活动"的信号是 `tools/post-execute`——有工具调用与结果、无消息文本。

### tools 三段管线：协同的主战场

工具执行是一条三段瀑布：**pre-execute 准入 → execute 本体 → post-execute 结果治理**（`ToolsService` 契约）。多插件在这条线上协同的时序是硬约定：

1. **审批先行**：pre-execute 段里，钩子（若挂）与审批策略同段先到先决——审批拒绝的调用**到不了 guard**；
2. **guard 次之**：`tools.guard(...)` 注册的单调否决在审批之后、工具本体之前，理由即拒、无"允许"结果、拒绝无法翻回；
3. **输出契约兜底**：声明了输出契约的工具在治理段按契约校验，违约收敛为 error 结果。

这不是文档说说，仓库里有活的时序证明：`ContractGuardDemoMain`（example 模块 `contract` 包）第三幕同时装审批（always-deny）与 guard，调用一个声明需审批的工具——结果被审批拒绝，**guard 执行计数为零**：

```java
out.println("调用 deploy（工具声明需审批，策略 always-deny）:");
ToolResult result = tools.execute("deploy", NullNode.getInstance());
out.println("  -> [" + (result.isError() ? "被拒" : "放行") + "] " + result.value());
out.println("  guard 执行次数: " + guardRuns.get() + "（审批拒绝在先，调用到不了 guard）");
```

同一演示的三幕分别验证输出契约（合规放行 / 违约点名 / 未声明宽松透传）与 guard（理由即拒、首个拒绝短路后续 guard 不再执行），可运行复现：

```bash
mvn -pl duo-harness-example -am package exec:java \
  -Dexec.mainClass=dev.duo.harness.example.contract.ContractGuardDemoMain
```

### 插件监听的两个范式：否决改写 vs advisory

**pre 否决 + post 改写**——`ToolGuardPlugin`（example 模块 `tools` 包）一个插件占两段：

```java
Disposable pre = ctx.on(ToolsService.PRE_EXECUTE,
        (WaterfallListener<ToolExecution, Boolean>) (exec, next) -> {
            if (EchoToolPlugin.TOOL_NAME.equals(exec.toolName())
                    && exec.args().path("input").asText("").contains("危险")) {
                exec.deny("参数含敏感词（治理插件否决）");
                return false;                      // 不调 next 即否决
            }
            return next.invoke(exec);
        });
Disposable post = ctx.on(ToolsService.POST_EXECUTE,
        (WaterfallListener<ToolExecution, Boolean>) (exec, next) -> {
            if (!exec.resultIsError()) {
                exec.setResult(exec.result() + " [已治理]");   // 改写结果
            }
            return next.invoke(exec);
        });
```

**advisory 改写**——`RepeatReminderPlugin`（example 模块 `mcpfs` 包，装配行 `repeat-reminder`）在 post-execute 给重复调用附加逐级加码的提醒文本：提醒是建议不是否决——不改错误形态、不拦执行，模型自行换方法，硬性兜底仍是迭代上限。它的注释点破了语义分界：advisory 提醒**不是 guard**——guard 是单调否决，两者语义不兼容别混用。

### hooks.json：外部进程形态与插件监听的分工

不是所有协作者都写 Java。装上 `dev.duo.harness.hooks.HooksPlugin` 行（opt-in，不装零感知）后，`~/.duo/hooks.json` 让**任意语言的脚本**挂进同一条管线——格式复用 Claude Code/Codex，整文件粘贴即用：

```json
{
  "hooks": {
    "PreToolUse": [
      {"matcher": "bash", "hooks": [{"type": "command", "command": "/path/to/guard.sh", "timeout": 30}]}
    ],
    "PostToolUse": [
      {"matcher": "Write|Edit", "hooks": [{"type": "command", "command": "/path/to/audit.sh"}]}
    ]
  }
}
```

机制要点（全表见[插件配置参考 §hooks.json](../05-参考/插件配置参考.md)，决策见 [ADR-0019](../adr/0019-扩展机制.md)）：`PreToolUse` 映射 `tools/pre-execute`（可阻断）、`PostToolUse` 映射 `tools/post-execute`（结果改写为错误，不假装撤销已执行的副作用）；matcher 支持精确名/多选/正则；裁定走 exit 2 或 stdout JSON（deny/allow/ask，`ask` 交审批段）；**失败语义 fail-open**——钩子超时、崩溃一律放行 + WARN。

分工由此清晰：**外部脚本走 hooks.json**（生态兼容、语言自由、但不是执法边界——"绝不放行"的硬闸门用进程内 guard 或审批承担）；**进程内协同走插件监听**（类型安全、可逆副作用、与注册表/服务面联动）。两者同在准入段时先到先决、钩子只收不放——deny 占先省掉审批交互，但没有"跳过审批放行"的能力。

## 3.5 装配与行序

### 行格式与装载语义

`Boot.from(yml)` 读单文件 YAML，行格式四字段：

```yaml
plugins:
  - id: echo-tool          # 稳定标识：审计点名与状态面的锚点，必填
    name: com.x.EchoPlugin # 插件类 FQCN，反射实例化，须有公共无参构造
    config: { ... }        # 绑定到插件的 config 类型；声明了类型就必须带（免配置写 config: {}）
    disabled: false        # true = 跳过该行（保留行，不加载实例）
```

**顶层 `plugins:` 逐行反射装载，行序即装载序**——同一棵树按行序依次 `apply`。但对跨插件依赖来说，行序**不是正确性约束**：依赖未就绪的插件自动 PENDING 等待，提供方装载后自动唤醒。仓库 `demo.yml` 里故意把消费者行放在提供者行之前演示这一点（boot 状态叙述里可见它先 PENDING、`greeting` 行装载后转 ACTIVE）。所以"依赖先行"是**可读性建议**——读者从上往下能看懂数据流——而非硬性规则；真正按行序较真的只有下面这一对。

### web 先于 cli：行序契约双道闸

`cli` 行的 apply 就是 REPL 主循环——**它后面的所有行要等 REPL 退出才装载**。web 行排到 cli 行之后，Web 呈现位就静默缺席（M27 工单 05 实测后立约，[ADR-0029](../adr/0029-M27至1.0版图重排第二弹.md)）。防线有两道：

- **boot 前预检**（[启动器](../05-参考/术语表.md) `DuoMain` 的 `validatePresenterRowOrder`）：启动前扫描 yml，cli、web 两行同在而 web 后置时直接点名拒绝，错误信息带两个行号；
- **web 装配期 fail-fast**（二道闸）：预检只识别标准行形态（行尾注释、引号变体不识别，`disabled: true` 的停用行豁免）——漏网案例由 `WebPlugin` 装配期兜底：发现回答者已注册（说明 cli 已先装配）即抛点名异常。

```java
static void validatePresenterRowOrder(Path yml) throws Exception {
    // …逐行识别 "- id: cli" / "- id: web"（strip 后全等；停用行豁免）…
    if (cliIdx >= 0 && webIdx >= 0 && webIdx > cliIdx) {
        throw new IllegalArgumentException("行序契约：web 行必须先于 cli 行——cli 行的 apply"
                + " 即 REPL 主循环，其后的行在 REPL 退出前不会装载，web 行后置将静默缺席"
                + "（yml 第 " + (cliIdx + 1) + " 行 cli / 第 " + (webIdx + 1) + " 行 web）。"
                + "请将 web 行移至 cli 行之前。");
    }
}
```

顺带一提行序的第二重含义：cli、web 双开时**行序即回答者路由**——web 行在前，审批/提问由 Web 卡片优先呈现（纯 CLI 装配则是终端 y/n）。

### mcp 行：建议序而非契约

MCP 连接行后置（排在消费它的呈现位之后）不踩 cli/web 那种坑：呈现位对 MCP 状态服务是可选注入（`optionalInject`），服务出现经双向自动重载自动接上（3.3）——所以 `agent-demo.yml` 把 MCP 演示挪去 `demo-m2.yml`、正文里只留指路注释，行序上只作建议。这也解释了两种行序约束的本质差别：**cli/web 是"装载即阻塞"的硬语义，可选项靠自动重载自愈**。

### agent-demo.yml 全量导览

demo 装配（`duo-harness-example/src/main/resources/agent-demo.yml`）每一行都是前四节机制的活样本，逐行过一遍：

| 装配行（按文件行序） | 演示的机制 |
|---|---|
| `tools` | 工具域一行启用：发布 `tools` 服务（三段管线 + 审批/guard 挂点），后续工具类插件全部 `inject` 它 |
| `fs-tools` | inject `tools` 注册六件 + 发布 `workspace` 服务——服务面"既消费又发布"的复合形态；`mode` 配置走严格绑定 |
| `web-tools` | config 块须在场（可空块）、可选段控制注册面（search 不配即 fetch-only） |
| `attachment` / `session-query` | 行在场即启用的可选能力；`session-query` 对 `tools` 也是可选消费（tools 在册才注册 session_search 工具） |
| `prompts` / `agents-md` / `memory` | 内容域三行：prompt 片段、AGENTS.md 链、记忆本——memory 行 optionalInject `tools`（tools 在场才挂写入工具） |
| `skills` / `commands` | 技能清单 + 命令注册表（发布 `commands` 服务，供呈现位与 `/toolstats` 这类自定义命令共用入口） |
| `answers` | 交互服务回答者注册表——审批/提问 seam 的呈现端 |
| `approval` | 审批三选一互斥挂载（3.3），optionalInject `permissionRules` |
| `permission-rules` | 发布 `permissionRules` 服务（camelCase 惯例的修复产物）；不挂载即无规则能力，装配零感回退 |
| `repeat-reminder` | 3.4 的 advisory 改写插件；声明了 config 类型所以带 `config: {}` |
| `web`（在前） / `cli`（在后） | 行序契约双道闸 + 回答者路由（本节）；两行各带 `maxIterations` 走严格绑定 |
| `tool-stats` | 3.2 全程的主角：独立模块接入两行中的第二行 |

装配的三条通用约定（行序即装载序、config 块纪律、审批三选一）与逐行 config 字段全表都在[插件配置参考](../05-参考/插件配置参考.md)，不在此复制；启动失败的排查（FAILED 点名 / PENDING 缺失服务清单 / 整树回滚）同见其 §出错怎么看。

# 技能写作机制讲义（C1-02，四课）

- **读者**：duo 技能作者与改写执行会话。每课一个机制主题：Matt 侧机理（原文对照）→ duo 侧现状（原文对照）→ 改写方向。
- **锚点**：Matt 侧相对插件 1.2.3 根；duo 侧相对仓库根。机制编号 M1–M15 对应 [机制清单](机制清单.md)；逐技能证据见 [对比报告](对比报告.md) §2。
- **用法**：工单 04《技能写作规范》的五支柱（指针/判据/领先词/否定/剪枝）即本讲义课 1–3 的规范化产物；课 4 是中文写作的补偿策略。

## 课 1：指针与调用权（M1/M2/M7）

### Matt 侧机理

技能的 description 与 AGENTS.md 里的一行指向，都是**上下文指针（context pointer）**：命名上下文之外的材料，并写明什么条件下触达它。决定触达可靠性的是指针的**措辞**而非目标——"A must-have target behind a weakly worded pointer is a variance bug: sharpen the wording first"（writing-for-agents/SKILL.md:12）。指针写三件事：材料是什么、哪些分支该触发、领先词前置；常驻指针每个词每回合都付费，所以"Cut identity the body already carries"（:18）。

调用权（invocation）是编译期分流：user-invoked 设 `disable-model-invocation: true`，"reachable **only** by the human typing its name"（invocation.md:5）、"nothing but the human can fire it: **no other skill can**"（:8）——流程类技能对模型**不存在**，被擅自启动在结构上不可能。model-invoked 的判据测试："could the model usefully reach for this autonomously?"（:6）。依赖表达只有一种合法形态："Call the Skill tool with \"grilling\""——"**Naming the tool is what gets it fired**"（:16）；两个技能写两次调用（:20）；前置条件是 user-invoked 时改为"tell the user to run `/setup…`"（:22）。

### duo 侧现状

```markdown
# duo-code-review/SKILL.md:15（弱指针——目标材料不在上下文，凭记忆执行）
Standards 轴：调用 mattpocock `code-review` 技能的 Standards 子代理，用法以该技能为准。

# duo-workflow/SKILL.md:16（分流停留在正文散文——约束力最弱档）
设计访谈段模型不可自动触发，提示用户显式调用：`/grill-me`

# duo-workflow/SKILL.md:43（operative 引用用 markdown 链接）
验收件的准备与用户手动运行验证的完整流程见 [duo-acceptance](../duo-acceptance/SKILL.md)
```

15 个技能 0 个 `disable-model-invocation`、0 处显式调用形态（对比报告 §3 M1/M2 行）。

### 改写方向

- 调用权按工单 03 探测结论落地：支持分流字段则流程命令档切 user-invoked（description 同步剥触发词）；不支持则"正文点名文件+章节 + AGENTS.md 显式命令表"兜底并记档。
- operative 引用统一为显式调用指令；引用本体材料（规范/配置）时写"读 `<路径>` 的 `<节>` 并按其执行"，禁止"用法以该技能为准"。
- description 重写三规则：领先词前置、砍身份句（正文 H1 已有）、触发按概念收敛（对比报告 §5 预算：user 档 ≤60 字、model 档 ≤80 字）。

## 课 2：完成判据与领先词（M3/M5）

### Matt 侧机理

每个步骤以**完成判据（completion criterion）**收尾，两个杠杆属性：**clarity**（能分辨 done 与 not-done，模糊边界招致抢跑）与 **demand**（要求多少工作——"every modified model accounted for" 逼出彻底劳动）；最强判据兼两者（writing-for-agents/SKILL.md:47–52）。判据的落地形态是"出示已运行的证据"：

> "you can name **one command** … that you have **already run at least once (show the invocation and its output, redacted)**"（diagnosing-bugs/SKILL.md:59–60）
> "**No red-capable command, no Phase 2.**"（:66）

**领先词（leading word）**是预训练已有的紧凑概念，以 token 反复出现，招募模型已有先验锚定一整片行为——"fast, deterministic, low-overhead" 收敛为一个词 _tight_（writing-for-agents/SKILL.md:63–72）。它在指针里兼管触达：同一词活在提示词、文档与代码库中，触达更可靠（:65）。

### duo 侧现状

```markdown
# duo-acceptance/SKILL.md:18（正例：可判定 + 出示证据）
完成判据：命令在干净检出上复制粘贴即可执行成功

# duo-acceptance/SKILL.md:44（正例：形容词是 no-op，示例才锚定行为）
"详细"由示例锁定，不以形容词为准。

# duo-workflow/SKILL.md:14（反例：七节点箭头链，零完成判据）
流程：设计访谈 → spec/ADR → 拆工单 → 逐单实现 → 审查 → 验收 → 版本合并。

# duo-code-review/SKILL.md:94（duo 自己的诊断：描述性条款必然衰减）
「顺序固定不跳步」是描述性条款、无机械校验点，跨会话后必然衰减
```

duo 不缺判据意识（13/16 技能有判据语句），缺的是**统一用语**与**证据出示型判据**的推广；领先词有雏形（三件套/收口/最窄测试/防复发三问）但无自觉、无配套。

### 改写方向

- 判据用语统一为"完成判据："，流程节点逐个补判据；声称落盘完成的，判据写成"出示路径/输出"而非"确保已做"。
- 工单 04 词汇表设领先词条目（正例：收口、三件套、最窄测试；候选新词：上下文指针、证据先行），每词带一句定义 + Avoid 同义词。

## 课 3：否定措辞与体量治理（M6/M8）

### Matt 侧机理

以禁令转向是失败模式——被禁行为被拉进上下文反而更可用；默认正向表述，禁令只在无法正向表述的硬护栏处保留、且配正向目标（writing-for-agents/SKILL.md:74）。体量治理是四条互补纪律（:76–81）：单一事实源（duplication 抬高含义地位）、环境即真相源（复述即 cache，只 cache 环境查不到的：未成文惯例、决策理由、坑）、逐行相关性检查（默认命运是 **sediment** 陈旧沉积层）、no-op 猎杀（默认已遵守的指令白付负荷，判定"does it change behaviour versus the default?"）。

### duo 侧现状

```markdown
# duo-code-review/SKILL.md:33（反例：三重否定承载最关键治理条款）
豁免行级轴或 Java 规范轴的唯一合法路径：在工单审查报告与 review-log 双处写明理由，并经用户显式确认；
现场裁量豁免无效，沿袭先前工单的豁免同样无效（每次豁免都是独立决定）。

# duo-bug-ledger/SKILL.md:82-87（反例：否定作组织单元——整节四条禁令）
## 反模式（不要做）
- 只修不记、或修完才补记——…
- 症状转述、根因写操作层、防复发写"以后注意"——三条登记纪律不可破

# duo-trim-cot-leakage/SKILL.md:39（正例：同一约束的正向形态——列"什么保留"）
## 不是泄漏的（保留规则）
…以下规则按字面执行

# duo-skill-evolution/SKILL.md:230-281（反例：sediment 活体——两个完整示例与 §3/§5 换皮重复，全文 328 行）
```

### 改写方向

- 收口/豁免条款改正向："出示两处记档路径 + 本轮用户确认记录，缺一即未豁免"（治理语义不减，认知负荷大降）。
- 反模式节改"每步完成判据"节；硬护栏至多保留一条并配正向目标。
- 变更历史迁出 SKILL.md（duo-code-review 6 段 → experience.md）；duo-skill-evolution 328→≤120 行；新增剪枝问句进工单 04：这一行删掉后行为会变吗？不变即删。

## 课 4：中文补偿策略（背景线索 §5 重验终审）

### 结论

**中文不是执行漂移的根因**——duo 执行最好的技能（acceptance/comprehension）恰是判据密度最高的中文文档；Matt 全部机制可原样翻译。但中文在四个维度**放大**机制缺口，需补偿（24 版 §5 四维经重验成立，量化校准如下）：

| 劣势 | 重验后的量化与机理 | 补偿（进工单 04/05） |
|---|---|---|
| 同义空间大 | 验收/验证/确认/跑一下……口语方差高于英文；bug-ledger 列 7 种说法仍漏 | 触发分支写成概念（"任何'现实与预期不符'的陈述"），词汇表钉首选词 |
| 长定语链歧义 | "修复引入阻断级新代码改动时复跑四轴"修饰边界靠猜 | 判据与硬护栏一律短句列表，单句单判断（acceptance 已是范本） |
| token 密度 | 实测 duo description 均值 **163 字**（89–224）≈ Matt model 档（均值 31 词 ≈ 40 token）的 **4–5 倍**（24 版"3~5 倍""平均 90–130 字"按此修正） | user 档 ≤60 字、model 档 ≤80 字；身份句删除、触发词表占大头时上限放宽 |
| 词汇一致性无人钉 | 英文有天然中心词，中文必须人为钉住 | docs/agents/domain.md 升级为 Avoid 格式词汇表；SKILL 不引入表外同义词 |

### 中英并列锚点（独有建议，重验维持）

description 领先词中英并列——"收口（gate）"、"验收（acceptance）"。触发匹配发生在用户口语与描述词之间，双语锚点加倍召回路径，成本仅数 token。

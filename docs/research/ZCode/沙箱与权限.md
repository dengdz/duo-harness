## 功能一句话

ZCode **没有 OS 级沙箱**——曾有「protected-resource sandbox」，已整体撤除（源码注释留证），仅残留契约与遥测位；安全边界完全由权限引擎承担：五档协作模式 + allow/deny/ask 规则 + 只读 bash 命令运行时识别。

## 沙箱：无（曾有，已撤除）

- 全库（含 node_modules）`landlock` / `seatbelt` / `sandbox-exec` / `self-restrict` / `no_new_privs` / `bwrap` / `firejail` / `e2b` / docker 执行后端 **0 命中**；执行适配器裸 spawn（`apps/zcode-cli/packages/adapters/src/exec/node-execution-adapter-run.ts:204`）。
- 撤除铁证（注释）：`node-execution-adapter-run.ts:276`——「计时器提前到准备阶段是 **protected-resource sandbox 时代**的行为……**sandbox 撤除后**准备阶段只剩 shell snapshot 等既有异步步骤」。
- 残留契约（死代码/纯遥测）：`ExecutionSandboxPolicy`、`ExecutionRequest.sandbox`（adapters 侧无消费方）、模型可见入参 `dangerouslyDisableSandbox`（no-op，只喂 `zcode.command_execution.sandboxed` 遥测位，`packages/telemetry/src/agent-trace-runtime.ts:464`）、`SANDBOX_VIOLATION` 错误枚举与 `ShellPermissionPolicy` 死类型（`contracts/src/tools/bash.ts:314,329`）。
- 撤因不可考：开源快照历史压缩，无 commit 线索。
- 伪命中澄清：Electron `webPreferences.sandbox`（Chromium 渲染进程）、ai-elements 沙箱展示组件、`node:vm` REPL 上下文、workflow 子进程 VM——皆非 OS 沙箱。

## 权限引擎：安全边界的全部

### 五档协作模式

`contracts/src/interfaces/session.port.ts:32`：`plan` / `build` / `edit` / `yolo` / `auto`（auto 保留未实现、恒 deny）。TUI 循环切换 plan→build→edit→yolo（`packages/tui/src/app-mode.ts:5`）。

### 决策优先级链

`core/src/permission/service.ts:97` `checkPermission`：plan 切换工具 → 交互工具 → alwaysAsk（ask 压过放行压不过阻断，`:333`）→ **yolo 直通**（`:136`）→ auto deny（`:140`）→ `disallowedTools` deny（`:149`）→ 项目 deny/ask 规则（`:158/:167`）→ `checkPlanMode`（`:404`，readOnly+非 destructive 放行）→ 项目 allow（`:180`）→ WebFetch 域名预批（`:189`）→ workflow 草稿预批（`:202`）→ `allowedTools` 放行（`:217`）→ `checkEditMode`（`:518`）→ `checkBuildMode`（`:452`，readOnly 放行 / critical ask / high ask 除非 `autoApproveHighRisk` / 副作用 ask）。

决策产物 `PermissionBehavior = "allow" | "ask" | "deny"`（`:59`）；会话级规则仅内存（`grantSessionPermission:92`）。

### Bash 工具的三个专门机制

1. **能力声明**：`needsApproval: true` + `riskLevel: high` + `denyPriority: beforeAsk` + `patternSources: ["command"]`（`contracts/src/tools/bash.ts:470`）。
2. **只读命令运行时重估**（`core/src/tool/handlers/bash-semantics.ts:39` `isRuntimeReadOnlyBashCommand`）：命令解析（`bash-command-parser`，产出逐命令 AST 分析）→ permission-safe 检查 → git 运行时上下文安全（`bash-git-runtime-safety`，git 命令 + 不安全上下文拒判）→ 逐命令只读策略表（`bash-readonly-policy`）→ 写选项检测（`sed -i` 等）全部通过 → 改判 readOnly / `needsApproval: false` / risk low → **build / plan 档免审批**。全链 fail-closed：解析错误、不支持语法、动态词一律按非只读。
3. **前缀规则**：`Bash(prefix:*)` 规则经 `bash-command-permission-policy.ts:85` 评估与建议（`generated/bash-command-registry.ts` 命令注册表支撑）；高危根命令（bash / rm / sudo / chmod 等，`:19-36`）永不生成前缀规则。

### 审批执行流

`core/src/tool/executor/permission-flow.ts:41` `resolveToolPermission`：checkPermission → PreToolUse hook 覆盖（`applyPreToolPermissionDecision`）→ memory-file 权限 → deny 短路 → 审批门（工具 `prepareApproval` 可把 ask 降为 proceed，仅 workflow 三工具实现）→ ask 时 `emitPermissionRequested` + broker 与 PermissionRequest hook 竞速（`permission-responder-race.ts`）→ allow/deny/escalate/modify；`permissionUpdates` 持久化到项目规则（SQLite sessionStore，`permission-rules-persistence.ts:23`），会话级仅内存。hook 改写输入后重判（`permission-input-recheck.ts:24`）。

### 子代理加固

`bootstrap/src/subagents.ts:115` `sanitizeProjectAgentProfile` 剥项目级 `.zcode/agents/*.md` 的 `permissionMode`——仓库内容不能把子运行时切到 bypass/yolo；workflow 脚本子运行时固定 yolo（`script-workflow-child-runtime.ts:118`）。

## 配置面

配置键仅 `permission.mode` / `allowedTools` / `disallowedTools` / `autoApproveHighRisk` / `allowMediumRiskInAuto`（`contracts/src/config/index.ts:12-20`；缺省 `mode: "build"`、列表空、布尔 false）。**零沙箱配置键**。scope 优先级 System<User<Project<Session<Env<Cli（`:157-175`）；项目级模式持久化 SQLite（`getProjectPermissionMode`，`session-store.ts:39`）；`ZCODE_*` 环境变量清单无沙箱/权限项。

## 对 duo 的启示

1. **撤除先例**：一家曾实现沙箱又整体撤除（撤因不可考，记为风险证词）——duo 2026-09-21 沙箱出栈决议的直接参照。
2. **只读命令识别**是 read-only 档 bash 体验的替代路径（免审批的代价是一个 fail-closed 的命令解析器 + 策略表，工程量中等、永远追不上真实 shell 语义，故边界从宽判非只读）。
3. **规则引擎**（allow/deny/ask + `Bash(prefix:*)` + 项目级持久化）减少 ask 弹窗的工程形态，duo 权限深化期的直接蓝本。
4. **子代理权限加固**与 duo M16 的「子代理审批恒 never」异曲同工：受信边界按发起方收紧，防仓库内容提权。
5. `dangerouslyDisableSandbox` 类模型可见安全开关撤除后沦为遥测位——duo 设计安全参数时应避免「模型可见但 no-op」的中间态。

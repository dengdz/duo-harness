# 审批与提问交互（ZCode）

> 源锚点：`872ad960de7ec172591f7e1952f7849229f94521`（2026-09-21 本地核验）。M22 探测里程碑工单 07（T-11）产物，五段统一模板——本单只探**交互执行半边**，权限策略判定见 [../沙箱与权限.md](../沙箱与权限.md)。接口参考见 [../模块手册.md](../模块手册.md)。

## 机制全貌

权限服务判 ask 后，`resolveToolPermission`（permission-flow.ts:41）先经 approval-gate 收窄，再 `emitPermissionRequested`（:162）渲染确认窗，随即进入 `racePermissionResponders`（:184）：PermissionRequest hook 链与 broker 并发竞速，先到者生效。broker（ManualPermissionBroker，broker.ts:34）以 pending map 挂起 deferred 等客户端应答（Web 端 ElicitationDialog/PermissionDialog 反向 RPC，TUI 端 app-approval 审批面板），`resolvePermission` 回填后 `emitPermissionResolved`（:296），按 deny/escalate/allow/modify 分支落地。ask_user_question 走同一条审批通道（needsApproval），但 broker 按 toolName 分流到 userInput 交互（interaction-broker.ts:48），答案以 modify+modifiedInput 回注工具输入。

## 关键流程

① **竞速**：broker 先启动、requestPermission 内同步注册 deferred，保证「可见即可答」（permission-responder-race.ts:59-67）；broker 被 claim 即 abort hook，hook 胜出则 abort broker；败者 abort 在胜者 settle 之后（:50-57）。hook 抛错只「退赛」记 warn，不代用户拒绝（permission-flow.ts:185-197）。hook 应答形态：preventContinuation/permissionBehavior=deny→deny，allow→allow，带 updatedInput→modify（hook-flow.ts）；modify 后必须用新输入重查权限（permission-flow.ts:248-266）。

② **ask_user_question**：handler 本身只校验「已应答输入」（ask-user-question.ts:43-68）；问题含 multiSelect、option preview、Other 自由输入。应答链：broker 发 interactionRequestUserInput 反向 RPC，与 v4 resolveInteraction 登记 deferred 竞态（interaction-registry.ts:8-14）；accept→decision modify，modifiedInput={...input, answers, annotations}（interaction-broker.ts:370-395）；decline/cancel→deny；空 answers={} 是「继续用最佳判断」的显式语义（:495）。TUI 键位：j/k/数字/空格多选、o=Other、s=跳过、return 提交进 review，review return→resolve modify（app-question-state.ts:114-145）；escape=deny。

③ **持久化**：`permissionUpdates`（allow_project）经 persistProjectPermissionUpdates 写 sessionStore 项目规则（permission-rules-persistence.ts:51-53，SQLite）；`sessionPermissionUpdates` 只进内存 ruleset，与项目级互不可见（permission-flow.ts:390-393）。TUI 未带建议时从 input 的 command/path 合成规则（app-approval.ts:144-158）。

## 接口与参数要点

- PermissionBrokerRequest：requestId/toolName/input/riskLevel/reason/suggestedPermissionUpdates/optionsPolicy；Result：decision(allow|deny|modify|escalate)+reason+permissionUpdates+modifiedInput。
- approval-gate 单向收窄：prepareApproval 只能把 ask 降为 proceed 或附预览，失败仍 ask（approval-gate.ts:61-74）；askOptions.allowAlways→"no-always-allow"/"session-always-allow"（contracts/tools/contract.ts:114），create-workflow=session、save-workflow=false。
- broker 超时=deps.permissionTimeoutMs，仓库内无默认值（runtime/types.ts:132，undefined 即不超时）；abort→ToolCancelled，重复 requestId→InvalidStateTransition（broker.ts:44,87-94）。
- v4 侧 askUserQuestion 另有 hiddenGrace 60s+autoResolution 300s（interaction-registry.ts:37-38）。

## 边界与坑

- **竞速源于旧串行 bug**：hook 阻塞期间确认窗可见但 deferred 未注册，点击被幂等丢弃、turn 永久挂起（permission-flow.ts:179-183 注释）——应答通道必须先于可见窗建立。
- hook 基础设施故障≠用户拒绝，退赛不 fail-closed；但 hook 胜出时 broker 产生的拒绝要吞掉（自己的取消）。
- memory 文件（.md 且在 memoryRoot 内）写操作特判强制 allow（memory-file-permission.ts）。
- 会话规则不持久，重启即失；项目规则持久化失败会整体 turn 失败（StorageError）。

## 对 duo 的启示

- duo 现为审批 seam+y/n 与卡片、单应答方：可参考「**应答通道同步注册先于 UI 可见**」的时序契约，避免 UI 先渲染、回调后挂的死窗。
- **allow_project→规则落 SQLite 项目库**、跨会话免确认，比 duo 仅会话内记忆价值更高；可分「项目规则/会话规则」两层。
- **超时语义**：ZCode broker 默认不超时、取消走 abort→ToolCancelled；duo 若加超时应区分「超时拒绝」与「用户取消」两种错误形态，并明确 hook 类自动应答方故障时不代用户拒绝。

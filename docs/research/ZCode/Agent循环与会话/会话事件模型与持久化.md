# 会话事件模型与持久化（ZCode）

> 源锚点：`872ad960de7ec172591f7e1952f7849229f94521`（2026-09-21 本地核验）。M22 探测里程碑第 4 批产物，五段统一模板。接口参考见 [../模块手册.md](../模块手册.md)；循环语义见 [Agent循环与状态机.md](Agent循环与状态机.md)。

## 机制全貌

事件词表集中单文件：`packages/contracts/src/events/session.events.ts:83-173` 的 `SessionEventType` 常量表共约 80 个类型，按域分组：session 生命周期（created/resumed/forked/compacted/title/mode/ended）、turn/steer 输入队列（steer 的 queued/delivery/dispatch/drained/rejected/discarded/reordered、input promoted、queue autoDrain、followup mode）、消息（user/assistant/system/feedback）、模型流（request/selected/streaming/complete/error/network/anomaly）、流恢复（stream_recovery 6 种）、tool（scheduled/started/progress/result/error/batch）、后台任务 3 种 + `dynamic_workflow_run_progress`（带 dynamic_ 前缀防与 legacy script workflow 同名混淆，:139-142）、权限 3+1、workspace hook 审查 4、hook run 5、compact 5（含 compact/microcompact boundary）、rewind/checkpoint、target 2、subagent 3、控制（interrupt/cancel/resume/error）。payload 按类型一 interface（:182 起），统一信封 `SessionEvent`（:72-81：id/sessionId/turnId?/type/timestamp/traceId/sequenceNumber/payload: unknown）。

存储分层的关键设计：`SessionEventStorePort`（`packages/contracts/src/interfaces/session.port.ts:57`，append/getEventsAfter/getLatestSequenceNumber）唯一实现是 `InMemorySessionEventStore`（`contracts/src/events/in-memory-session-event-store.ts:33`），事件按 turn-window 淘汰、本质易逝；持久事实走 `SessionStorePort`（`session-store.port.ts:1089`）落到 sqlite。即「**事件流内存、投影落库**」。

## 关键流程

① **入库链路**：`core/src/runtime/methods/events.ts:88 appendEvent` → `eventStore.append`（内存追加+统一补 seq，append 计数器只增不减防 seq 复用）→ `persistDurableSessionEvent`（events.ts:263）只选择性投影：CheckpointCreated/RewindTriggered/UserInputAutoResolutionUpdated/session_input 账本等 → `notifyEventSinks`。live/replay/snapshot 的 seq 全部来自同一 event store。

② **打开与迁移**：`adapters/src/storage/session-store/sqlite-session-store.ts:248` `new DatabaseSync(path,{timeout})`（timeout 须在首条 PRAGMA 前生效）；`openStartup`（:272）用 `deferredStartup` token 延迟迁移，`runSqliteSessionMigrationsAsync`（`migration-runner.ts:59-97`）先把 busy_timeout 降到 25ms、锁等待预算放宽到 1 小时，结束（含失败）在 finally 恢复 5 秒，`steps.return()` 收尾 generator 事务——半迁移连接绝不交给业务。

③ **message/part 模型**：0001 建 `message(id,session_id,data)`/`part(id,message_id,session_id,data)`，data 整体 JSON 序列化（`codecs.ts`/`repositories/messages.ts:69,146`）。0014 加 `sequence` 列，用 `row_number()` 全量回填+3 个索引；0015 起因旧版本二进制并存写 NULL sequence（观测 1690/5933 行），改为增量回填（从 max+1 起编号避免撞号）+ AFTER INSERT 触发器 `message/part_sequence_autofill` 兜底。

④ **事务与并发**：迁移强制 WAL（`migration-runner.ts:137-148`，拒 WAL 即抛）；`begin immediate` 拿锁后逐项核对 `schema_migration` 账本（id/checksum(sha256)/app_version/time_applied），checksum 不匹配即拒（:300-315）；fork 走 begin immediate 多表单事务并留故障注入点（`options.ts:1-16`）。多个本地/远程 Agent 显式共库（sqlite-session-store.ts:246 注释）。

- PRAGMA：`foreign_keys=on`、`journal_mode=wal`、busy_timeout 三态（常态 5s / async 迁移期 25ms / DatabaseSync timeout）。

## 边界与坑

- busy_timeout 必须先于首条 PRAGMA，否则并发启动在 migration prelude 直接 `database is locked`。
- 只重试 SQLITE_BUSY，SQLITE_LOCKED（同连接/共享缓存）不重试（:122-123）；通知失败不得覆盖原始数据库异常。
- 历史迁移 SQL 冻结不可改（补新迁移，0022 即范例）。
- 词表用 `/* eslint-disable max-lines */`（session.events.ts:3）强制单文件维护防协议类型漂移。

## 对 duo 的启示

duo 现状：JSONL 会话文件 + M21 内存倒排检索。对照三条：

1. duo JSONL+内存倒排与 ZCode「事件内存+选择性投影」同构，缺的是 **seq 权威单点与投影分离**——可先补 append 统一补号，不必换引擎。
2. **迁移器最小闭环**（编号 SQL+账本+checksum 冻结+WAL/busy_timeout 策略）可直接照抄；duo 已留 FTS5 接口语义，等消息量或多进程共写成为真实痛点再切 SQLite。
3. **message/part 两表 + JSON data + sequence 列**天然承载 file/image/pdf/url part（session.events.ts:1053），duo 单行 message 粒度对附件元数据检索不利；0015 的 NULL 序号事故警示：并存二进制共库是真实风险，兜底触发器+读路径 fallback 值得预置。

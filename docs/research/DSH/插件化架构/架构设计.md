# DSH 插件化架构设计

> 源锚点：`b150a551b8d465e31e418e1b2eaf5e79bbb7d28e`（2026-08-24 确认为本地 HEAD；同日远端 pull 因网络失败，本地为最新已知状态）。出处均为 DSH 仓库内路径。配套：[代码说明.md](代码说明.md)、[细节备忘.md](细节备忘.md)、[../总览.md](../总览.md)。

## 功能一句话

DSH 没有单体核心：整个 harness 跑在 vendored 的 Cordis 插件容器上，所有能力（LLM、工具、MCP、会话、Web UI）都是插件，运行形态由 profile → bundle 补丁层在启动时合成为一棵插件树，宿主与浏览器各跑一棵树共享同一容器内核。

### 框架与插件的边界

- **无特权核心**："There is no privileged core to patch: you extend dsh by mounting a plugin beside the others"（`docs/architecture.md:13`）。模型适配器、工具注册表、agent loop 本身都是插件。
- 插件能做的：实现 `apply(ctx, config)` 或继承 `Service`；声明 `inject`/`provide`/`Config`；注册可逆 effect（`ctx.effect`/`ctx.on`/`ctx.provide`）。插件形状三规范见 `vendor/cordis/src/registry.ts:92-133`。
- 插件不能做的：Context 是 Proxy，未 provide 就 set 属性直接抛错（`vendor/cordis/src/reflect.ts:178-183`）；未声明 inject 读服务抛错（`vendor/cordis/src/reflect.ts:144`）；保留名（`prototype`/`then`/`_` 前缀）绕不开服务解析（`vendor/cordis/src/reflect.ts:80-91`）。
- 所有产品包把 cordis 声明为 peerDependency——运行时必须共享单一份容器实例（`vendor/README.md`；强制脚本 `scripts/check-workspace-constraints.ts:336-342`）。

## 核心抽象与职责表

四轴正交：**Context/Fiber 是"作用域与生命周期"轴，Registry/Reflect 是"服务寻址"轴，Events 是"通信"轴，Loader 是"配置→代码"轴**。同一插件可在不同 isolate 作用域有不同实例，同一服务名在不同作用域解析到不同实现。

| 概念 | 职责 | 定义处 |
|---|---|---|
| `Context` | 依赖容器 + 插件唯一句柄。Proxy 包裹，属性读写走服务解析；`extend()` 产原型链子上下文；`isolate()`/`intercept()` 产作用域子上下文 | `vendor/cordis/src/context.ts:42,99,121,139` |
| `ReflectService` | 服务寻址：全局 store 按 (服务名, isolate symbol) 分槽；静态 ProxyHandler 是 ctx 属性 trap 的实现；`provide/notify/mixin` | `vendor/cordis/src/reflect.ts:133,233,254,277,314,364` |
| `Service` | 具名服务基类，构造即 provide、fiber 卸载即注销 | `vendor/cordis/src/service.ts:11,42` |
| `RegistryService` | 插件回调注册表；`ctx.plugin()` 归一化插件形状、建 Runtime、new Fiber | `vendor/cordis/src/registry.ts:195,316` |
| `Fiber` | 一次插件 apply 的运行时实例（同插件多加载 = 多 Fiber）；持有子 context、inject 依赖表、disposer 栈、六态状态机；epoch 依赖指纹驱动自动启停 | `vendor/cordis/src/fiber.ts:184,147` |
| `EventsService` | 事件总线，五种派发模式 emit/parallel/serial/bail/waterfall；监听器注册为 fiber effect 自动解绑 | `vendor/cordis/src/events.ts:32,131` |
| `Loader` | 配置树所有者（服务 `loader`），Entry 树 + `internal/config`/`internal/update`/`internal/plugin` 钩子 | `vendor/loader/src/index.ts:65` |
| `Entry` / `EntryGroup` | 一行配置 / 一组行；Entry 负责 import 模块并 `registry.plugin()`；Group 做事务式增删改回滚 | `vendor/loader/src/config/entry.ts:52`、`config/group.ts:6` |
| `Include` | 文件型子树：cordis.yml 即一棵子树；`applyEntryPatches` 是层序合成唯一算法 | `vendor/include/src/index.ts:174,58` |
| `Hmr` | 源码/配置热更：chokidar 监听 → 定位受影响插件入口 → 保 entry/config 重载 | `vendor/hmr/src/index.ts:86` |
| `ToolRuntime` | 工具注册与执行中枢（服务 `tools`）；分层注册表 + waterfall 管线 | `packages/core/tools/src/index.ts:787` |
| `ClientModuleRegistry` | 宿主半边双面模块系统（服务 `clientModules`）：扫 Loader 树的 `dsh.client` 声明，组装 boot manifest | `packages/client/modules/src/index.ts:282` |
| `ClientModuleSystem` | 浏览器半边：lazy CJS 表 + 实现 loader `internal` 契约，让 vendored Loader 在浏览器原样复用 | `packages/client/modules/src/client/system.ts:53` |

### 关系图（谁持有谁）

```
Context 构造器（context.ts:71-84）一次造齐：proxy / root fiber(uid=0) / reflect / registry / events / logger

RegistryService ──Map<callback,Runtime>──► Runtime{fibers: Fiber[], Config}
     │ ctx.plugin()
     ▼
Fiber ──持有──► ctx(=parent.extend({fiber})) / inject 表 / _disposables(effect 栈)
     │ 父 fiber.effect 注册 dispose（fiber.ts:265-297）→ 父卸载级联卸子
     ▼
ReflectService（全局单例）
     ├── store: 按 isolate symbol 键控的 impl 表
     ├── 静态 ProxyHandler = Context 的 get/set trap
     └── mixin 把 on/emit/plugin/inject/provide 铺到 ctx 上（reflect.ts:219-222）

Loader(服务) ──extends──► EntryTree ──store──► Entry ──fiber──► Fiber
     Include = 文件型 EntryTree（cordis.yml 子树）
     EntryGroup(Group 插件) = 树中树

EventsService ──_hooks[name]──► Hook{ctx, callback}（listener 归属 fiber，随卸载摘除）
```

## 数据流向

### 1. 启动合成链（配置 → 插件树）

```
dsh bin → composeProfile（profile.ts:371,413）
  层序：空表 → 各 bundle patch（dsh.profile.bundles 顺序）→ profile cordis.patch.yml → home 层 → --patch overlay
  全部 flatten 成一个 patch 列表，一次 applyEntryPatches 调用
    ▼
boot()（app-boot/src/index.ts:757）
  new Context() → ctx.plugin(Loader) → prepare → mountRootInclude()
    ▼
Include（固定 id 'include'）：读 cordis.yml → applyEntryPatches → EntryGroup.update 逐行 create
    ▼
每行 Entry._init：tree.import(name) → registry.plugin(plugin, config) → fiber.await()
    ▼
loader.await() 等全树 settle → assertEntriesActivated 审计（FAILED 重抛 / PENDING 点名缺失服务）→ 失败整体 dispose 回滚
```

patch 合成语义（`vendor/include/src/index.ts:58-128`）：`{insert}` 向根或指定 group 追加行（insert 行即时入索引，后续 patch 可继续改它）；`{id, ...overrides}` 按 id 定位、**逐字段浅覆盖，config 整行替换而非深合并**；没有 delete，删除行 = `disabled: true`（行缺席会随层序重排复活，禁用不会——`packages/bundle/web-app/cordis.patch.yml` agent plane 注释块）。

### 2. 服务解析链（插件间依赖）

```
provider：Service 构造 / ctx.provide(name, value)
  → props[name] 登记 + 按 isolate symbol 写全局 store + 记入 provider fiber 快照
  → notify(依赖者集合)：逐个 _checkImpl + fiber._refresh
       ▼
consumer：静态声明 inject: ['tools', ...]
  → Fiber._refresh：epoch = 各依赖 impl.fiber.uid 拼串
       依赖全就绪 → epoch 变化 → _reload（校验 config → 跑 apply → ACTIVE）
       依赖缺失   → epoch = INACTIVE → 自动 _unload 回 PENDING
  → ctx.tools 读取：Proxy get 沿 fiber 父链查激活期快照，每步校验 isolate 一致
```

依赖等待是声明式永久 PENDING（无超时无报错），由 boot 终审兜底判死；服务注销时 notify 反向驱动依赖者自动卸载或换实现重启（`vendor/cordis/src/reflect.ts:314-336`、`fiber.ts:611-639`）。

### 3. 工具执行管线（waterfall 洋葱）

```
agent loop → ctx.tools.execute(name, args)
  → createExecution（冻结参数/token）
  → tools/pre-execute waterfall（allow/deny/ask → approval 服务）
  → guard 门（单调否决，只能拒不能准）
  → tools/execute waterfall（超时/重试/指标包装）→ tool.execute 本体
  → 结果过 output.schema 契约校验
  → tools/post-execute waterfall（accept 换内容 / block 变错误反馈）
  → finalizeContent → tools/result 事件
```

工具对模型可见面只有 name/description/parameters 三字段（`packages/core/tools/src/index.ts:1256-1267`）；`timeoutMs`、`presentCall` 等治理字段永不发给模型。

### 4. MCP 工具同步链（外部能力 → 普通工具）

```
mcp-client fiber（inject ['tools']，每个实例连一个 server）
  → apply：预约 serverName 命名空间 → startConnection → await connection.ready（阻塞 fiber 激活）
  → syncTools 两阶段：Phase1 fetch（tools/list 分页，任何失败保留上一代）→ Phase2 swap（先 dispose 旧代、再全量注册，冲突回滚全代——全有或全无）
  → 命名：mcp__<server>__<raw>，非法字符清洗 + 截断后追加 sha256 前 12 hex 防碰撞（tools.ts:111-117）
  → 断连：指数退避（500ms 起、30s 顶）、稳定窗口清零计数、10 次预算耗尽注销全部工具；fiber dispose = 停连 + 注销
```

MCP 工具对 ToolRuntime 来说与内置工具无差别——这是"外部能力零侵入接入"的样板：能力包只 `ctx.tools.register(def)`，不碰主循环。

### 5. 页面插件链（双面模块系统）

```
宿主半边（host 树内）：
  ClientModuleRegistry（inject ['webServer','loader']）
    订阅 internal/plugin 增量标脏 → 扫描 entry 包的 dsh.client 声明 + exports['./client']
    → orderByModuleGraph 拓扑排序（external 边，环报错）→ BootManifest{rev, entries[]}
    → /plugins/<id>/client.js bundle 路由 + HTML 注入 __DSH_BOOT__ 与预载脚本

浏览器半边（独立一棵树）：
  AppWebEntry.run（packages/client/web/src/boot.ts:46-78）
    → __ModuleLoader__.create（queue→live）→ new Context() → ctx.plugin(Loader)
    → loader.internal = clientModuleSystem（浏览器版模块到达契约）
    → 为 manifest 每行 loader.create({name}) → loader.await() → 激活审计 → 注入 UI
```

两棵树共享同一套 Fiber/inject/激活语义；宿主树行带 config（配置驱动），浏览器树行只有名字和 inject 边（manifest 驱动）。ui-* 插件是标准 Cordis 插件：`inject = ['slots','layout',...]`，apply 里向 slot 注册 React 组件——"声明即占位（declaring is claiming）"，shell 声明的洞由其他插件占用（`packages/client/ui-sidebar/src/client/index.ts:26-58`）。

## 扩展点分类（DSH 实际使用的六种形态）

| 形态 | 机制 | 实例 |
|---|---|---|
| service 提供者 | 继承 Service / ctx.provide，占住 ctx.\<key\> | `dsh-llm-deepseek` 注册适配器（base patch webserver 行同族） |
| 工具注册者 | `ctx.tools.register(def)`，schema 自动进 prompt | `dsh-mcp-client`（inject ['tools']，effect-scoped） |
| waterfall 拦截者 | `ctx.on('tools/post-execute', (exec, result, next))`，不调 next 即否决 | `dsh-spill-policy` 转存超大结果 |
| 事件监听者 | `ctx.on(event)`，随 fiber 摘除 | `dsh-client-modules` 监听 internal/plugin 增量扫描 |
| UI slot 注入者 | 浏览器树插件占通用 UI 槽位 | `dsh-client-ui-brand-official`、`ui-sidebar` |
| bundle 装配者 | patch 文件 + runtime glue，改变整棵树形状 | `dsh-web-app`（关行 + 插行 + webStartup 服务） |

隐含第七种：**配置行本身即扩展**——`disabled: true` 关行与加行同级，都是 patch 动词。

## 能力接缝（seam）设计

- **seam = 可交换能力**，三角色齐全才算：Service Definition（声明接口的包）+ Service Provider（实现包）+ Consumer（使用方）。「A package may combine roles, but one role alone is not a seam」（`docs/architecture.md:100`）。
- seam 的价值在**成组交换**：fs 与 subprocess 共享同一执行世界，指向远程沙箱即同时迁移 Bash/PTY/LSP（`docs/architecture.md:102`）。
- 边界规则：seam 包零运行时依赖（实证 `packages/fs/fs/package.json` dependencies 为空）；实现包 peer 依赖 seam 包；消费者只依赖 seam 接口与事件；策略类横切能力经 `fs/*`、`tools/*` 事件门挂载，不进 seam 接口（`docs/capability-seams.md:423`）。
- 服务三档标注：`seam`（可换实现）/ `core`（脊柱单实现）/ `bundle`（组合点），全表 `docs/capability-seams.md:426-488`。设计 seam 前先决定是注册表（如 `ctx.llm` 多实现并存）还是单座位（如 `ctx.sessionTitle` sole provider）。
- 扩展挂在事件与服务契约上，不挂在具体驱动实现上：`ctx.agentLoop` 标为 bundle 并注明 extension packages depend on events and services, not this package（`docs/capability-seams.md:460`）。

## 机制要点提炼（事实性总结，是否采纳由 duo-harness 的 ADR 决定）

1. **Context 动态代理 + 注册表解析**：服务寻址与类型声明分离；"读服务必须先声明 inject"是刻意约束（错误前移）。
2. **Fiber = 插件实例 + 依赖驱动 epoch 重载**：依赖集合指纹（各依赖 fiber.uid 拼串）变化自动启停，免手写 boot 顺序（`fiber.ts:611-639`）。
3. **一切注册皆可逆 effect**：on/provide/plugin 全注册为 fiber effect，disposer 逆序清理、清理错误只记日志不传染——热插拔与作用域回收的地基。
4. **isolate 二阶键**：(服务名, 作用域 symbol) 寻址，配置行级 `isolate: true|label` 支撑"每会话一棵子组合"。
5. **patch 合成算法独立成纯函数**（applyEntryPatches）：boot 与 dump 工具共用永不漂移；insert 行即时可被后续 patch 命中是正确性关键。
6. **bundle = patch 文件 + 元数据声明**：产品"核心"只是一层 patch，无特权代码。
7. **配置惰性求值**（!!js）：表达式在依赖就绪后于行上下文求值，使配置能引用服务值。
8. **双面系统 = 同一容器内核 + 两个入口树**：浏览器半边只需实现"代码到达"契约，fiber/inject 治理完全复用。
9. **MCP 接入模式**：确定性命名（hash 防碰撞）+ 两阶段全有或全无同步 + 阻塞 fiber 激活直到首连完成。
10. **外部工具与内置工具同构**：能力包只注册工具 + 挂 system prompt 段，不侵入主循环。

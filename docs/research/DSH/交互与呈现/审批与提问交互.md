# 审批与提问交互（DSH）

> 源锚点：`ddefc45fbc7f8e46dd73185e68295696d1297887`（2026-09-21 本地核验）。M22 探测里程碑工单 07（T-11）产物，五段统一模板——本单只探**交互流半边**，档位策略语义见 [../沙箱与权限.md](../沙箱与权限.md)。接口参考见 [../模块手册.md](../模块手册.md)。

## 机制全貌

DSH 把「向人要一个决定」统一成 Cordis waterfall：`ApprovalService.request` 与 `UserQuestionService.ask` 都以 `scopeTarget(agent, agent)` 为目标向 Agent 作用域派发 `approval/request`（user-approval/src/index.ts:274-277）和 `user-questions/request`（user-questions/src/index.ts:135-142），答案者按组合顺序接力，返回结果即认领、调 `next()` 即委托，链尾兜底：审批 fail-closed `'unavailable'`，提问 reject `NO_PROVIDER`。UI 侧（ui-approval/ui-user-questions）经 Remote Event 白名单（api/remotes/src/remote-events.ts:20,41，mode 均为 waterfall）把 Host 事件转发给浏览器，客户端在 `ctx.remote.$on` 注册答案者（ui-approval/src/client/index.ts:90；ui-user-questions/src/client/index.ts:105）；Host 转发器要求事件携带的 `agent` 与 scope key 严格相等（api/remotes/src/index.ts:62-67），agent 身份随调用投影成客户端 scoped context。`ask_user` 工具不另开通道，直接消费 `ctx.userQuestions`（tool-ask-user/src/index.ts:81），与审批共用同一条用户问题链路；另一答案者 ACP 也在同一 waterfall 上挂监听（acp/acp/src/index.ts:155）。多面板/多客户端路由靠「认领过滤」：客户端答案者用 `ctx.sessions.scopeOf(owner)` 判自己是否拥有该会话，不拥有即 `next()` 让给别的客户端（ui-approval/src/client/index.ts:42-43）。

## 关键流程

① **审批 ask**：`tools` 的 `serviceAsk` 在 gate 决策为 ask 时调 `approval.request({agent, toolName, callId, reason, signal})`（core/tools/src/index.ts:1715-1721）；服务先校验 open turn，append `approval/asked`，派发 waterfall，append `approval/decided`（user-approval/src/index.ts:208-227）。UI 端 `answerApproval` 构造 `PendingApproval` 发布到 uiSession pending 域，composer 链的 select 命中后由 `ApprovalPanel` 接管输入位（ui-approval/src/client/index.ts:35-89）；用户点按 → `pending.answer('allowed-once'|'rejected')`（contract/slots.ts:122-126,64）→ 回传 Host waterfall → 映射：allowed-once→allow，rejected→deny，cancelled→deny+approvalCancelled，unavailable→deny「无审批通道」（core/tools/src/index.ts:1723-1736）。

② **提问 ask**：`AskUserQuestionItem{id,question,detail?,header?,options?,multiSelect?,intent?}`，应答 `AskUserQuestionAnswer{answers:[{id,selected[],custom?}]}`（user-questions/src/types.ts:36-67）；exit_plan_mode 走 `intent:{kind:'plan-review',approve,callId}`（plan/plan-mode/src/index.ts:315），UI 以 PlanReviewPanel 呈现。错误路径：`NO_PROVIDER`（无人认领，src/index.ts:130-133）、`BAD_INTENT`（approve 标签不在选项/缺 detail，115-128）、`EMPTY_QUESTIONS`。

③ **超时/abort**：审批 signal 已 abort 或竞速中 abort → `'cancelled'`，迟到答案按构造丢弃（user-approval/src/index.ts:262,286-299）；提问 abort → `ASK_ABORTED`（user-questions/src/index.ts:87,146-149）；UI 侧 signal abort 让 Pending 卡片 `abort(reason)` 收场（slots.ts:110-116,147-150）。

④ **UI 端**：答案者注册在 client 根 context（remote `$on`，监听 `this` 为按 agent 投影的 scoped ctx）；多会话按 `scopeOf(owner)`→sessionId 归属路由，无归属即 next()；同会话多 pending 靠域优先级选卡上屏：plan-review=2 > question=1 > approval=0（ui-user-questions/src/client/index.ts:91-93；ui-approval/src/client/index.ts:77-79；ui-session/src/client/index.ts:460-480）；插件卸载 teardown 先对未决请求逐个 `delegate()` 再 `next()`（ui-session/src/client/index.ts:400-406）。

## 接口与参数要点

- `ApprovalRequest`：agent/toolName/callId?/reason?/signal?（user-approval/src/index.ts:104-125）。outcome 闭集 `allowed-once|rejected|cancelled|unavailable`（types.ts:32），UI 只能回前两种；非法返回值归一为 unavailable（index.ts:281-284）。
- 答案者注册：Host 内 `ctx.on('approval/request', …)`；浏览器 `ctx.remote.$on(event, function(req,next){…})`；UI pending 发布 API `ctx.uiSession.registerPendingInteraction<T>(precedence)` 返回 `(interaction, delegate)=>disposer`（ui-session/src/client/index.ts:390-409）。
- `userQuestions.ask(request)`：questions+agent?+signal?；tool 参数 `multi_select` 映射 `multiSelect`（tool-ask-user/src/index.ts:87）。

## 边界与坑

- 非 open turn 调 `approval.request` 直接 throw（审计对必须被 turn 包裹，否则重载即 crash-tail，user-approval/src/index.ts:77-85,210-216）。
- 被委派子代理禁问人：agent 非 registry 根 → `DELEGATED_CALLER`；非活跃实例 → `CALLER_NOT_LIVE`（user-questions/src/index.ts:94-107）。
- fail-closed 缺省：无答案者/答案者抛异常/返回词表外的值都归 `'unavailable'`；`'never'` 策略在派发前就拒绝（index.ts:263-268,276-284）。
- 审计成对性只在审批侧：`approval/asked`+`approval/decided` 同 id 恰各一条（types.ts:44-58）；user-questions **无审计事件**，唯一痕迹是 ask_user 工具结果——duo 若要问题审计需自建。
- ACP 答案者无 callId 即 next()（acp/src/index.ts:156），即审计/呈现依赖 callId 关联既有工具卡。

## 对 duo 的启示

duo 现状=审批 seam（终端 y/n / Web 卡片）+ask_user/exit_plan_mode、M19 亲和路由、M9-M11#2 销账。对照三条：

1. **答案者瀑布 vs duo 呈现位路由（M19 亲和）**：DSH 的优先级是「组合顺序 + next() 委托」，并把「不该答」（scope 不符→next）与「答不了」（fail-closed unavailable）分成两条路径；duo 的发起方优先路由可对齐这两态——亲和方不匹配时显式委托而非吞掉，耗尽后明确 fail-closed 而非挂起。
2. **审计事件对**：DSH 以 service 签发 id 强制 asked/decided 一一成对、turn 包裹、unavailable 也记账；duo 销账可引入同构 id 对 + 「提交即记 asked」的先写后决，避免审计孤儿。
3. **两层优先级要分清**：DSH 中答案者优先级（waterfall 顺序）与 UI 卡片优先级（per-session precedence，plan-review>question>approval）是独立机制；duo 若多渠道（终端 y/n 与 Web 卡片并存）宜同样分离「谁有权答」与「先给谁看」。

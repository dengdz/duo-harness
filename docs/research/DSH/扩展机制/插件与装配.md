# 插件与装配（DSH）

> 源锚点：`ddefc45fbc7f8e46dd73185e68295696d1297887`（2026-09-21 本地核验）。M22 探测里程碑工单 15（T-19）产物，五段统一模板。接口参考见 [../模块手册.md](../模块手册.md)；容器机制深析另见 [../插件化架构/](../插件化架构/) 三件套（2026-09-21 已增量补扫至同锚点）。

## 机制全貌

dsh 的装配是「分层 patch + Cordis Loader」：bin 先 `loadLayeredEnv`（继承环境 > 项目 .env > home .env，bootstrap 变量拒收，boot/app-boot/src/index.ts:212-233、apps/cli/src/bin.ts:39），再 `loadProfile` 读 `$DSH_HOME/profiles/<name>/package.json` 的 `dsh.profile.bundles` 有序 bundle 列表（boot/app-boot/src/profile.ts:5-13、135-151），把每个 bundle 声明的 `dsh.bundle.patch` yml 依次叠上 profile 自身与 `--patch` 覆盖层，最后 `boot()`：`new Context`→`ctx.plugin(Loader)`→`prepare`→`mountRootInclude`（根 entry 固定 id `include`，挂 `cordis:include`+`cordis:group` builtin，boot/app-boot/src/index.ts:510-553）→`ctx.get('loader').await()` 等整树落定→`auditStartupEntries` 审计必需 entry（boot/app-boot/src/index.ts:917-983、870-884）。patch yml 四语法：①同 id 覆写（整键替换，include/src/index.ts:120-123）；②`insert` 追加（:79-101）；③`disabled` 停用（可为 `!!js` 表达式，loader/src/config/entry.ts:85-90）；④`!!js`（js-yaml 自定义 tag，求值推迟到 Loader 挂载时 `interpolate(ctx, config)`，loader/src/index.ts:100、config/utils.ts:5-26）。preset 与 bundle 是两级复用：bundle 是 profile 的静态层；preset（packages/preset/agent-presets）是一份 `cordis.yml` 组合，按会话挂在 standing scope 下（mount.ts:369-424），与 patch 层互不覆盖。

## 关键流程

① **层叠序**：`readProfilePatches` 固定顺序 = bundle 层（按 `dsh.profile.bundles` 序）→ profile 的 `cordis.patch.yml` → home 的 `~/.dsh/cordis.patch.yml` → `--patch` 覆盖层 → 遥测旗标派生 patch（boot/app-boot/src/profile-context.ts:63-75）；全部 flatten 后**单次** `applyEntryPatches` 合成（profile.ts:944-951），`--dump-config` 复用同一函数保证所见即所装。bundle 解析双锚点：安装目录优先、profile 目录其次，缺 `dsh.bundle` 声明即 fail loud（profile.ts:856-902）。

② **插件生命周期**：插件=实现了 `apply`/`Service` 的模块；`Service` 构造即 `ctx.reflect.provide(name, self, check)` 并随 fiber 卸载自动注销（cordis/src/service.ts:42-59）。fiber 启动前先同步校验 config，然后跑插件回调/`[Service.init]` 生成器，逐个 yield disposer（include/src/index.ts:245-263）；fiber 状态机 PENDING→LOADING→ACTIVE→FAILED/UNLOADING/DISPOSED（cordis/src/fiber.ts:142-152），PENDING=在等 `inject` 的必需服务，未就绪判定=`Object.keys(fiber.inject).filter(s=>ctx.get(s)===undefined)`（boot/app-boot/src/index.ts:795-800）。disposer 逆序执行、可异步（fiber.ts:69-74）。HMR 串行：所有模块替换与配置重载都进 `runExclusive` 单队列（boot/hmr/src/index.ts:139-147）；配置变更走 `reconcileProfilePatches`（entry.update 原地换 patches、以旧失败为基线只拒绝新引入失败，boot/app-boot/src/index.ts:251-276）；模块变更走 `partialReload`：按依赖图分类 accepted/declined（:351-404）→备份并清除 ESM loadCache+CJS require.cache→重新 import→dispose 旧 fiber→以原 config 重新 plugin（:471-557），失败则 rollback 缓存并回装旧插件（:558-575）；externals 文件变更直接 `loader.exit()` 全量重载（:294-296）。

③ **patch 语义细节**：同 id 覆写是**整键替换**——`config:` 一写就替换整个 config 对象，不深合并，覆写须重述全部需要的字段（include/src/index.ts:120-123）；`insert` 只能追加、不能改既有行；未命中的 patch 仅 warn 跳过（:110-111），但 patch 文件本身不可读/非数组则 fail loud（boot/app-boot/src/index.ts:279-298、344-362）；`!!js` 在挂载时按 entry 自己的 ctx 求值，可访问注入服务与 `process.env`。

④ **plugin-manager**：`writePluginEnabled` 用保注释的 yaml Document 找最后一个匹配 id 的条目改 `disabled`，无则追加，原子写回 0600（boot/plugin-manager/src/patch.ts:14-43）；`setPluginEnabled` 落盘后有 HMR 则热应用，无 HMR 则返回 `restart-required`（boot/plugin-manager/src/index.ts:302-313、546-550）；全部变更包在 `withFileLock(package.json)` 内（:557-591）。

## 接口与参数要点

- 位置约定：profile=`$DSH_HOME/profiles/<name>/`（含 package.json、`cordis.patch.yml`，profile.ts:50-53）；home patch=`$DSH_HOME/cordis.patch.yml`；bundle patch 路径由 bundle 自己的 manifest 声明。模块解析还维护 `profiles/node_modules` fallback（profile.ts:571-606）。
- 旗标：launcher 只认 `--profile`（可缩写为位置参数）、可重复 `--patch`、`--dump-config`/`--dump-default-config`（互斥），其余 argv 原样传给树内 `cmdlineArgs` 服务（apps/cli/src/args.ts:10-140、boot/cmdline/src/index.ts:84-89）。
- 配置校验：StandardSchema 在**每个 fiber 启动前同步**执行，不支持异步校验，失败抛 ValidationError（cordis/src/fiber.ts:50-62）；`!!js` 内联表达式不受 schema 约束。

## 边界与坑

- patch 覆写=整 config 重述，漏字段即丢配置；`insert` 行与覆写行不可混淆。
- HMR 纪律：disposer 必须可完成且幂等（boot/hmr/src/index.ts:198-204）；预设树禁用 write() 防回写（mount.ts:122-123）。
- 失败方式：patch/配置文件坏=fail loud 拒启；但热重载中配置坏只 warn 并保留运行树（include/src/index.ts:279-287）；启动审计里必需 id（agent-loop/webserver 等，:691-699）落定失败抛 `StartupError`，可选 entry 仅 warn。
- 稳定判定=`loader.await()` 全树落定 + `inactiveEntries` 审计，而非固定超时（:955-957、769-807）；`installFailLoud` 兜住启动窗口后的 unhandledRejection（:633-673）。
- **架构级变化（b150a551→ddefc45f）**：loader/include 事务回滚机制整体移除——失败从「回滚保旧」变为「log-and-continue + boot 必需清单终审」（三件套补扫结论）。

## 对 duo 的启示

duo 现状是 M1 自研插件容器：`Boot.from(yml)` 一次性引导、单层 yml 行装配、`awaitStartup` 等待；M18 加了 awaitStartup 超时。对照三条：

1. **层叠 vs 单层**：DSH 把「bundle 静态层→用户层→旗标层」flatten 后单次 patch 合成，缺省/用户定制/一次性覆盖各有归位，未命中 patch 只 warn 不炸。duo 若仍单层 yml，可借鉴最小形态：内置默认层+用户 patch 层两层、同 id 覆写整键替换的语义写进文档即可，不必先做 insert/!!js。
2. **稳定判定**：DSH 不用超时——`loader.await()` 等全树落定后按「必需 id 必须激活、其余 pending 只列缺失服务清单」审计。M18 的 awaitStartup 超时可改成同构方案：区分「必需插件失败」与「可选插件等依赖 pending」，诊断里直接输出 missing services，避免用统一超时掩盖根因。
3. **HMR 借鉴度低**：DSH 的热重载强依赖 Loader 内部 loadCache/依赖图分类/runExclusive 队列与 dispose 纪律，成本高；duo 热重载是遗留限制 1，短期不必对标，但其「配置坏保留运行树、fail loud 只留给冷启动」的分级策略值得抄。
4. **校验时机**：DSH 在每个插件 fiber 启动前同步做 StandardSchema 校验，失败即该插件 FAILED 而非进程崩；duo 可把 yml 行的参数校验前移到装配时，失败行降级为该插件未激活并进入启动诊断。

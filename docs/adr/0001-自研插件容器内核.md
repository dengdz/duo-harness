# 自研插件容器内核（不用 DI 框架 / ServiceLoader）

Status: 批准

从零构建 Java 版插件化 agent harness（参考 DSH / vendored Cordis，见 `docs/research/DSH/插件化架构/`）。决定自研轻量容器内核，由四个子决策构成：

1. **服务寻址 = 字符串服务名 + 视图接口动态代理**。Context 实例是动态代理，插件用 `ctx.as(XxxView.class)` 取得视图接口（方法名即服务名），不用 `Class<T>` 做服务身份，也不用注解字段注入。理由：保留 DSH `ctx.tools` 手感与开放式扩展（第三方插件自定义视图接口不改核心）；Class 身份与"同服务名多作用域实现"的 isolate 模型冲突。
2. **插件加载 = 同 classpath + 配置声明**。插件类编译期可见，但加载与否、配置、禁用完全由配置树的一行决定；运行期"拔掉"= 逻辑 dispose（effect 逆序回滚），不做类卸载。理由：配置树持有发现权是 bundle/profile 层序合成的前提；Java 类卸载不可靠，逻辑卸载已覆盖插拔语义。
3. **生命周期 = 依赖驱动启停（epoch 复刻）**。插件声明 inject，依赖全就绪才启动、任一消失自动停止、换实现自动重启。不采用一次性拓扑排序或显式 before/after。理由：这是运行期插拔自动传导的前提；boot 顺序零手写。
4. **事件 = 五种分派模式**（emit / parallel / serial / bail / waterfall）一次定稳。waterfall 的洋葱否决语义是工具管线与 `internal/*` 钩子的地基。不拆成"广播 + 独立拦截链"两套机制。

## Considered Options

- **Guice / Spring / CDI 做容器**：生命周期模型与"依赖驱动启停"不匹配，改造成本可能高于自研，且违背最小依赖原则——拒绝。
- **ServiceLoader 自动发现**："发现即全装"与配置合成模型冲突——拒绝，仅可能留作未来装配工具的便利入口。
- **独立 jar + child ClassLoader 真热加载**：类隔离、依赖冲突、卸载泄漏三座大山，首里程碑风险大——推迟，保留为内核扩展点。
- **一次性拓扑排序启动**：运行期禁用服务后依赖方进入未定义状态——拒绝。

## Consequences

- 插件 API 形状全部由本决策派生（as() 视图、inject 声明、effect 注册、五种监听签名），后续反转成本高。
- 首个里程碑形态：内核 + 示例插件（含一个工具插件跑通注册→执行全链路），agent 循环 / LLM / Web UI 作为后续插件域叠加。

# M32 立项决策：1.0 收口盖章——纯手续五件定版

Status: 批准（2026-10-02，M32 启动 grill 五问逐题裁定；[ADR-0029](0029-M27至1.0版图重排第二弹.md) 的 M32 节（原 M31 收口，经 [ADR-0033](0033-M31文档官方化立项决策.md) 顺移）范围确认不变——五件照版图定版，本决策记执行裁定）

## 背景

版图对账（启动 grill 首步）：版图定 M32 = 1.0.0 收口期，CHANGELOG 实发最新 0.27.0（M31 文档官方化 2026-10-02 发版，tag v0.27.0 在），两条版本线一致无错位。

实现面 smoke 实测（核对对象逐件过）：

- **文档三层齐备**：站内五段 24 篇（入门 1 / 指南 9 / 高级 3 / 架构 2 / 参考 9）+ 已知限制页全部在位，导航完整——判定第三项核对对象（M31 大改后文档站）成立。
- **终审对象**：backlog 108 行在位，含「1.0 后菜单」约 15 条；发现一处陈账——「03-高级章节」条目仍挂「未实施」勘误注，实际三章已随 0.25.0 交付（CHANGELOG 在案），终审工单内顺手销账。
- **安全基线**：Origin 栅栏（M16）/ 审批钉死（M12 起）/ 沙箱出栈决议（ADR-0023）三项交付均有 ADR 与 CHANGELOG 锚点。

无 M30 式「承诺物理不成立」类阻塞点，五件手续的核对对象全部就位。

## 决策（五问裁定）

### 一、范围：五件照版图定版，纯手续

具名候选终审 / 移出项与 1.0 后菜单终审 / 1.0 判定四项出证据 / 1.x 版本策略声明 / 盖章 1.0.0，零代码改动。理解关卡补考维持「不排期、用户主动发起」（ADR-0029 横切口径），不作为盖章前提。理由：M27-M31 五期已把工程活做完，收口期混入工程活会重演 M31 版号被插单打乱的局面；判定四项现状实测均成立，无增补动因。

### 二、版本策略声明内容：语义化版本 + 按需发版

1.x 内向后兼容（新功能进 minor、修缺陷进 patch、破坏性变更才到 2.0）；发版不排期、按需发；声明带一句对照系惯例说明（ADR-0029 原文「对照惯例：ZCode 主、DSH 辅」）。对照调研在工单期执行一轮轻量核实（两家如何声明版本策略），结论落声明正文与验收档案——本 ADR 落卷后不回填。

### 三、声明落点：README 小节 + 文档站短页 + 本 ADR 记档

README 加一小节（使用者第一入口）；文档站同步一篇短页（版本与发布策略，参考层）；决策理由与取舍随本 ADR 记档。理由：1.0 的承诺是对使用者说的，README/文档站看得见；「决策即档案」纪律不破，且不为一份声明单开 ADR。

### 四、盖章形态：照旧自动化

切 1.0.0 分支 → CHANGELOG 落 1.0.0 段（择要并入判定四项证据结论，ADR-0033 预裁形态）→ tag v1.0.0 → release.yml 自动挂 GitHub Release。不手写公告、不特殊化——发版链路 M30 起两轮验证稳定，CHANGELOG 1.0.0 段本身就是发布说明。

### 五、1.0 后运转：轻量里程碑制延续

后续活从 1.0 后菜单 / backlog 按需挑，每件仍走既有流程（grill → to-spec → to-tickets → 逐工单实现 → 审查 → 验收 → 发版），版本号按语义化版本走。不立新路线图，需要时再议。M32 之后无既定期号，本条为版图终态。

## 拒绝的选项

- **补考清账入 1.0 前提**：约 5-6 门补考变盖章前置，工期拉长且推翻 ADR-0029「不排期、主动发起」裁定。
- **最小声明**（只说按需发版不做兼容承诺）：「1.0」的分量变轻，使用者判断「可依赖」无依据。
- **强承诺**（定期发版/长期支持/废弃预告期）：个人项目维护节奏跟不上承诺，违约风险高。
- **只进 ADR**：使用者看不到承诺，声明形同内部备忘。
- **只进 README/文档站**：决策理由无档案，违背「决策即档案」纪律。
- **Release 公告化**（手写历程摘要）：多一道手工活，CHANGELOG 1.0.0 段已承载发布说明职能。
- **去里程碑化 / 冻结维护态**：前者让审查/验收/记账质量卡点失去抓手；后者让 1.0 后菜单约 15 条长眠，与「按需挑」既定口径冲突。

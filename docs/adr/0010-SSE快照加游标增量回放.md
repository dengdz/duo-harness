# SSE 增量回放：快照先行 + Last-Event-ID 游标

Status: 批准（2026-09-14，M10 grill 裁定）

Web 面的 SSE 事件流在 M8 定案为"每次连接全量回放会话日志 + `replay/done` 边界帧"。本决策给事件帧加上序号游标：首次连接仍全量快照，断线重连经 SSE 标准 Last-Event-ID 只补缺失段，游标无法对齐时全量重发兜底。修正 M8 spec 的全量回放定案；DSH 0.1.5 会话事件流的"快照先行 + seq 游标 + 缺口修复"协议为参照物（[docs/research/DSH/](../research/DSH/)）。

## 背景

M8 全量回放在当时是正确的最简选择：单用户本机、会话短、事件少。M9 之后前提变了——80K token 的合成会话冒烟是真实场景，事件数上千，每次刷新页面或切换会话都要重放一切，且重放期间前端要重新装配全部卡片。会话只会越用越大，全量回放的成本线性上涨且无上限。

游标协议是业界成熟解（SSE 的 `id:` 字段 + 浏览器 EventSource 重连自动携带 Last-Event-ID 是标准机制）。DSH 的会话事件流验证了同一语义：连接时服务端发快照（含投影基线），随后逐条推送带整数 seq，客户端丢弃重复 seq、发现断档则调分页接口修复；其物理通道虽是自研 WebSocket mux + generation 分层，但那是多会话多流产品级架构的产物，协议内核（快照 + 游标 + 兜底）与传输无关。

## 决策

1. **帧序号**：会话事件帧携带 `id:`，取事件在会话日志中的下标（append-only 列表的下标天然是序号，无须新增计数器）；`replay/done`、`run/error` 等非会话帧不带数字 id。
2. **首连快照**：无 Last-Event-ID 的连接保持 M8 行为——全量回放 + `replay/done` 边界帧（前端重建 UI 的既有触发点不变）。
3. **重连增量**：携带 Last-Event-ID 的连接只发下标之后的事件；日志已被治理折叠/裁剪导致游标越界（对不上号）时，退化为全量快照重发——兜底永远正确，宁可重放不可丢事件。
4. **传输维持 SSE**。不引入 DSH 式 WebSocket mux/generation 分层：duo 是单会话单向推送，SSE 原生游标即可获得同等增量语义，少一套连接管理。

## 拒绝的选项

- **维持全量回放**：成本随会话线性上涨无上限；增量是 SSE 标准能力，弃之无益。
- **自研游标协议**（DSH 式 seq 帧字段 + 客户端修复循环）：多一层帧格式与修复逻辑，而 SSE 原生 `id:`/Last-Event-ID 免费提供同语义；DSH 用自研是因为它的 WebSocket mux 上还要复用非事件流，duo 没有这个约束。
- **服务端缓冲增量段**（只保留最近 N 条供补发）：引入"缓冲窗口外游标失效"的新失效模式；会话日志本就全量在内存/文件，直接对号取用更简单。

## Consequences

- SSE 帧格式变更（新增 id 字段）——公开契约变更；`replay/done` 触发语义不变，旧前端行为向后兼容（多收一个 id 字段无影响）。
- 前端 EventSource 零改动获得增量能力（标准重连机制自动携带）；`replay/done` 后的增量帧渲染路径复用既有事件处理。
- fail-closed 语义与本协议独立钉死：触发判据是"是否还存在能看见该审批的连接"，刷新场景（断旧立新）不触发——新连接快照回放中含审批卡片、可继续作答；须消除"旧连接写失败摘除、新连接尚未入列"窗口的误杀路径。
- 会话切换无刷新（消除 location.reload）留待下期——与增量协议、向上分页（DSH 50 条/页参照）是天然一对，届时前端才真正消费"游标续传"的全部能力。

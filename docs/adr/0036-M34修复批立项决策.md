# M34 立项决策：1.0.1 修复批——M33 实测七档缺陷全修

Status: 批准（2026-10-02，修复批启动确认——草案三项默认 + 直排工单经用户确认；1.0 后轻量里程碑制第二期，首期 M33）

## 背景

M33 浏览器实测质量期收口（2026-10-02，用户终验通过）：100 例硬指标达成，坐实 7 档 P2 缺陷（无 P0/P1——安全栅栏六形态 fail-closed 全过、无崩溃/白屏/数据丢失类缺陷），全部有档案、根因假设与修复候选口径（`.scratch/bugs/BUG-20261002-01 ~ 07`）。总报告分级汇总已给五步排期建议；M33 的 13 例阻塞中 8 例被 BUG-01 连带——修复后测试资产可直接复验翻转。

版图对账：CHANGELOG 实发 1.0.0（tag 在），1.x 策略声明在案（缺陷修复进修订号）——1.0.1 为首个修订号，无错位。

实现面核对：七档档案的根因均为「假设 + 待实钉」形态（如 BUG-01 的 null 兜底、BUG-07 的锁释放缺口），工单执行按「假设验证 → 根因实钉 → 修复」三步走，与假设不符先改档案再动手——不阻塞立项。

## 决策（四问确认）

### 一、范围：七档全修 + 两个顺手项，拒绝夹带

BUG-01 ~ 07 全修；O15（发送后 chip 残留）并入按钮/chip 态机单、O17（auth:none 页面横幅）并入小面收尾单。M33 的 13 例阻塞中非 BUG-01 连带的 5 例（设计不可达 4 + IAB 环境限制 1）不在范围——它们是设计形态或环境限制，不是缺陷。理由：1.0.1 纯修复语义（语义化版本口径），夹带新功能会破坏「修订号 = 缺陷修复」的承诺。

### 二、版本与流程：1.0.1 直排工单，跳过修复批 grill

分支 `1.0.1` 随本 ADR 自 main 切出，开发提交不落 main（红线 7）；流程按 ADR-0035 预留口子降级——七档档案已含根因假设与修复候选口径，范围零悬念，跳过修复批 grill 直排工单。工单内小裁定（BUG-06 补注册 or 改文案）单内定并回写档案。

### 三、验收口径：回归锁前置 + M33 阻塞例复验翻转

每档先写回归锁（档案「回归测试」候选已预写）再修；工单 06 做 M33 报告复验——8 例 BUG-01 连带阻塞例翻转记录回填 M33 报告附注，测试资产变成修复验收件。发版收口按 M32 经验档「发版两查」：Release 实查 + main CI 末次 run 绿。

### 四、发版：修完即发 1.0.1

CHANGELOG 逐单记账 → tag v1.0.1 → release.yml 自动挂 Release。不攒不拖——修复批天然是发版单位，1.x 按需发版语义下的标准动作。

## 拒绝的选项

- **修复批捎带新功能/菜单项**：破坏「修订号 = 缺陷修复」承诺，1.x 兼容背书打折。
- **只修不发布**：修复不发布则使用者拿不到，1.0 的质量背书继续悬空；按需发版语义下修复批就是发版时机。
- **逐档开 7 个里程碑**：单档粒度过碎，流程开销吞掉修复本身；七档共享一个修复分支一次验收一次发版。
- **修复批走完整 grill**：范围与排期已在 M33 总报告定调、档案已含修复口径，grill 无新决策点——ADR-0035 预留的降级口子正是为此。
- **顺手项单开工单**：O15/O17 均为单点小改，挂靠对应缺陷工单（态机/小面收尾）成本最低。

## Consequences

- 分支 `1.0.1` 自 main 切出（2026-10-02）；M33 报告/spec/cases 状态已在 main 定稿（收口提交 03f4584a），本分支承接修复与回归。
- 七档修复涉及产品代码变更——每单提交前核对（调试残留 grep / CHANGELOG 记账 / 档案 Status 流转）恢复全量执行。
- M33 报告的 13 例阻塞例在工单 06 复验后回填附注（翻转与否如实记）；回归锁随修复入库，成为 1.x 永久资产。
- BUG-06 的路线裁定（补注册 vs 改文案）与 BUG-07 的泄漏缺口实钉结果回写对应档案 Comments。
- 发版后 limitations 页随修复回写「已修复」状态与总报告「新发现」4 条的核实结果（工单 06 内执行）。

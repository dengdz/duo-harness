# MCP 接入采用官方 Java SDK，隔离在实现层

Status: 批准

duo-harness-mcp 模块接入 MCP 服务器。自写协议实现（JSON-RPC 编解码、stdio 帧协议、初始化握手、能力协商、工具列表变更通知）工作量数倍且易错，且协议胶水不是本项目的核心价值——核心是"远端工具 ↔ 本地工具域"的适配与生命周期管理（同步、命名、重连、失败语义）。决策：采用官方 `io.modelcontextprotocol.sdk:mcp:0.10.0`（nexus 已确认可取，经用户同意引入），SDK 严格隔离在 duo-harness-mcp 的 internal 层，不渗透契约——对下游与 tools 服务而言，MCP 工具与本地工具毫无区别。

## 拒绝的选项

- **自写协议实现**：学习价值最高，但协议面大（传输/握手/通知持续演进），跟随 MCP 规范升级的维护成本长期高于 SDK 依赖；且自写的质量风险直接暴露给用户（协议边界 bug 难查）。
- **推迟 MCP 到 M3+**：MCP 工具是工具域强化件（output 契约、审批）的真实消费方，拆开交付削弱强化件的存在意义。

## Consequences

- duo-harness-mcp 引入 SDK 传递依赖树（工单 01 实现时核实其携带的传递依赖，若带入与轻量原则冲突的重依赖，评估 exclude 或显式接受并记录）。
- MCP 协议演进跟随 SDK 官方版本升级（升级成本 = 适配层改动，非协议重写）。
- stdio 传输优先交付；HTTP 传输利用 SDK 的可替换传输层后置补齐，不锁死。

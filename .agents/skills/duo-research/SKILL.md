# duo-harness 参考项目研究

目的：把对参考项目的分析变成持久资产——研究一次、落盘一份，后续会话直接读文件，不重新扫描源项目。分析对象用项目别名指代（如 DSH = deepseek-harness），别名与路径注册在 [docs/research/index.md](../../../docs/research/index.md) 的项目注册表。

## 两档粒度

| 你说 | 产出 |
|---|---|
| "看一看 DSH"（未指定功能） | 项目总览单文件 `docs/research/<别名>/总览.md` |
| "看一看 DSH，XXX 功能" | **功能深析三文件**（本 skill 主流程，见下） |

## 功能深析流程

1. **拉最新 + 记锚点**：`git -C <本地路径> pull --ff-only`（失败时报告原因，不擅自 rebase/merge），记录 `git rev-parse HEAD` 作为版本锚点——分析结论只对该锚点负责。
2. **查索引**：读 [docs/research/index.md](../../../docs/research/index.md)。
   - 该功能已有三件套且锚点一致 → **直接复用文档**，本次结束（这就是"不重扫"）
   - 锚点落后（源有新提交）→ 对新差异做增量补扫，更新锚点与索引状态
   - 无条目 → 继续下一步
3. **定位功能边界**：先派 Explore 子代理摸清该功能在代码里的落点——入口、模块边界、涉及的文件清单。确认"这个功能是哪几块代码"之后再深挖，不盲目全库扫。
4. **三路深挖**（一个或多个子代理；每条结论必须带 `文件:行号` 出处，读代码核实、不信 README 转述）：
   - **架构**：模块划分、核心类与接口、数据流向
   - **代码**：关键实现逻辑、重要方法、依赖关系
   - **细节**：配置项、边界条件、异常处理
5. **落盘三文件**到 `docs/research/<别名>/<功能名>/`：

   | 文件 | 固定结构 |
   |---|---|
   | `架构设计.md` | 源锚点 → 功能一句话 → 模块划分 → 核心类与接口（职责表）→ 数据流向 |
   | `代码说明.md` | 源锚点 → 关键实现逻辑（按流程分节）→ 重要方法（签名 + 做什么 + 位置）→ 依赖关系（依赖谁 / 被谁依赖） |
   | `细节备忘.md` | 源锚点 → 配置项（名 / 默认值 / 作用）→ 边界条件 → 异常处理（类型 / 触发 / 处理）→ 已知坑 |

6. **登记 + 记账**：index.md 功能条目表加一行（别名 / 功能 / 文档位置 / 锚点 / 状态）；CHANGELOG 记账；提交走 duo-workflow 的提交前核对。

## 消费规则（写给后续会话）

- 需要参考该功能时**直接读 `docs/research/<别名>/<功能名>/` 三件套**，不重扫源项目
- 索引状态列标"源已更新"时，先拉最新再增量补扫，并更新锚点
- 分析中确定的"我们要采纳 XXX"不在分析文档里发酵——按 domain 规则记 ADR：分析文档记事实，ADR 记决策

## 复盘维度

任务收尾调用 duo-skill-evolution 复盘时（AGENTS.md 红线 8），本技能按以下口径收集输入：

- 任务摘要：研究的项目与功能、生成的文档数量、关键发现
- 执行过程关键点：功能边界定位是否准确、代码分析是否深入、三件套是否完整、出处引用是否准确
- 用户反馈：用户对分析深度、文档质量、可操作性的反馈
- 自我感知：流程中是否有遗漏环节、分析粒度是否合适、可优化点

## [2026-09-21] 注册第二参考项目 ZCode：新目录惯例与历史文档路径的冲突

**问题描述**：
SKILL.md 新增"对照文档落 `docs/research/<别名A>+<别名B>/`"目录惯例时，既有对照文档（`docs/research/subagent-派发与提示词对照.md`）平铺在根目录，二者形态不一致，曾考虑把旧文档迁入新目录。

**原因分析**：
旧文档已被 ADR-0016 / ADR-0017 与 .scratch 历史记录按当时路径引用，迁移会破坏 ADR 链接稳定性（ADR 是决策记录，引用应保持当时形态）。

**解决方案**：
不迁移旧文档；SKILL.md 明确"新对照文档走新目录，既有平铺先例因被 ADR 引用路径稳定不迁移"。以后凡要迁移已被 ADR / 工单历史引用的研究文档，默认豁免，新惯例只约束新文档。

**影响范围**：
所有涉及 docs/research/ 文档移动的场景；索引条目的文档路径列同步以实际落盘为准。

## [2026-09-29] 研究文档的「模仿开发可用性」：锚点之外要抄录可移植定义与目标库映射

**问题描述**：
M29 工单 05 产出两篇 ZCode UI 形态研究后，用户审查「是否支持后续的模仿开发」——发现文档给的全是「源码在哪」（文件:行锚点）而非「长什么样、怎么抄」（可移植 CSS 定义、目标项目 token 映射），实现者模仿时仍要回参考项目源码逐段挖。

**原因分析**：
研究文档默认读者是「理解机制的人」，锚点即回溯路径；但 UI 形态研究的消费方是「照着做的人」，需要落地素材本身——扫光 keyframes 渐变色标、动画时长精确值、token 对照这类「抄录级」细节。锚点可回溯 ≠ 可直接执行。

**解决方案**：
形态/样式类研究文档的「对 duo 落地清单」按模仿开发标准补三层：①可直接移植的完整定义（CSS 全文抄录、动画参数精确值，不是「见 :823-842」）；②目标项目 token 映射表（参考项目语义 token → 本项目现状的四类处置：直映/近似映射/需新增/待议）；③参照来源分工声明（哪些交付物以本研究为参照、哪些另有来源，防实现者找错参照）。补强方法 = 以实现者视角逐工单对照「实现所需 vs 文档已有」。

**影响范围**：
所有 UI/样式类研究产物（M29 工单 06/07/09/10 直接消费本批附录）；后续「研究 → 模仿开发」类工单的产出标准。

## [2026-09-21] 离线 pull 的锚点一致性惯例 + 注册表元数据亲核

**问题描述**：
（1）两家仓库 `git pull --ff-only` 因 github.com 离线双双失败，SKILL 只规定"失败时报告原因"，未规定能否继续分析；（2）Explore 负结论暴露注册表元数据错误——DSH 注册标"Java"，实为 TypeScript monorepo（全仓 0 个 .java），此前历次研究未核证过该标注。

**原因分析**：
（1）pull 的目的是"锚点新鲜"，离线时若本地锚点恰与索引登记一致，分析有效性不受损——缺的是这条判定惯例；（2）注册表的语言/形态描述是写下时的快照，无人复核过。

**解决方案**：
（1）离线 pull 失败时：报告原因 → 对比本地 `rev-parse HEAD` 与索引登记锚点 → 一致则继续并在文档头注明"离线，锚点与登记一致"；不一致则停止并挂账待补扫。（2）凡引用注册表元数据做结论（语言、形态、版本）前，以一条廉价亲核命令验证（如 `find -name "*.java" | wc -l`）；错误随发现随手修正并在文档中留痕。

**影响范围**：
所有网络受限环境的调研；注册表元数据被下游 ADR/文档引用前。

## [2026-09-21] 大规模「全面探查」请求的分批模式

**问题描述**：
用户要求对参考项目做覆盖功能/结构/设计/UI/路由的全源码探查——一次全库扫会失焦，逐功能深析又不成体系。

**原因分析**：
「全面探查」的合理粒度是**维度**而非功能：按维度（代码结构与模块划分 → 核心功能与业务逻辑 → 整体设计与架构风格 → UI 界面与组件 → 页面路由与交互流程）划批次，每批双项目并行派 Explore（报告中密锚点、限字数、禁贴大段代码），批间汇报、末批汇总成各项目「总览」单文档。

**解决方案**：
固化五批次模板与总览文档结构（一句话定位 + 五节 + 总体评价三标签/最可借鉴/最重负担）；已有同项目旧总览且锚点过期时，全景探查顺带完成增量补扫（重写总览、更新索引锚点，不另立平行文档）；每域已有专册的（如沙箱与权限）在总览中只标位置不重复展开。

**影响范围**：
"全面探查/整体看一看 X 项目"类请求；总览文档的维护策略。

## [2026-09-30] 锚点漂移的处置分流：复用文档先补扫，当场实读直接换锚

**问题描述**：
M29 工单 12 验收对比时 `pull --ff-only` 拉进新提交（872ad96 → 29628c9），且上游发生目录迁移（ToolCallBlocks 从 components/ai-elements/ 迁至 src/ToolCallBlocks/）——SKILL.md 规则「锚点漂移时先停下报告」照做会打断用户显式要求的当场对比。

**原因分析**：
「先停下报告」是为防"旧文档结论被当现状转述"；但任务本身是源码实读时，结论将直接对新锚点产生，不存在陈旧转述风险。两类场景未区分。

**解决方案**：
分流——①任务=复用既有文档结论：锚点漂移即停，先增量补扫更新文档与索引再引用；②任务=当场实读（对比/验收/新研究）：直接以新 HEAD 为锚记录并继续，事后在 walkthrough/索引标注旧文档锚点已落后（本次即如此：新锚 29628c9 已记档，工单 05 两篇文档标"待增量补扫"）。

**影响范围**：
duo-research 流程第 1 步（锚点核对）的执行口径；已漂移未补扫的文档：呈现与UI/交互组件形态.md、消息渲染与面板形态.md（锚点 872ad96，行号/目录路径需校正）。

## [2026-09-30] 模仿开发落地的验证口径：computed 探针 + 重复定义排查

**问题描述**：
子代理 8 色落地时按"CSS 只有 0-5"的判断新增 6/7 定义，探针验证发现 6/7 渲染色与定义不符——文件另一处存在旧 6/7 重复定义（theme.css:490），级联在后覆盖新值。

**原因分析**：
「某类缺失」的判断来自局部 grep/窗口阅读，未全文件查重；且落地验证只看了"源码改没改"，没看"浏览器实际算出什么"。前条经验（2026-09-29 模仿开发可用性）解决了"抄录级细节"，没解决"抄完怎么验"。

**解决方案**：
UI 落地验证固定两步：①改样式前对目标类名做全文件 grep（重复定义/级联覆盖排查）；②重启实例后用 computed 探针（临时元素 + getComputedStyle）验证实际渲染值（颜色/字号/动画名），不凭源码推断。探针法本轮同时验证了扫光动画名、todo 三态、8 色值，一次脚本全覆盖。

**影响范围**：
所有「研究 → 模仿开发」场景的验收步骤；浏览器端验证优先用探针脚本而非截图目测（截图看布局，探针看值）。

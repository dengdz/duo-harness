# 单元测试与安全规约规则细则

> 本文件包含阿里巴巴Java开发手册中单元测试和安全规约的完整规则条目。
> 当审查代码涉及测试代码或安全相关逻辑（权限、敏感数据、SQL、密码）时加载本文件。

## 三、单元测试

| 编号 | 等级 | 规则 |
|------|------|------|
| UT-01 | BLOCKER | 好的单元测试必须遵守AIR原则：Automatic（自动化）、Independent（独立性）、Repeatable（可重复） |
| UT-02 | BLOCKER | 单元测试应该是全自动执行的，且非交互式的。测试用例通常是被定期执行的，执行过程必须完全自动化才有意义 |
| UT-03 | BLOCKER | 为了保证单元测试稳定可靠且便于维护，单元测试用例之间决不能互相调用，也不能依赖执行的先后次序 |
| UT-04 | BLOCKER | 单元测试不能依赖外部环境（如数据库、网络、中间件等），应使用Mock方式 |
| UT-05 | BLOCKER | 单元测试是可以重复执行的，不能受到外界环境的影响。反例：本次测试结果依赖上次测试产生的数据 |
| UT-06 | BLOCKER | 对于单元测试，要保证测试粒度足够小，有助于精确定位问题。单元测试粒度最高是类级，一般是方法级 |
| UT-07 | BLOCKER | 编写单元测试代码遵守BCDE原则：Border（边界值测试，如循环边界、特殊值、异常值）、Correct（正确的输入，并得到期望的输出值）、Design（与设计文档相结合，理解业务场景和代码设计意图）、Error（强制错误信息输入，如网络异常、非法参数等，得到预期的异常处理结果） |
| UT-08 | BLOCKER | 和数据库相关的单元测试，可以设定自动回滚机制，不给数据库造成垃圾数据。或者使用内嵌数据库（如H2）替代真实数据库 |
| UT-09 | BLOCKER | 对于不可测的代码建议做必要的重构，目的是为了使代码变得可测，同时避免重构引入新问题 |
| UT-10 | BLOCKER | 在设计评审阶段，开发人员需要和测试人员一起确定单元测试覆盖范围 |
| UT-11 | CRITICAL | 单元测试作为一种质量保障手段，不应在项目发布后补充，应在项目开发过程中同步编写 |
| UT-12 | CRITICAL | 测试方法命名规范：`test[被测方法名]_[测试场景]_[预期结果]`（如`testGetUser_whenUserIdIsNull_thenThrowException`） |

## 四、安全规约

| 编号 | 等级 | 规则 |
|------|------|------|
| S-01 | BLOCKER | 隶属于用户个人的页面或者功能必须进行权限控制校验 |
| S-02 | BLOCKER | 用户敏感数据禁止直接展示，必须进行脱敏处理（如手机号中间4位用*替换，身份证号出生年月日用*替换） |
| S-03 | BLOCKER | 用户输入的SQL参数严格使用参数绑定或者METADATA字段值绑定，防止SQL注入，禁止直接拼接SQL语句 |
| S-04 | BLOCKER | 用户请求传入的任何参数必须做有效性验证（如长度、范围、格式等），防止绕过前端校验直接请求后端接口 |
| S-05 | BLOCKER | 禁止向HTML页面输出未经安全过滤或未正确转义的用户数据 |
| S-06 | BLOCKER | 表单、AJAX提交必须执行CSRF安全过滤 |
| S-07 | BLOCKER | 在平台配置文件中使用的密码、密钥等信息应该进行加密存储，严禁明文存储 |
| S-08 | BLOCKER | 在微服务架构中，服务间调用的敏感参数应加密传输 |
| S-09 | BLOCKER | 后端响应数据中包含敏感信息时，必须进行脱敏处理后再返回 |
| S-10 | BLOCKER | 禁止在日志中打印用户敏感信息（如密码、身份证号、银行卡号等） |
| S-11 | BLOCKER | 密码必须使用不可逆的加密算法（如BCrypt）存储，禁止使用MD5/SHA等可被彩虹表破解的算法 |

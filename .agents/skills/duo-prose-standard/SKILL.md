# duo-harness 文档写作规范

文档写到刚好保住契约为止，然后删掉推理过程、重复和装饰。契约是调用方、被调方、实现者、生产者或消费者所依赖的义务、不变量、前置条件、后置条件或兼容性承诺。注释只说代码本身表达不了的非显而易见契约或理由，不复述代码已经隐含的内容。

本 skill 是指导原则，不是脚本。与 duo-doc-standards 配合使用：后者管位置和层次，本 skill 管质量。

## 输入与排除

必须有明确的 `scope`。缺失时报告缺少什么输入然后停下；不要自行推断范围，也不要反过来盘问用户。

接受 `mode: automatic | interactive`，默认 `automatic`。仅当用户明确要求提问或校准时进入交互模式。

`mode` 只控制是否提问，不控制写入权限：审查和审计类任务只报告发现、不动文件；用户明确要求写入、修复或修剪时才执行修改。

始终排除 `target/` 等构建产物，不跟随指向它们的符号链接。排除 glob 要放在包含 glob 之后，避免后面的包含规则把排除项又放回来。如果范围内只有构建产物，直接报告"没有符合条件的文件"。

生成的 API 目录、快照、测试夹具（fixture）都是衍生品：先改源头（所属源码或场景），再重新生成，不直接编辑生成物。

## 保留完整命题

下笔前先数清段落里的每个命题，以下内容逐项保留：

- 主体（谁）与动作（做什么）
- 条件、时机与顺序
- 必须、可以、禁止这类情态词
- 否定性保证与例外
- 所有权、副作用、失败模式和后果

只有当每个事实分句都存活、且改后确实更清晰时，才删形容词、重复和叙述；单纯减字数不算改进。

在使用现场保留完整的局部契约——调用者或维护者在这里需要知道的行为、失败方式、所有权和后果。架构、理由、算法、历史、扩展示例这类深水内容，链接到归属文档，不要复制：一个解释只有一个家；基本的契约事实允许在本地重复。

省略某个理由会导致误用或被错误简化时，把理由留下来；否则只陈述后果，并链接到解释它的文档。

## 各位置的必需覆盖

本规范不是单向压缩：代码、类型和结构表达不了下述契约时，要补文档或找回被删掉的文档；反过来，事实在局部一目了然时，不要加注释。

- **公共 JavaDoc**：写清调用者可见的全部契约——返回值差异、抛出的异常、副作用、资源所有权、时序、取消行为、持久化影响
- **内部注释**：为非局部结构和复杂局部结构导航：不变量、竞态顺序、所有权、安全边界、意外失败行为；删掉控制流复述和代码复读
- **模块注释**：说明模块的角色、依赖、职责和非显而易见的架构决策；架构决策链接到它的归属解释
- **测试**：只解释看不出来的测试设计——为什么要这个夹具、这条断言、平台适配、真实入口路径或间接观察；删掉步骤走查和清单式复述
- **README**：覆盖消费者契约：配置、语义、失败模式、限制、扩展点。引用稳定的用户可见文案，细节链接到归属文档；长期存在的差距和维护者陷阱要保留，普通清理任务清单不要放这里
- **示例和配置注释**：解释访问限制、看不出来的连接或加载顺序、安全立场、重放行为、异常与常见误用；配置自己已经显示的条目不要复述
- **提示词和可见字符串**：措辞就是行为——改动后要检查真实产生的输出
- **诊断信息**：点明失败的主体或路径、违反了什么规则，不显然时给出纠正方法；删掉内部执行过程的叙述

机制名称保持可搜索；承担情态、时序、否定语义的强调保留不动，只统一装饰性强调。

## 工作流程

1. 确认范围、模式、当前分支和适用的 AGENTS.md 文件
2. 判断段落之前，先读它所属的代码或文档
3. 覆盖整个请求范围，不要只盯最大的文件：先用搜索和字数筛出候选，再逐个语义判断
4. 给每个候选定去留：保留、补写、修剪、恢复、重组或暂缓。只有任务授权编辑时才动手；不要为了凑删除指标而制造改动
5. 先改源头，再重新生成衍生品。学到新规则后，回头用同样的标准复查范围内类似的段落
6. 跑与改动相关的最窄检查、`git diff --check`，以及可见字符串的行为测试；确认最终 diff 里没有 `target/` 路径。发现意外的构建产物匹配要如实报告，不要声称排除历史干净
7. 报告：检查范围、执行的修改、刻意保留的部分、暂缓的案例、实际跑过的检查

## 边界决策

只有当两个以上版本都能满足完整命题规则、差别在于本 skill 尚未裁决的原则权衡时，才算边界案例；存在唯一保命题答案的改写不是边界案例。

自动模式：授权范围内直接执行明确的编辑，真正的边界案例如实报告但不提问；不要为了推进任务而削弱命题。

交互模式：把同类段落归到同一原则下处理；每类给出两三个可行版本，推荐其一，说明事实或结构上的差异；不要放凑数的劣质选项。

用户拍板后，把原则和版本提炼成示例（不含 PR 历史和审查叙述），并用学到的规则复查范围内所有同类段落。

## Java 项目特定指导

### JavaDoc 标准

- **公共 API**：必须有完整的 JavaDoc；`@param`、`@return`、`@throws` 按成员实际具备的项提供——void 方法没有 `@return` 是完整而非残缺。形式标签服务于上面的契约清单，不反向硬凑。
- **包级文档**：每个包应有 `package-info.java` 描述包的职责和主要类型
- **线程安全性**：明确说明类或方法是否线程安全
- **依赖政策**：引入任何外部依赖前必须向用户说明理由并获得确认

范本形状（每个要素都服务于调用方的使用决策）：

```java
/**
 * 等待首次启动完成：依赖未就绪时阻塞至激活或失败；已失败则重抛原始错误（保留栈）。
 * 只覆盖首次启动；运行期的卸载与重启经状态事件观测。
 *
 * @throws PluginException 插件启动失败（cause 保留原始异常），或等待被中断
 */
void awaitStartup();
```

@throws 写明何时抛与 cause 里有什么、否定性保证（"只覆盖……"）划出方法不管的事、失败模式（"保留栈"）说明异常的形态——调用方能否正确使用，取决于这三件事都在场，而不是标签数量凑齐。

### 代码注释原则

- **Why, not What**：注释解释为什么这样做，不是在做什么（代码已经说明了）
- **不变量注释**：涉及核心不变量（序列号连续性、所有权、生命周期）的代码应注释保持的不变量
- **超时分层**：涉及超时的代码应说明是哪一层的超时（HTTP、模型调用、工具执行）
- **跨模块契约**：模块间调用的参数和返回值契约必须清晰

### Markdown 文档

- **代码示例**：必须是可运行的完整示例，包含必要的 import 和错误处理
- **版本信息**：API 契约的兼容性起点用 `@since` 标注；用户可见变更的记账走 CHANGELOG（版本唯一锚点）——两者分工不同，不在两处重复叙述同一条变更
- **已知限制**：文档应诚实说明当前限制，不过度承诺

## 验证

- 编译验证 JavaDoc 语法（如 `mvn compile`）
- 提示词和错误消息的更改应通过相关测试验证输出（Markdown 链接校验归 duo-doc-standards 的验证节）

## 常见问题

### 何时添加注释？

- 非显而易见的算法或数据结构选择
- 性能考虑或优化
- 并发控制和线程安全保证
- 与外部系统的集成点
- 已知的局限或未来改进方向

### 何时删除注释？

- 重述代码已经清楚表达的内容
- 过时的注释（代码已变但注释未更新）
- 推理过程和决策历史（应移至 Git commit 或设计文档）
- 审查反馈痕迹（"根据 XX 建议修改为..."）

### JavaDoc vs 内联注释？

- **JavaDoc**：公共 API 契约，调用者需要知道的一切
- **内联注释**：实现细节，维护者需要理解的非显而易见逻辑

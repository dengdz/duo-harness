# 应用 duo-harness 文档规范

文档规则活在 `docs/index.md`（建立后）的导航结构与各篇自身。本技能覆盖放置、结构分类、全库文档审计与验证。**它是指导，不是脚本**；编辑判断（该保留什么、删什么）用 [duo-trim-cot-leakage](../duo-trim-cot-leakage/SKILL.md)；**永远不要把长度本身当缺陷**。

## 目标结构（docs/ 建立前的默认方案）

沿用五章节骨架：01 入门 / 02 指南 / 03 高级 / 04 架构 / 05 参考。`docs/index.md` 为导航唯一入口；`README.md` 只做"摘要 → 详情"的门面，不承载细节——审计时先确认它是否真的存在：未建 README 时，门面职责落在谁身上（CONTEXT.md 兼任或显式决定暂缺）要是一个记录过的决策，规范不默认它已存在。已知限制类内容有唯一清单（如 limitations.md），任何"暂不可用/未接线"的表述以它为准。docs/ 立起后如调整结构，同步更新本节与 index.md。

## 文档网站（VitePress + GitHub Pages，ADR-0005）

`docs/` 同时是文档站的源目录：站点由 VitePress 构建、push main 时 GitHub Actions 自动部署到 `https://dengdz.github.io/duo-harness/`（配置在 `docs/.vitepress/config.mts` 与 `.github/workflows/docs.yml`）。

- **上站范围**：五章节正式内容 + limitations + adr；内部开发文档（`docs/agents/`、`docs/research/`）经 `srcExclude` 排除不上站——指向它们的 markdown 链接在站点上是死链，构建配置以 `ignoreDeadLinks` 显式容忍（有意取舍）
- **新增篇章或 ADR 后（硬性）**：同步更新 `config.mts` 的 nav/sidebar 对应分组——**ADR 也算**（sidebar 的"决策记录"分组是手工维护的条目列表，新 ADR 落盘但 config.mts 未加条目 = 站上导航不可见，0.2.0 曾因此漏了 ADR-0006）
- **本地预览**：`cd docs && npm run docs:dev`（需 Node）；改动发布以 push main 为准，CI 自动构建部署
- **构建验证**：结构或导航变更后跑 `npm run docs:build` 确认无死链阻断再提交

## 先结构，后文字

对范围内每篇文档按此顺序检查（历史 ADR 不适用结构改造；新建 ADR 的最小骨架：Status / 决策与理由 / 拒绝的选项 / Consequences——骨架齐全才算立卷）：

1. **定位**：文档在 docs/ 树中的位置是否匹配其主题？入口（index.md 导航表）是否有它的链接？
2. **详略分层**：本篇保留自身主题的完整细节；直接子主题按"目的 + 职责 + 高层行为"摘要并链接到拥有它的篇章。反例：入门篇里深入讲运行时语义（属于对应参考篇）。
3. **体裁分类**（按用途，不按路径或标题）：
   - **教程**（01/02 章）：带领读者按顺序完成可观察的结果；必须可照抄运行。
   - **参考**（05 章）：在明确范围内支撑查阅，不要求顺序阅读。
   - **原理**（04 章）：解释为什么这样设计；假设读者已会用。
   一篇文档混两种体裁且都很重 → 拆分；轻量次体裁 → 明确标注的小节。目标章节尚未建成时（如 05 参考缺席），内容可暂居最近的建成章节，但必须标注"暂代 X 章职责，建成即迁"——未标注的代管按体裁混杂处理。
4. **教程递进**：暗自确定起点读者（初学者/中级/高级），每个概念追溯其前置，超前材料后移。

放置成本检查：

- **移动是原子的**：从旧位置删除、在新位置添加、**同一个变更内修复所有入链**（`grep -rn "旧路径" docs/ README.md`）。
- 手写目录/清单（事件表、配置表）与权威来源重复时，保留一处，其余链接过去。行为语义（状态机、分派模式、管线段）的权威是源码 JavaDoc 与 ADR——架构文档保留"一句话语义 + 链接"即可，逐条展开等于双家维护，改代码要同步两处。

## 全库文档审计

结构检查后，用最便宜的探针先：

1. **度量**：`find docs -name "*.md" | xargs wc -l | sort -rn | head -10` 找异常值；超出同类篇幅一倍以上要有明确理由（参考表类文档天然长）。
2. **猎捕思维链泄漏** —— 用 [duo-trim-cot-leakage](../duo-trim-cot-leakage/SKILL.md)：变更叙述、死引用、审查过程记录、流程复述。文档里最常见的形态："如前所述"、审查轮次引用、"本次重构后"、"状态更新"字样（变更叙述的变体）、本地工单/issue 编号引用（编号指向 `.scratch` 等本地档案，仓库读者不可达）。
3. **猎捕重复**：对特征短语 `grep -rn "短语" docs/ README.md`。同一行为说明只留一个家，其余替换为链接。`TODO(docs 成形后):` 补记易重复点清单。
4. **数字与代码对账**：测试数、示例数、版本号、API 签名——从源码重新数，不信文档转述。
5. **结构对账**：最近的提交动了包结构、模块或公共 API 时，检查架构段落、教程里的包路径、配置示例中的类名字符串（如 yml 里的插件 FQCN——编译器不查字符串引用，漏改只在运行时爆）是否同 diff 更新。
6. **导航对账**（文档站专检）：`config.mts` 的 nav/sidebar 条目与 `docs/` 实际 md 文件双向对账——docs/ 下有文件而 sidebar 无条目 = 漏同步（导航不可见）；sidebar 有条目而文件不存在 = 死链。重点核对 adr/ 目录：ADR 文件数应等于 sidebar"决策记录"分组的条目数。push main（触发部署）前必查。
7. **状态三档标注**：功能描述必须落在正确档位——门面可用 / 底层可用需手动组装 / 已定义未接线（对照已知限制清单）。把未接线功能写成可用是 blocker 级错误。同一文档内多处状态标注（头部状态行、表格行内的"规划/建设中"标记）必须互相一致——自相矛盾的状态字段是新鲜度欠账最直接的信号。

## 验证

- 内部链接：抽查（或全量脚本）每个相对链接指向的文件存在；相对链接必须从**链接所在文件**的位置解析——从仓库根或 docs/ 根解析会把跨层链接全部误报成断链。`docs/` 内链接用相对路径。
- 代码示例：出现在文档中的 Java 片段，其 API 签名对照源码核实（类名、方法名、参数顺序、构造器参数个数）。
- 改了功能描述 → 对应源码行为核对 + 相关测试名核对。

## PR 卫生

文档变更的报告应给出：改了哪些篇、为什么、行数变化、发现并修复的入链。纯文档变更不需要跑测试，但**引用了 API 的示例代码变更**需要编译级别的核对。

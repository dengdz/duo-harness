# duo-bug-ledger：bug 留存台账

bug 修完不等于结束——**没留存的 bug 一定会以另一种形态复发**。本技能把每个 bug 变成组织记忆：台账一条记录 + 防复发措施落地 + 阶段收官回顾。

与 `diagnosing-bugs`（mattpocock）分工：它管诊断与修复的**过程**；本技能管修复后的**留存与复用**。修复完成、commit 之后走本技能。

## 台账位置与条目格式

台账唯一权威：`.scratch/bug-log.md`（git 入库、不上站）。**新条目插在台账头部**（最新在上）。

每条记录按此模板（ID 规则：`BUG-<日期yyyymmdd>-<当日序号两位>`）：

```markdown
## BUG-<日期>-<序号> · <一句话标题>

- **日期**：yyyy-mm-dd（发现于哪个里程碑 / 哪张工单 / 谁发现：用户验收 or 开发自测）
- **症状**：用户/测试看到的现象（原样引用报错或输出片段，不转述）
- **根因**：为什么会发生（机制层面的解释，不是表面原因）
- **修复**：改了什么（文件/行为层面）+ 关联 commit
- **防复发**：具体措施——回归测试名 / 文档更新 / 技能规则更新 / 无（说明为什么可以没有）
```

登记纪律：

- **症状必须原样引用**（报错原文、日志片段），不写"报错了"这种转述——下回排查靠它模式匹配
- **根因写到机制层**（"X 被 Y 覆盖"），不写到操作层（"我改错了"）
- **防复发必须具体可核查**（"新增测试 XXX"），"以后注意"不算

## 修复 bug 后的三步（提交前完成）

1. **登记台账**：按模板追加条目。提交 bug 修复的同一 diff 内包含台账更新（与 CHANGELOG 记账同纪律）。
2. **防复发三问**（逐条回答，落到条目的"防复发"栏）：
   - 有回归测试锁住这个 bug 吗？（在正确 seam 上、能抓到这个具体 bug）
   - 是不是暴露了某个"mock 验证不到、真实环境才现形"的差距？（是 → 验收对照表要不要补真实场景）
   - 是不是暴露了某个流程/技能规则缺口？（是 → 更新对应 SKILL.md，如 duo-acceptance / duo-code-review）
3. **查同族**：`grep` 台账已有条目，看是否同根因复发——同根因第二次出现说明防复发措施没落实，升级处理（加结构化防线的代码，而不是再修一次）。

## 阶段收官回顾

每个里程碑验收收官时（duo-release-workflow 第五步前后），扫一遍台账：

- 本阶段新增条目里，"防复发"栏是测试的 → 确认测试还在套件里跑
- 跨阶段仍存在的条目（如 M2 的限制延续到 M4）→ 确认 docs/limitations.md 有对应表述
- 高频根因（同类根因 ≥2 次）→ 提升为 spec 级决策或结构化防线（如"mock 与真实 provider 协议差距"出现 2 次 → 把真实 provider 冒烟纳入常规验收）

## 反模式（不要做）

- 只修不记——台账断档后，"处理过哪些 bug"只能靠翻 commit 考古
- 把台账写成 commit message 的复制粘贴——台账是"给人看的知识"，commit 是"给 git 看的变更"
- 防复发栏写"以后注意"——没有可核查载体的措施等于没写
- 把用户配置错误、环境问题记成代码 bug——台账只收仓库可修的缺陷；环境问题单独备注即可

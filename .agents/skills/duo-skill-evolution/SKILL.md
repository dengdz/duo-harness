# duo-skill-evolution — Skill 自我进化元技能

## 一、定位

本技能是「元技能」，不直接解决业务问题，而是服务于其他 Skill 的持续改进。

**核心机制**：其他 Skill 在任务结束后，主动调用本技能，对刚才的执行过程进行复盘评估。若发现问题或改进空间，触发进化；若执行顺畅、无明显不足，直接跳过，保持轻量。

**目标**：让每个 Skill 在日常使用中持续自我升级、越用越好。

---

## 二、接入方式（给其他 Skill 的作者）

### 2.1 在 Skill 结尾添加调用说明

在你的 SKILL.md 末尾添加如下章节：

```markdown
## 任务结束后：自我进化

本次任务完成后，调用 `duo-skill-evolution` 进行复盘：

1. 总结本次执行的关键步骤、遇到的问题、用户反馈
2. 评估是否存在改进空间
3. 若有价值的经验教训，触发进化

调用方式：
- 直接在任务结尾说："现在调用 duo-skill-evolution 复盘本次执行"
- 或在用户确认任务完成后，主动询问："是否需要复盘本次执行并记录经验？"
```

### 2.2 调用时机

- **必须**：任务完整结束后（不要在中途调用）
- **可选**：用户明确表示"这次执行有问题"或"记录一下这次经验"时
- **跳过**：用户明确拒绝复盘、或任务被中断/取消时

### 2.3 输入内容

调用时，向 duo-skill-evolution 提供以下信息：

1. **Skill 名称**：你自己的 Skill 名称（如 `duo-code-review`）
2. **本次任务摘要**：用 2-3 句话描述本次做了什么
3. **执行过程关键点**：
   - 主要步骤（如"读取文件 → 分析 → 生成报告"）
   - 遇到的障碍或意外情况
   - 采取的变通措施
4. **用户反馈**（若有）：用户是否满意、提出了哪些问题或建议
5. **自我感知**：你认为本次执行是否顺畅、有无改进空间

---

## 三、复盘评估逻辑

当被调用时，按以下流程执行：

### 3.1 快速判断：是否需要进化

根据输入信息，评估本次执行：

#### 无需进化的情况（直接跳过）：
- 执行顺畅，无错误、无遗漏
- 用户满意，无负面反馈
- 流程符合预期，无新的边界情况
- 本次经验与已有经验文档高度重复

**跳过时的输出**：
```
达，本次执行无明显问题，无需进化。复盘完毕。
```

#### 需要进化的情况（继续下一步）：
- 出现错误或遗漏
- 流程不顺畅（如重复劳动、冗余步骤、工具选择不当）
- 用户提出改进建议
- 发现新的边界情况或最佳实践
- 与已有指令冲突或矛盾

### 3.2 确定复盘维度

从以下维度分析本次执行：

| 维度 | 检查点 |
|------|--------|
| **执行结果质量** | 输出是否准确、完整、符合预期？有无遗漏或错误？ |
| **流程顺畅度** | 步骤是否合理？有无冗余、重复劳动、工具选择不当？ |
| **错误处理** | 遇到异常时是否优雅处理？有无改进空间？ |
| **用户体验** | 用户是否满意？反馈了哪些痛点？ |
| **可复用经验** | 本次遇到的情况是否有普遍性？能否提炼为通用规则？ |
| **与现有指令的一致性** | 本次执行是否与 SKILL.md 现有指令冲突？是否暴露了指令的模糊或遗漏？ |

### 3.3 提炼改进点

用 1-3 条简洁的改进点总结问题，每条包含：
- **问题描述**：出现了什么问题？
- **原因分析**：为什么会出现？
- **改进建议**：如何避免或优化？

示例：
```
1. 问题：审查时未检查 CHANGELOG.md 是否同步更新
   原因：SKILL.md 中未明确要求检查 CHANGELOG
   建议：在"红线检查"章节增加 CHANGELOG 同步检查项

2. 问题：用户修改了 3 个文件，但只审查了 2 个
   原因：git diff 输出解析逻辑遗漏了重命名文件
   建议：在经验文档记录"git diff 需处理 rename 情况"
```

## 四、进化方式

根据改进点的性质，选择合适的进化方式：

### 4.1 方式 A：追加经验文档（优先）

适用场景：
- 边界情况、最佳实践、踩坑经验
- 不需要改变 Skill 主流程，但值得记录的细节
- 可复用的技巧或模式

**操作步骤**：

1. 检查该 Skill 是否已有经验文档 `.agents/skills/<skill-name>/experience.md`
2. 若无，创建文件，写入标题：
   ```markdown
   # <Skill 名称> 经验文档
   
   本文档持续记录该 Skill 在实际使用中积累的经验教训、边界情况和最佳实践。
   
   ---
   ```
3. 追加新条目：
   ```markdown
   ## [日期 YYYY-MM-DD] <问题/场景简述>
   
   **问题描述**：
   （本次遇到的问题）
   
   **原因分析**：
   （为什么会出现）
   
   **解决方案**：
   （如何处理或避免）
   
   **影响范围**：
   （哪些场景需要注意）
   
   ---
   ```

4. 在该 Skill 的 SKILL.md 中增加引用（若尚未引用）：
   ```markdown
   ## 经验参考
   
   执行前建议阅读 `experience.md`，了解常见边界情况和最佳实践。
   ```

### 4.2 方式 B：修订 SKILL.md（谨慎使用）

适用场景：
- 现有指令存在错误、遗漏或模糊
- 流程需要调整（增加/删除/重排步骤）
- 红线规则需要补充或修正
- 触发条件、输出格式需要更新

**操作步骤**：

1. 读取该 Skill 的 SKILL.md 全文
2. 定位需要修改的章节
3. 应用改进点，修订相关内容
4. 在 SKILL.md 末尾的"变更历史"章节（若无则创建）记录：
   ```markdown
   ## 变更历史
   
   ### [日期 YYYY-MM-DD] 进化记录
   
   - **触发原因**：（本次复盘发现的问题）
   - **改动内容**：（修改了哪些章节/规则）
   - **预期效果**：（改进后应避免什么问题）
   ```

**注意事项**：
- 修订 SKILL.md 是「重」操作，仅在必要时使用
- 若改动较大（超过 3 处修改），建议先询问用户确认
- 保持 SKILL.md 简洁，避免过度膨胀

### 4.3 方式选择的优先级

**默认策略**：
1. 优先选择「方式 A：追加经验文档」——轻量、可逆、易积累
2. 仅在以下情况使用「方式 B：修订 SKILL.md」：
   - 现有指令明确错误或遗漏
   - 改进点属于「必须执行」的红线规则
   - 流程结构性调整（增删步骤）

**组合使用**：
- 可以同时使用两种方式（如：修订 SKILL.md 补充红线，同时在 experience.md 记录具体案例）

## 五、输出格式

### 5.1 无需进化时

```
达，本次执行无明显问题，无需进化。复盘完毕。
```

### 5.2 触发进化时

```
达，复盘完毕。发现以下改进点：

【改进点 1】
- 问题：（描述）
- 原因：（分析）
- 建议：（方案）

【改进点 2】
...

【进化方式】
- 方式 A：已追加到 `.agents/skills/<skill-name>/experience.md`，记录了 XX
- 方式 B：已修订 SKILL.md 的 XX 章节，补充了 YY

【预期效果】
下次执行时应避免 XX 问题，并在 YY 场景下更顺畅。
```

## 六、使用示例

### 示例 1：duo-code-review 调用复盘

**输入**：
```
现在调用 duo-skill-evolution 复盘本次执行：

Skill 名称：duo-code-review
任务摘要：审查了 3 个 Java 文件的改动，发现 2 处问题
执行过程：
- 读取 git diff
- 逐文件审查代码质量
- 生成审查报告
- 用户反馈：忘记检查 CHANGELOG.md 是否同步更新

用户反馈：应该同时检查 CHANGELOG
自我感知：现有流程未包含 CHANGELOG 检查，属于遗漏
```

**输出**：
```
达，复盘完毕。发现以下改进点：

【改进点 1】
- 问题：审查时未检查 CHANGELOG.md 是否同步更新
- 原因：SKILL.md 的"红线检查"章节未明确要求检查 CHANGELOG
- 建议：在红线规则中增加"文档与代码同步"检查项，包括 CHANGELOG

【进化方式】
- 方式 B：已修订 `duo-code-review/SKILL.md` 的"红线检查"章节，新增：
  > 6. 文档同步：CHANGELOG.md 是否记录了用户可见的变更？

【预期效果】
下次审查时会自动检查 CHANGELOG，避免遗漏版本记录。
```

### 示例 2：无需进化的情况

**输入**：
```
调用 duo-skill-evolution 复盘：

Skill 名称：duo-project-structure
任务摘要：审查目录结构，确认模块划分合理
执行过程：顺利完成，无异常
用户反馈：满意
自我感知：无问题
```

**输出**：
```
达，本次执行无明显问题，无需进化。复盘完毕。
```

## 七、注意事项

### 7.1 保持轻量原则

- **不要过度进化**：并非每次调用都要产出改动，大部分情况应该是"无需进化"
- **不要过度文档化**：经验文档记录真正有价值的教训，不要流水账
- **不要过度修订 SKILL.md**：保持 SKILL.md 简洁，避免膨胀成百科全书

### 7.2 进化的边界

- **不改变 Skill 的核心定位**：进化是优化细节，不是重构整个 Skill
- **不越权决策**：若改动涉及 Skill 的根本逻辑或用户偏好，先询问确认
- **不重复记录**：追加经验文档前，检查是否已有类似条目

### 7.3 与用户的互动

- 若改动较大（如修订 SKILL.md 超过 3 处），先告知用户并征得同意
- 若不确定某个改进点是否值得记录，询问用户意见
- 用户可以主动禁用某次复盘（如"这次不用复盘"）

---

## 八、元技能的自我进化

本技能自身也可以进化。若在使用过程中发现：
- 复盘维度不够全面
- 进化方式不合理
- 输出格式不清晰
- 其他问题

可以：
1. 直接修订本 SKILL.md
2. 或在 `.agents/skills/duo-skill-evolution/experience.md` 记录元技能自身的改进点

---

## 九、总结

本技能的价值在于：
- **持续改进**：每次执行后都有机会变得更好
- **知识积累**：经验文档成为 Skill 的"记忆"
- **轻量可控**：无问题时不强制进化，保持高效

让每个 Skill 在日常使用中持续升级，越用越好。

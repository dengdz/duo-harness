# duo-code-review 经验文档

本文档持续记录该 Skill 在实际使用中积累的经验教训、边界情况和最佳实践。

## 复盘维度

任务收尾调用 duo-skill-evolution 复盘时（AGENTS.md 红线 8），本技能按以下口径收集输入：

- 任务摘要：审查范围、发现问题数、修复情况
- 执行过程关键点：两轮审查是否顺畅、工具调用是否有问题、测试是否通过
- 用户反馈：用户对审查质量、报告格式、修复效果的反馈
- 自我感知：流程中是否有冗余步骤、遗漏检查、可优化点

## [2026-09-19] 测试收口时发现审查遗漏

**问题描述**：
两轮审查（双轴 + OCR）完成后，测试收口环节发现一个测试用例失败，但该问题在两轮审查中均未被发现。

**原因分析**：
1. 两轮审查侧重代码质量、架构合理性、行级规范，但未明确要求评估"测试覆盖充分性"
2. 审查报告中没有"测试覆盖预判"维度，无法提前识别测试用例不足的风险
3. 测试收口是"被动验证"（跑测试看结果），而非"主动预判"（审查时就评估测试是否充分）

**解决方案**：
在审查报告中增加"测试覆盖评估"维度，要求审查时主动判断：
- 变更涉及的核心逻辑是否有对应测试用例？
- 新增分支/边界情况是否有测试覆盖？
- 测试用例是否充分？是否需要补充？

若发现测试覆盖不足，在报告中明确标注，并在修复环节补充测试用例。

**影响范围**：
- 所有代码审查场景，尤其是涉及核心逻辑变更、新增功能的审查
- 建议在报告模板中增加"测试覆盖"章节（与"阻断"、"建议"并列）

## [2026-09-20] M20 夜间实现自审两则

**顺序脚本队列夹具在用例间泄漏**：mock HTTP 夹具若同时支持"固定脚本"与"顺序队列"两种设定，用例 A 遗留的排队脚本会在用例 B 设定固定脚本后被抢先消费（表现为 B 的超时/错误路径莫名拿到 200，4ms 通过）。修法：固定脚本设定入口必须清空队列。审查含 mock 夹具的测试代码时查"两种设定模式是否互斥"。

**JDK URI 的 resolve/normalize 不消解前导 .. 段**（RFC 2396 口径）：`base.resolve("/../up").normalize()` 仍得 `/../up`——路径形态不能依赖 JDK 代劳，涉及安全判定时只断言真正关心的属性（如同源的 host/scheme/port），路径形态留给目标服务器。

**影响范围**：涉及顺序 mock 夹具、URL 处理/SSRF 校验的测试与实现审查。

## [2026-09-21] 审查收尾的复盘触发：长流程末尾最易漏红线 8

**问题描述**：
M23 工单 01 审查（双轴 + OCR 两轮 + 修复 + 测试收口 + 报告持久化）全部完成后，直接输出了最终总结，跳过红线 8 的 duo-skill-evolution 复盘，被用户点名补触发。

**原因分析**：
审查是长流程（两轮审查穿插修复），收口时注意力全在"报告落盘 + 测试全绿"上；红线 8 的触发点是"duo- 技能任务收尾"——持久化完成即任务收尾，复盘必须在最终总结之前，不能拿"会话早段复盘过"抵扣同会话后续任务段。

**解决方案**：
把"duo-skill-evolution 复盘"当作收口流水线的固定末步：报告持久化落盘之后、最终总结输出之前执行（无进化点也明确说"无需进化"）。

**影响范围**：
所有 duo-code-review 任务（单工单到里程碑批次），以及其他 duo- 技能的长流程收尾。

## [2026-09-22] 测试用例形态同质化会藏 bug 到验收

**问题描述**：
FsGlobTool 锚定相对模式（`docs/adr/*.md`）从不工作，但 26 个既有用例全部采用 `**` 前缀形态（恰好是唯一侥幸可用的形态），全绿掩盖 bug 直到用户验收实测（模型 glob 返回 No files found）才暴露。

**原因分析**：
用例编写跟随工具 description 的示例形态（`**/*.java`），输入空间的关键维度（锚定 vs 任意深度、相对 vs 绝对）未做组合覆盖——同质化的绿等于单点绿。

**解决方案**：
审查「测试覆盖」维度增加形态多样性检查：同类参数存在多形态（锚定/通配前缀、带/不带可选参数）时，用例是否覆盖了互补形态；给公共工具写用例时刻意采用与 description 示例不同的形态。

**影响范围**：
所有带模式/参数形态分叉的工具类审查（glob/grep 的 include、.gitignore 判定器的锚定/negate 等——工单 08 重点适用）。

## [2026-09-22] 流水线「不跳步」无豁免理由：实测发现不能替代 OCR 轮

**问题描述**：
工单 03 审查以「两个坑已在测试先行中实测暴露（比 OCR 更硬的证据）」为由跳过了第二轮 OCR 委托，复盘时才发现——SKILL.md 流水线明写「顺序固定，不跳步」，该措辞没有给任何豁免。补跑后确认无新增发现，但流程违规已成事实。

**原因分析**：
实现期测试暴露的问题（/stop 吞应答、NIO 炸）给了「审查已充分」的错觉；但实测发现的问题是**已知问题**，OCR 的价值恰在**未知问题**的独立视角——两者不可互替。

**解决方案**：
任何情况下不跳轮；若认为某轮冗余，仍跑完并如实标注「无新增发现」——证据归档的价值独立于发现数量。

**影响范围**：
所有 duo-code-review 执行（单工单与批次）。

## [2026-09-23] 委托模式 OCR 轮零产出的根因：行级审查失去独立性（两轮制改三轴）

**问题描述**：
用户质疑「每次 OCR 都识别不到内容」。核对 review-log 实证：端点模式时代（M19-M21）OCR 产出 27/16/2+ 条，切委托模式后（M23 至今）每轮仅 0~2 条 Low——同期双轴子代理持续产出实质发现（M24 工单 03 路径归一逃逸口、工单 02 Web 高危语义相悖与提问卡 id 断链回归），OCR 轮贡献为零。

**原因分析**：
委托模式把行级审查交回代码作者本人、在原上下文执行——自审刚写完的代码，假设与盲点完全同源，产出率天然趋零；「报告必须落盘」的硬判据只堵了跳步，没恢复独立性。

**解决方案**：
两轮制并入三轴（2026-09-23 SKILL.md 修订）——行级规则审查升格为第三轴，与 Standards/Spec 并行由**新上下文子代理**执行（brief 携 OCR 规则清单 + 「先列候选再过滤，宁多勿漏」防锚定指令）；`ocr` 命令降级为文件选取/规则来源工具；收口硬判据改三轴齐全。

**影响范围**：
所有 duo-code-review 审查会话；第三轴产出率以后续工单实证检验，持续为零再议豁免或回端点模式。
## [2026-09-23] 多宿主/多上下文改造工单：兼容位与业务路由的选源疏漏

**问题描述**：
工单 07（标签级会话绑定）四轴审查中，Spec 轴抓到唯一阻断：后台任务通知路由按 `min(seq)` 选标签时把匿名上下文（seq=0 恒在场）选为投递目标——单标签下浏览器标签永远收不到通知，注释声称的「单标签行为不变」不成立。

**原因分析**：
为兼容 curl/缓存页/存量测试引入「匿名上下文/默认对象」时，实现者的注意力在新增路径上；一切「按业务语义选目标」的既有代码改造成 Map 遍历后，兼容位天然出现在候选集里且常以最小序号/最先插入胜出。兼容位的正确角色是接住无头请求，不是业务路由的兜底目标。

**解决方案**：
1. 审查多宿主/多上下文改造（单例 → Map）的 diff 时，专查一条：「遍历选源、聚合统计、广播目标」三类代码是否显式排除兼容位/默认键；
2. 相邻同构教训：Consumer 回调承载不了「产物归谁」（全局单槽 setAgent 即分脑面），Function 化让产物回流正确宿主——回调型装配的产物归属是改造工单的固定审查点；
3. POST 体排空先于标签/会话解析（keep-alive 复用正确性）——端点参数化时新增的前置步骤要放在读体之后。

**影响范围**：
后续任何「单例状态 → 多实例并存」的工单（多会话、多租户、多呈现位）审查走查清单适用。

## [2026-09-23] 停止链路三轮实测：夹具语义失真与 interrupt 的连坐面

**问题描述**：
停止功能验收三轮才收敛——①「流式段点停止无反应」：中断依赖线程打断唤醒阻塞读，但真实适配器的 readLine 阻塞在 socket 流上对 interrupt 免疫；②「停了但报错 + 红卡」：打断落地时正击中会话落盘的 FileChannel IO，InterruptibleChannel 语义直接关闭唯一持锁通道（POSIX 连坐释放独占锁，不可恢复）；③ 前端 sendMode 未声明（node --check 只查语法不查引用）。

**原因分析**：
1. **夹具语义失真**：CooperativeInterruptTest 用 Thread.sleep（可打断）模拟「流式阻塞读」——测试模型与现实相反，全绿掩盖缺陷。2. **中断设计未盘点目标线程的全部阻塞点**：send 线程既有「需要唤醒的可打断等待」（工具 waitFor）也有「必须不被打断的 FileChannel 落盘」，无差别 interrupt() 必然偶尔击中后者。3. 静态检查工具的能力边界（语法 ≠ 引用解析）。

**解决方案**：
审查走查清单新增两条：① 涉及 Thread.interrupt/interruptible 的 diff，要求列出目标线程的全部阻塞点并逐点判定「该被打醒 / 必须免疫」——流式段走回调收敛（相位门不打断线程）、工具段才打断；② mock/stub 模拟阻塞 IO 时核对其可打断性是否与真实原语一致（sleep ≠ readLine），失真夹具要标注或改用吞中断阻塞。前端改动 review 时记住 node --check 的盲区（未声明引用运行时才炸）。

**影响范围**：
所有协作式中断/线程打断设计；一切用 mock 模拟阻塞 IO 的测试。

## [2026-09-24] 纯文档 diff 审查：转录锚点的三类"写快了"错误（C1-01）

**问题描述**：
C1-01（Matt 侧机制清单，4 文件全文档 diff）审查抓回 8 处，其中 3 处同族且全是"写快了不核对"：①引用 loop-me:45-47——该行号实为 Bash 持久化输出文件的行号，SKILL.md 只有 32 行（自附覆盖表里都写了 32）；②断言 hitl-loop.template.sh「插件内无该文件」——未 find scripts/ 子目录，文件实际存在，负向断言无证据（两轴独立抓回）；③「七词条」「两条 on-ramp」等计数/数量词与实际枚举不符（含原文 ask-matt 自身 two on-ramps 列三项的矛盾被照抄未标注）。

**原因分析**：
批量 cat -n 多文件输出被 persist 后再读时，log 自身行号与源文件行号同屏出现，转录极易串号；负向断言（不存在/无此文件）被当成不需要证据的结论；数量词照感觉写而不重数。

**解决方案**：
1. 从持久化输出转录锚点必须逐条带文件名前缀核对，写死前抽查「行号 ≤ 文件总行数」这一廉价不变量（wc -l 一次全批校验）；
2. 负向断言与正向断言同价：「我没找到」≠「它不存在」，断言缺失前必须全量搜索（find/grep 全插件或全仓）；
3. 计数类陈述落笔时重数一遍；被引对象数量词与枚举冲突时按实际枚举记录并标注原文矛盾（收入张力点节，不静默改正原文）。

**影响范围**：
一切含大量 文件:行号 锚点的审查对象（研究文档、机制清单、对比报告）；一切「声称 X 不存在」类审查发现。

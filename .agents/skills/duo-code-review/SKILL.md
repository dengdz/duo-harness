# duo-harness 审查即修复流程

两轮审查、两轮修复、测试收口。开工前先读 `.scratch/review-log.md`（不存在则视为无历史），把已知模式纳入两轮重点。红线不变：未经用户确认不 commit；架构类分歧先确认方案再动手。

## 流水线（顺序固定，不跳步）

### 第一轮：双轴审查 → 报告 → 修复

1. **双轴审查**：调用 mattpocock `code-review` 技能（Standards/Spec 双轴并行子代理），用法以该技能为准。fixed point 取改动前的提交（单工单审 `HEAD~1`，批次/里程碑审分支基点或用户指定点）；Spec 轴来源 = `.scratch/<feature>/spec.md` 与对应工单文件，找不到如实报"无 spec 可对照"，不臆造需求。
2. **生成第一份审查报告**（模板见下，标注"第 1 轮·双轴"）。
3. **基于报告修复**：明确缺陷直接修并带回归测试；架构/设计类 blocker 把方案摆给用户确认后再动手。

### 第二轮：OCR 行级审查 → 报告 → 修复

4. **OCR 审查**：调用 `open-code-review-delegate` 技能（OCR 委托模式），对含修复在内的完整 diff 出行级意见，用法以该技能为准——OCR 只做文件选取与规则解析（`ocr delegate preview` / `ocr delegate rule`），行级审查由本 agent 亲自执行，不调 LLM 端点。其名单默认不含测试与文档——这两类的核对结论由第一轮与两轮修复覆盖，报告覆盖率按 `git diff --stat` 全集口径标注。
5. **生成第二份审查报告**（标注"第 2 轮·OCR"）。
6. **基于报告再修复一轮**（授权边界同第 3 步）。

### 收口（硬判据：两轮齐全才算收口）

7. **两轮齐全核对**：第 1 轮·双轴与第 2 轮·OCR 的报告**齐全且均落盘**，本次审查才算收口——缺任何一轮即未收口，不得输出最终总结。豁免 OCR 轮的唯一合法路径：在工单审查报告与 review-log **双处**写明理由，并**经用户显式确认**；现场裁量豁免无效，沿袭先前工单的豁免同样无效（每次豁免都是独立决定）。
8. **测试收口**：跑覆盖该 diff 的最窄测试，全绿即本次审查结束。不自动复跑 OCR；用户点名复核才再来一轮。
9. **持久化**：两轮报告落盘 + 审查总结追加（见下两节）。

## 报告模板（每轮一份）

```markdown
## 审查报告（第 N 轮·双轴/OCR）：<范围>

**覆盖**：N 个文件 = 已审 X + 跳过 Y（覆盖率 Z%）；跳过逐个附理由

### 阻断
- **`path:line`** — 问题 / 影响 / 证据

### 建议
- **`path:line`** — 问题（可选修法）

### 测试覆盖
- 变更涉及的核心逻辑是否有对应测试用例？
- 新增分支/边界情况是否有测试覆盖？
- 测试用例是否充分？若不足，列出需补充的场景
```

双轴轮在报告尾部保留 Standards / Spec 两轴原样分列，不重排不合并；已被绿灯测试覆盖或抓不住上下文的问题不进报告。

## 报告持久化

- 单工单审查 → 并入工单（`.scratch/<feature>/issues/NN-*.md`）末尾「审查轮（日期）」小节；批次 / 里程碑 / 分支审查 → `.scratch/<feature>/reviews/YYYY-MM-DD-<范围>.md`。
- 落盘内容 = 对话里给出的报告全文；修复处置在同一处续写，形成"发现 → 处置 → 复核"闭环。

## 审查总结（持续维护文档）

`.scratch/review-log.md`（与 bug-log 同型）在每次审查收口时追加一节：

- 日期 / 范围 / 两轮发现与修复计数；
- 模式化问题：本仓库反复出现的坑与本次新发现的模式；
- 对后续开发的优化建议：可沉淀为约定、检查项或新工单的。

## 变更历史

### [2026-09-22] 收口加两轮齐全硬判据

- **触发原因**：M23 复盘发现 OCR 轮自工单 03 起滑移——「实测替代」「并入双轴行级」的现场豁免沿袭至 05-07，近三张连豁免记录都消失；「顺序固定不跳步」是描述性条款、无机械校验点，跨会话后必然衰减
- **改动内容**：收口节前置「两轮齐全核对」硬判据（收口步骤 7→9）——两份报告齐全且落盘才算收口，缺轮即未收口不得输出最终总结；豁免 OCR 唯一路径 = 工单报告与 review-log 双处记档理由 + 用户显式确认，现场裁量与沿袭既往豁免均无效
- **预期效果**：跳步在收口核对处被机械抓到（报告缺失即未收口）；豁免权从执行者现场裁量回归用户显式审批

### [2026-09-20] OCR 切换委托模式

- **触发原因**：`open-code-review` 端点审查一次近 40 分钟，委托模式约 5 分钟
- **改动内容**：第二轮 OCR 审查由 `open-code-review`（LLM 端点）改为 `open-code-review-delegate`（委托模式）——OCR 仅做文件选取与规则解析，行级审查由本 agent 执行
- **预期效果**：第二轮时长大幅缩短；名单、覆盖率口径与报告模板不变

### [2026-09-19] 进化记录

- **触发原因**：复盘发现测试收口时才发现审查遗漏（测试用例失败但两轮审查未发现）
- **改动内容**：
  1. 在报告模板中新增"测试覆盖"章节，要求审查时主动评估测试充分性
  2. 创建 `experience.md` 记录该案例，提醒后续审查注意测试覆盖预判
- **预期效果**：下次审查时会主动评估测试覆盖，在报告中标注测试不足，避免测试收口时才暴露问题

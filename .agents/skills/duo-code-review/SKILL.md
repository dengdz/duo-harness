# duo-harness 审查即修复流程

四轴并行审查、统一修复、测试收口。开工前先读 `.scratch/review-log.md`（不存在则视为无历史），把已知模式纳入四轴重点。红线不变：未经用户确认不 commit；架构类分歧先确认方案再动手。

## 流水线（顺序固定，不跳步）

### 第一阶段：四轴并行审查 → 合并报告 → 修复

1. **四轴并行审查**（四个**新上下文子代理**同时跑——独立性是产出率的来源，禁止本 agent 亲自执行任一轴）：
   - **Standards 轴**：调用 mattpocock `code-review` 技能的 Standards 子代理，用法以该技能为准。文档化标准源 + Fowler 坏味道基线随 brief 下发。
   - **Spec 轴**：调用 mattpocock `code-review` 技能的 Spec 子代理。Spec 来源 = `.scratch/<feature>/spec.md` 与对应工单文件，找不到如实报"无 spec 可对照"，不臆造需求。
   - **行级规则轴**：OCR 委托模式做文件选取与规则解析（`ocr delegate preview` / `ocr delegate rule`，用法以 open-code-review-delegate 技能为准），**行级审查交给独立子代理**执行——brief 携 OCR 规则清单与固定指令：「逐文件对照规则清单出候选发现，先列全再过滤，宁多勿漏」。测试与文档不入行级名单——这两类由 Standards/Spec 轴覆盖，报告覆盖率按 `git diff --stat` 全集口径标注。
   - **Java 规范轴**：调用项目内 `duo-java-review` 技能（阿里巴巴 Java 开发手册·嵩山版，渐进式加载 L1 规则文件），按其工作流出 BLOCKER/CRITICAL/MAJOR 分级发现。**三条 brief 约束**：① 适用子集裁剪——MySQL/服务器端章节默认跳过，仓库惯例与新范式（虚拟线程/record/switch 表达式）优先，手册未覆盖新范式的条款不适用；② 反条款倾销——先列候选再过滤，不适用的条款明确写出丢弃理由；③ 分工——只报「规则编号 + 条款原文」类发现，与 Standards 轴重叠的由主审合并处置。
   - fixed point 取改动前的提交（单工单审 `HEAD~1` 或工作树基点 HEAD，批次/里程碑审分支基点或用户指定点）。
2. **生成审查报告**（模板见下，标注"第 N 轮·四轴"，Standards / Spec / 行级规则 / Java 规范四轴原样分列，不重排不合并；重复发现由主审标注合并处置）。
3. **基于报告修复**：明确缺陷直接修并带回归测试；架构/设计类 blocker 把方案摆给用户确认后再动手。
4. **修复复核**：修复引入阻断级新代码改动时复跑四轴（基点改为本次报告落盘点）；小修由测试收口覆盖，不强制复跑。

### 收口（硬判据：四轴齐全才算收口）

5. **四轴齐全核对**：Standards / Spec / 行级规则 / Java 规范四轴的报告**齐全且均落盘**，本次审查才算收口——缺任何一轴即未收口，不得输出最终总结。豁免行级轴或 Java 规范轴的唯一合法路径：在工单审查报告与 review-log **双处**写明理由，并**经用户显式确认**；现场裁量豁免无效，沿袭先前工单的豁免同样无效（每次豁免都是独立决定）。
6. **测试收口**：跑覆盖该 diff 的最窄测试，全绿即本次审查结束。不自动复跑四轴；用户点名复核才再来一轮。
7. **持久化**：四轴报告落盘 + 审查总结追加（见下两节）。

## 报告模板（每轮一份）

```markdown
## 审查报告（第 N 轮·四轴）：<范围>

**覆盖**：N 个文件 = 已审 X + 跳过 Y（覆盖率 Z%）；跳过逐个附理由

### 阻断
- **`path:line`** — 问题 / 影响 / 证据

### 建议
- **`path:line`** — 问题（可选修法）

### 测试覆盖
- 变更涉及的核心逻辑是否有对应测试用例？
- 新增分支/边界情况是否有测试覆盖？
- 测试用例是否充分？若不足，列出需补充的场景
```

报告尾部保留 Standards / Spec / 行级规则 / Java 规范四轴原样分列，不重排不合并；已被绿灯测试覆盖或抓不住上下文的问题不进报告。

## 报告持久化

- 单工单审查 → 并入工单（`.scratch/<feature>/issues/NN-*.md`）末尾「审查轮（日期）」小节；批次 / 里程碑 / 分支审查 → `.scratch/<feature>/reviews/YYYY-MM-DD-<范围>.md`。
- 落盘内容 = 对话里给出的报告全文；修复处置在同一处续写，形成"发现 → 处置 → 复核"闭环。

## 审查总结（持续维护文档）

`.scratch/review-log.md`（与 bug-log 同型）在每次审查收口时追加一节：

- 日期 / 范围 / 三轴发现与修复计数；
- 模式化问题：本仓库反复出现的坑与本次新发现的模式；
- 对后续开发的优化建议：可沉淀为约定、检查项或新工单的。

## 变更历史

### [2026-09-23] 三轴并入四轴：新增 Java 规范轴（阿里手册）

- **触发原因**：用户提议以 `java-code-review-alibaba` 技能（阿里巴巴 Java 开发手册·嵩山版）增补代码规范审查。该技能与现有三轴互补：Standards 轴管仓库惯例 + 通用坏味道，阿里轴管 Java 语言/库用法细则（命名/并发/集合/异常/日志正是近期高频发现区）；渐进式加载（L1 规则文件按需）对子代理上下文友好
- **改动内容**：三轴扩为四轴——新增 **Java 规范轴**（调用户级 `java-code-review-alibaba` 技能，BLOCKER/CRITICAL/MAJOR 分级），brief 内置三条约束：适用子集裁剪（MySQL/服务器端章节默认跳过、虚拟线程/record 等新范式条款不适用）、反条款倾销（不适用条款写明丢弃理由）、与 Standards 轴分工（只报规则编号+条款原文类）；收口硬判据改四轴齐全；报告四轴分列，重复发现主审合并处置
- **后续收编（同日）**：技能本体收编进项目 `.agents/skills/duo-java-review/`（按 duo 命名规范改名，随仓库入库团队共享），Java 规范轴改调项目内 `duo-java-review`
- **预期效果**：Java 规范类发现的捕获面扩大；产出率以后续工单实证检验，持续零产出或全是误报再议裁撤该轴

### [2026-09-23] 两轮制并入三轴：行级规则轴独立子代理化

- **触发原因**：用户质疑「每次 OCR 都识别不到内容」。实证核对：端点模式时代（M19-M21）OCR 产出 27/16/2+ 条，切委托模式后（M23 起）每轮 0~2 条 Low——断崖与模式切换相关而非代码质量；根因 = 委托模式下行级审查由本 agent（代码作者）在原上下文亲自执行，无独立视角，自审刚写完的代码产出率天然趋零。本轮三张工单的全部实质发现均来自新上下文的双轴子代理，OCR 轮贡献为零
- **改动内容**：取消「OCR 第二轮」名义——行级规则审查并入第一阶段与 Standards/Spec 并行，成为**第三轴**（新上下文子代理执行，brief 携 OCR 规则清单与「先列候选再过滤」指令）；`ocr` 命令降级为第三轴的文件选取/规则来源工具；收口硬判据由「两轮齐全」改「三轴齐全」；报告由两轴分列改三轴分列；新增第 4 步「修复复核」（阻断级新改动复跑三轴）
- **预期效果**：行级审查恢复独立视角（新上下文、非作者）；保留委托模式的速度优势；产出率是否回升以后续工单实证检验，持续为零再议豁免或回端点

### [2026-09-22] 收口加两轮齐全硬判据

- **触发原因**：M23 复盘发现 OCR 轮自工单 03 起滑移——「实测替代」「并入双轴行级」的现场豁免沿袭至 05-07，近三张连豁免记录都消失；「顺序固定不跳步」是描述性条款、无机械校验点，跨会话后必然衰减
- **改动内容**：收口节前置「两轮齐全核对」硬判据（收口步骤 7→9）——两份报告齐全且落盘才算收口，缺轮即未收口不得输出最终总结；豁免 OCR 唯一路径 = 工单报告与 review-log 双处记档理由 + 用户显式确认，现场裁量与沿袭既往豁免均无效
- **预期效果**：跳步在收口核对处被机械抓到（报告缺失即未收口）；豁免权从执行者现场裁量回归用户显式审批

### [2026-09-20] OCR 切换委托模式

- **触发原因**：`open-code-review` 端点审查一次近 40 分钟，委托模式约 5 分钟
- **改动内容**：第二轮 OCR 审查由 `open-code-review`（LLM 端点）改为 `open-code-review-delegate`（委托模式）——OCR 仅做文件选取与规则解析，行级审查由本 agent 执行
- **预期效果**：第二轮时长大幅缩短；名单、覆盖率口径与报告模板不变

### [2026-09-19] 进化记录

- **触发原因**：复盘发现测试收口时才发现审查遗漏（测试用例失败但两轮审查未发现）
- **改动内容**：
  1. 在报告模板中新增"测试覆盖"章节，要求审查时主动评估测试充分性
  2. 创建 `experience.md` 记录该案例，提醒后续审查注意测试覆盖预判
- **预期效果**：下次审查时会主动评估测试覆盖，在报告中标注测试不足，避免测试收口时才暴露问题

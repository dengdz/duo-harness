## 复盘维度

任务收尾调用 duo-skill-evolution 复盘时（AGENTS.md 红线 8），本技能按以下口径收集输入：

- 任务摘要：任务级别（L1/L2/L3）、实现内容、涉及模块、关键步骤
- 执行过程关键点：分级是否准确、流程是否完整、测试是否充分、验收是否通过、提交前核对是否遗漏
- 用户反馈：用户对流程执行、代码质量、验收结果的反馈
- 自我感知：流程中是否有遗漏环节、质量卡点是否有效、可优化点

## [2026-09-29] 里程碑启动 grill 首步做版图对账：ADR 版图定版号 vs CHANGELOG 实发版号

**问题描述**：
M29 启动时发现 ADR-0029 版图定的 M29=0.24.0 已被插入的 C2 补丁式代码处置批占用并发版（CHANGELOG 落日期、分支已建），全仓无版图顺移记录——版本号错位直到里程碑启动 grill 才暴露，立项第一题被迫先补钉版号。

**原因分析**：
插入批（非版图内的插单工作）立项只走了 spec/分支/发版，没有同步记录「占用了哪个 minor 版本号、版图如何顺移」——版图 ADR 与 CHANGELOG 两条版本线无人对账，错位静默累积。

**解决方案**：
里程碑启动 grill 首步固定做版图对账：读 CHANGELOG.md 顶部实发版本 + grep 版图 ADR 对应期号，两者不一致即版号顺移议题前置（先于范围题裁定）；插入批若占 minor 版本号，立项同 diff 在版图 ADR 对应节加注（本次形态：ADR-0029 M29/M30 节勘误注 + ADR-0031 记顺移）。

**影响范围**：
所有里程碑启动 grill（M30/M31 及 1.0 后各期首步）；任何插单批占用 minor 版本号的立项场景。

## [2026-09-29] 接口新增可选通道时，包装/装饰实现必须同 diff 排查透传（缺省实现让测试全绿、生产链静默断链）

**问题描述**：
M29 工单 06 给 `LlmAdapter.streamTurn` 新增思考增量通道（三参 default 委托两参），实现、骨架、测试全绿——用户实测思考流式卡不出现。根因：生产执行链是 `RetryingAdapter`/`SwappableLlmAdapter` 装饰的，两包装器只覆写两参，agent 的三参调用落到接口 default 委托包装器自身两参，思考增量整链被静默丢弃。

**原因分析**：
接口新增通道用「default 委托旧形态」保证向后兼容——但缺省实现同时让**所有未升级的包装器编译通过且测试全绿**（测试桩直接实现旧形态，走 default 正确；生产包装器同样走 default，但语义是「丢弃新通道」）。测试绿 ≠ 生产链通：缺省实现把「未升级」与「升级了但没透传」两种形态都静默放行。

**解决方案**：
接口新增可选通道时同 diff 执行两步：①`grep "<接口名>" --include="*.java" -l` 列出全部 implements/装饰实现，逐一核对新通道透传（装饰器转发新参数、重试类把新通道计入安全计数）；②回归锁用「三参桩 + 两参抛 AssertionError」形态（ReasoningPassthroughTest 先例）——桩走 default 会绿，锁住「包装器必须显式透传」这一契约。

**影响范围**：
所有接口演进加可选参数/回调通道的场景（LlmAdapter 之后：AgentListener、呈现位接口、hooks 载荷扩展同风险）。

## [2026-09-29] 前端 IIFE 容器边界：顶层新增代码引用 IIFE 内部标识符必运行时断（M29 工单 10 两犯）

**问题描述**：
M29 工单 10 前端打磨，两处新增代码在页面首载即抛 ReferenceError（错误卡可见）：①状态面折叠段误用 render IIFE 内部状态 `t`（顶层不可见）；②`fillHero` 定义放 IIFE 内、顶层启动段调用够不着。`node --check` 全程语法绿——IIFE 内引用未定义名是运行时错，静态检查不拦。

**原因分析**：
duo 前端 app.js 的 render 块是 IIFE 容器（内部状态 `t`、工具函数外界不可见），而启动/初始化代码在顶层——两个作用域的边界没有机械核对点；「函数放哪近就写哪」的惯性天然踩线。

**解决方案**：
IIFE 内部函数/状态被顶层需要时，二选一并机械核对：①上提顶层（函数不依赖 IIFE 内部状态时，如 fillHero 纯 DOM 操作）；②经 render 返回面暴露。核对动作：新增顶层代码 `grep` 其引用的每一条 `xxx.` 标识符确认定义作用域；验证以**真实页面首载**为准（无头/浏览器截图），`node --check` 语法绿不算数。

**影响范围**：
duo-harness-web 的所有 app.js 顶层新增逻辑；同构的「模块容器 + 顶层启动」形态前端工程。

## [2026-09-20] CHANGELOG 未发布段多条目拆分两笔提交的技法

**问题描述**：
里程碑进行中两类无关变更（如技能整理与研究落盘）需分两笔提交，但两条 CHANGELOG 记账同处一个"未发布"版本段，`git add` 按文件暂存无法拆分同一文件内的不同行——直接整文件暂存会让第一笔提交夹带第二笔的记账。

**原因分析**：
"用户可见变更同 diff 记账"要求每笔提交携带自己的 CHANGELOG 行，而未发布段是多条目共存的单一文件。

**解决方案**：
先临时摘除后一条记账行 → 暂存并提交前一笔（携带自己的记账行）→ 补回被摘除的行 → 暂存并提交后一笔。顺序执行，两笔提交各自满足红线；发布时未发布段整体落日期。

**影响范围**：
后续所有里程碑的多提交记账场景（0.15.0 分支 M20 启动日实测有效）。

## [2026-09-20] 包私有 API 的手动验收——用同包临时类，别用 jshell

**问题描述**：
给用户写 jshell 脚本验证库行为，脚本第一步即"找不到符号"全线失败——被验类型是包私有（库的内部细节，设计正确），jshell 代码落在无名包够不到包私有成员；且 jshell 逐段求值放大级联错误、受检异常未包的语句也易写漏。

**解决方案**：
手动验收脚本改为 /tmp 下临时 Java 类，文件头声明与库同包（`package dev.duo.harness.attachment;`）——同包即合法访问包私有，一次 javac+java 出全部证据，跑完即删。给用户的可复跑命令须自带清场。

**影响范围**：
所有"让用户亲眼验证库行为"的场景（工单级手动验收）；jshell 仅适合纯公开 API 的随手验证。

## [2026-09-20] 给 stdio server 注入 EOF 监视：EOF 是随时到来的死亡信号，启动序列须按"已死"分支处理

**问题描述**：
给 MCP stdio server（SDK `StdioServerTransportProvider` 双参构造注入包装流）挂 stdin EOF 自退时，回归测试立即失败——测试在 `start()` 后马上关 stdin，SDK 读循环 EOF 终结传输层，随后 `addTool` 内部发 notification enqueue 失败抛 RuntimeException，进程以退出码 1 崩溃而非按预期自退。

**原因分析**：
EOF 不只在"服务期"到来——父进程强杀时它可能在子进程启动序列任意点插入。启动序列里任何触发通知/IO 的步骤（`addTool` 即发 tools 变更通知）在传输已死后都会抛，异常路径若不区分"EOF 已至"就会把自退变成崩溃。

**解决方案**：
启动序列中会触发 IO 的步骤包 try-catch，以 EOF 闸门计数为判据：`stdinClosed.getCount() == 0` 时吞掉异常按自退处理（退出竞态的预期噪声），否则原样抛出（真异常）。回归测试专门用"start 后立即关 stdin"压这个竞态窗口。

**影响范围**：
所有"监视底层资源死亡并自退"的子进程/server 夹具——死亡信号必须能在启动期到达且被优雅消化，而不仅在服务期。

## [2026-09-22] Javadoc 里写 glob/ignore 模式字面量：`*/` 序列会提前闭合注释

**问题描述**：
给 FsGlobTool 补 javadoc 时写了 `` `**/` ``，字面 `*/` 把注释提前闭合，剩余中文成了代码，编译报一串「非法字符」。

**原因分析**：
块注释内出现 `*/` 任何形式的序列（含反引号包裹、代码片段）都会终结注释；写文件路径模式说明时极易顺手带入。

**解决方案**：
javadoc/块注释内描述双星模式时用措辞替代（「双星前缀」「去前缀变体」），或用行注释 `//` 承载含模式的说明。

**影响范围**：
即将开工的工单 08（.gitignore 判定器）注释里会高频出现 `**/`、`*` 等 ignore 模式——高频踩雷区，写注释时先自查闭合序列。

## [2026-09-22] 新服务发布先核对命名惯例与取用方式

**问题描述**：
后台任务注册表服务发布为 `"background-tasks"`（连字符），呈现位经视图接口 `backgroundTasks()` 取用——动态代理按方法名解析服务名，启动即报「服务 backgroundTasks 未在依赖声明中」。

**原因分析**：
既有惯例是 camelCase 服务名（`sessionQuery`、`tools`、`prompts`——方法名直取），新服务命名未对照先例；连字符服务名在视图接口体系里无法直取。

**解决方案**：
新服务发布前先 grep 既有 `SERVICE_NAME` 形态（camelCase）；视图接口方法名 = 服务名逐字（带连字符的服务名只能走 ctx.services 之类的非视图通道——避免设计）。

**影响范围**：
所有新服务发布（tools/fs/agent/web 各域）。

**重现与强化（2026-09-22，M24 工单 01）**：本条重现——新服务 `permission-rules` 连字符命名致视图接口解析失败、恢复用例红（修复为 camelCase `permissionRules`）。强化为机械核对项：**新服务发布时 SERVICE_NAME 常量与消费方视图接口方法名并排摆放、逐字一致后才编译**； duo-code-review 的 Standards 轴与 OCR 轮都应核对这一对。

## [2026-09-22] 脚本化批量修改代码：replace 后必须断言生效

**问题描述**：
工单 05 实现中用 python 脚本批量修改测试文件，三次 replace 因转义层级不匹配**静默失败**（old 串没匹配上、无报错），导致后续调试在「spill 未触发」的错误方向上绕了数轮；同段还三犯 `-pl` 忘 `-am`（依赖解析失败）。

**原因分析**：
python 的 `str.replace` old 不存在时不报错；转义层级（bash heredoc → python → Java 源）叠加极易算错；mvn 单模块命令从记忆拼装已两次违反（见 duo-acceptance 2026-09-22 条）。

**解决方案**：
批量代码修改的硬纪律：① 优先用 Edit 工具（所见即所得、失败即报）；必须用脚本时，replace 后紧跟 `assert old in s`（或计数校验）再写盘；② mvn 单模块命令只从 `docs/01-入门/运行Demo.md` 或既有 README 原样复制（带 `-am package`），改动仅限 mainClass。

**影响范围**：
所有 agent 执行的批量代码修改与 mvn 构建命令。

**第四次重现（2026-10-03，M35 工单 04 验证）+ 两个新变体**：`-pl duo-harness-web test` 忘 `-am` 再现（sibling 依赖解析失败）；更隐蔽的新变体是**结果判定被管道吞掉**——`./mvnw ... | grep -E "..." | head; echo "exit: $?"` 取的是 head 的退出码（恒 0），编译失败被读成绿，且陈旧 surefire 报告（上一轮的 103 例）被当成本轮证据。解决方案升级为双保险：①真实退出码必须在无管道语句取（`cmd > log 2>&1; echo $?`）；②证据以"删旧报告后重新生成"的 surefire 计数为准（target/ 陈旧报告会冒充本轮结果）。**同日第三变体（陈旧产物家族扩员）**：多段复合命令里"上一段 package 失败、后段仍引用旧 fat-jar"——行为对不上新代码时，产物新鲜度用源码级抽查判定（解包 + `javap` 查新方法在不在），判定为陈旧即 `clean package` 强制全链重打。

## [2026-09-22] grill 收口前对照 backlog/代码现状做排他对账，防「事实在手、矛盾漏网」

**问题描述**：
M24 grill 把 /effort 四行 provider 映射照 ADR-0024 全收，但落 spec 时才发现「Anthropic 行映射」与「仓库仅一个 OpenAI 兼容适配器、Anthropic-messages 适配器已钉 1.0 后菜单」直接矛盾——探测事实早就在手（调研明确报了单适配器现状），grill 的 20 问却没把两者对到一起，用户只能在 spec 期追加裁定（补适配器、provider 显式声明）。

**原因分析**：

**解决方案**：
grill 收口前的范围确认题固定加一步排他对账：把本期范围逐项对照 1.0 后菜单/backlog/limitations/代码现状清单，凡「某项的前提依赖另一个被后置的项」即当场抛矛盾题；to-spec 落笔前再复跑一遍（本次正是这道二手防线兜住的）。

**影响范围**：
所有 grill 类会话的范围确认环节与 to-spec 开笔前对账。

**第二次实证（2026-10-03，M35 to-spec 落笔前复跑）**：grill Q5 裁定「插件中心操作写回 plugins.yml」时未对照在案事实「缺省启动来源是 classpath 资源（M30 起支持 fat-jar 内资源形态，物理不可写）」——矛盾在 to-spec 落笔前复跑时钉住：补「首启物化到 DUO_HOME 作唯一可写事实源」补钉，避免实现期爆雷。教训具象化：凡裁定含「写回某文件」，对账清单必查该文件在目标部署形态下的物理可写性。

## [2026-10-04] 宿主同族进程清理必须精确寻址：宽模式 pkill 可杀到 agent 宿主本体

**问题描述**：
M37 工单 02 壳联调清 Electron 挂死残留时，先 `pkill -f "Electron.app.*--smoke"`（尚可），后续又 `pkill -9 -f "Electron"`——本机宿主 ZCode 自身即 Electron 系应用（/Applications/ZCode.app），宽模式命中面覆盖宿主，`ps` 复核时 PID 3210 ZCode.app 仍在命中名单里，险些连宿主带会话一起杀。

**原因分析**：
进程清理的匹配模式写的是「应用类型名」而非「本次启动的确切实例」；agent 对「宿主应用与本会话的依存关系」无内建感知，kill 类命令一旦宽匹配就波及宿主链路。macOS 上 GUI 开发环境（Electron 宿主 + Electron 被测应用同机）使这类重名成为常态而非例外。

**解决方案**：
进程清理三纪律：①**优先按精确 PID**（先 ps 拿到本次启动的 pid 列表再逐个 kill）；②必须用模式时锁定本次启动的独有路径段（如 `desktop/node_modules/electron`——被测工程的 node_modules 路径宿主不可能有），禁用裸产品名/类型名（Electron/java/node 这类宿主同族词）；③kill 后 ps 复核存活时同样用精确模式，防把宿主进程误读为残留。

**影响范围**：
所有涉及进程清理的联调/验收场景（壳联调、多进程测试、后台任务收尾）；宿主为 GUI 应用（Electron 系）的 agent 运行环境尤甚。

**同族扩展（2026-10-05，M37-08 验收）**：不止 pkill——**写给用户的验收命令同罪**：`ps aux | grep "[d]uo-harness" | xargs kill -9` 的宽词命中了壳进程路径（仓库目录名即 duo-harness，打包 app 路径全程含它），用户照做把壳连同后端一起杀、报「桌面直接退出」的假缺陷。验收命令里的 kill 目标模式必须**含独有的产物特征**（如 `Resources/backend/duo-harness.jar` 的完整尾段），且发给人手的命令先自问「这模式会命中谁」。

## [2026-10-05] git add -A 场景的产物入库检查：commit stat 清单必须逐行过目（M37-08 实录）

**问题描述**：
工单 08 打包收尾用 `git add -A` 全量暂存，beforeBuild 钩子的输出物 `desktop/resources/backend/duo-harness.jar`（22MB 二进制）随行入库——若非提交后逐行过目 stat 清单时逮出并 amend 移除（未推送，本地修正零成本），22MB 二进制将永久进入仓库历史。

**原因分析**：
`-A` 全量暂存 + .gitignore 未覆盖新产物目录，两者叠加让「构建产物入库」零阻力；产物目录（resources/backend/）是本票新增，没有任何 ignore 规则先行在位。

**解决方案**：
①新增产物目录的票，.gitignore 规则与目录同 diff 落（创建输出目录的代码合入时同步写 ignore）；②`git add -A` 之后、commit 之前，`git status --short` / stat 清单逐行过目——二进制（.jar/.png 大文件/.icns）出现即问「这是源资产还是构建产物」；③已 commit 未 push 时 amend 移除零成本，推送后即成历史包袱——**二进制入库检查是推送前的最后闸门**。

**影响范围**：
所有 `git add -A` 场景（打包/构建类工单尤甚）；新增「会写文件到仓库目录」的脚本/钩子的工单。

## [2026-10-05] 对运行中壳做 HTTP 级测试的两个工法坑（M37-08 用户代测会话）

**问题描述**：
对运行中的桌面壳/后端做 curl 级测试连踩两坑：①busy 探活测试首轮用 3s 间隔轮询 turnActive，快速 LLM turn（1+1，秒级流完）的在飞窗口整个被跳过——误判「计数没生效」；②从锚点 URL 截查询串拼其他端点（`URL%%\?*`），路径留了尾斜杠，拼出 `//api/message` 被 JDK HttpServer 400「Bad request URI」（非应用缺陷，测试脚本解析 bug）。

**原因分析**：
①异步在飞状态的观测窗口与轮询粒度强相关——秒级完成的 turn 用秒级粒度测，看到的永远是「不在飞」；②锚点 URL 形如 `http://host:port/?token=x`，路径段自带 `/`，字符串截断后直接拼路径必然双斜杠。

**解决方案**：
①测在飞状态用 **0.5s 密轮询**抓窗口，另配「保证时长」的测试任务（如 bash `sleep 30`——执行期/审批等待期都锁在 turn 里，比依赖 LLM 流式时长的任务稳）；②URL 截查询后拼路径先 `%/` 去尾斜杠，或直接用 `new URL()` 语义（TS 侧）/完整字面量（shell 侧）；③测试失败先区分「应用缺陷」与「测试工法缺陷」——本例 turnActive 快速回落是后者（证据：会话事件里 assistant/message 在案）。

**影响范围**：
所有对运行中服务做 HTTP 级验收/探测的场景（壳联调、端点测试、状态轮询类验收件）。

## [2026-10-05] 回退某功能的基点 = 功能提交的父提交，checkout 回执不算数（M37-08 移除通知实录）

**问题描述**：
砍除桌面通知功能时，`git checkout e95294dc -- app.js` 想恢复「通知加入前」的渲染层——checkout 成功回执、语法绿，但 grep 实证 desktopNotify 仍有 6 处：e95294dc 在通知提交（1fe9cad5）**之后**，文件本就带通知。且 git status 显示 `M `（暂存态）进一步迷惑——checkout 会同时更新 index 与工作树，两处都写着「已处理」的样子。

**原因分析**：
「回退到功能加入前」的正确基点是**功能提交的父提交**（1fe9cad5^ = 04e53c51），随手抓一个早期提交在分支交叉时（并行工单、docs 提交穿插）极易选中功能之后的点；checkout 的成功回执只证明「命令执行了」，不证明「内容回到了你以为的样子」。

**解决方案**：
①回退基点公式：`git checkout <功能提交>^ -- <路径>`，先 `git log --oneline <功能提交>^ -1` 看一眼落点再动手；②checkout 后**当场 grep 实证目标符号归零**（本例 desktopNotify 计数），回执不算数；③grep 计数与预期不符时用三方对照定位（worktree/index/目标提交各 grep 一次）——本次靠 `git show e95294dc:path | grep -c` 当场坐实「基点选错」。

**影响范围**：
所有「移除某功能/回退某改动」的 git checkout -- path 场景；提交历史有并行穿插的仓库尤甚。

## [2026-10-05] 改前端后真机验证前必须重打 jar——后端服务的静态资源来自构件非源码（M38-07 实录）

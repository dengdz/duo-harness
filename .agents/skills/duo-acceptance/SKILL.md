# duo-acceptance：验收件与手动验证

agent 测试全绿 ≠ 验收。**验收件** = 可运行演示 + 过程日志 + 预期对照，三件齐备交给用户亲手运行，确认通过才算 done。

## 第一步：判粒度

- **工单级**（默认）：最小可运行演示——测试可执行入口或小 example，叙述本工单的核心路径与边界
- **里程碑级**（版本收官，或用户说"整体验收"）：example 模块汇总 Demo（M1 的 07 工单即范本：34 条叙述覆盖全部机制）

## 第二步：备验收件（三件套）

1. **可运行演示**：一条命令跑通，不给多步拼装指令；形态随功能——CLI 叙述、浏览器页面（UI 类须视觉验证）、测试入口
   - 完成判据：命令在干净检出上复制粘贴即可执行成功
2. **过程日志**：状态迁移、事件流、关键决策点逐条打到输出——不读代码的人能对照看懂行为；静默成功不算演示。两条路径都要日志：
   - 演示路径：Demo/example 的叙述输出
   - 测试路径：**测试套件作为验证方式时，套件级叙述日志必配**（@BeforeAll 一行说明本套件验证域与用例覆盖，用户跑 mvn test 时可见"正在验证什么"；失败详情自然上屏）——静默绿条不算可验收的测试输出
   - 完成判据：功能的每条核心路径在输出里至少有一行可指认；测试路径的每个套件有一行可指认的叙述
3. **预期对照表**：标志性行逐条列出（"应出现 X"）。位置按粒度：工单级放该工单 Comments；里程碑级放 feature 目录（`<feature>/acceptance.md`，M1 即范本）或对应 docs 篇章。里程碑级**附预期日志原文段**（实测快照，按验收点分段标注）——用户逐行对照，不凭描述猜
   - 完成判据：用户能逐行核对，无需追问"这行对不对"

## 第三步：交用户运行

给出命令与对照表，等结果。**用户实测现象优先于任何测试绿灯**——发现问题回实现修复，不得以"测试是绿的"反驳；修复后重备验收件再验。

完成判据：用户明确确认通过，或指出问题并进入修复回路。

命令行之外的等价路径——用户用 IntelliJ IDEA 时给这两条操作（输出与命令行预期日志一致，在 Run 工具窗核对）：

- **Demo**：打开 `DemoMain` → main 方法旁绿色运行箭头 → Run——输出即预期日志 B 全文
- **测试**：测试类（或包/模块）上右键 → Run Tests——Run 窗口逐套件显示叙述行与结果
- **玩法循环**：改 `demo.yml` 后直接点 rerun（IDEA 自动重编译资源），适合"改一行看形态"的验收玩法

## 状态记账

验收未过的工单 Status 停在 `in-progress`（Comments 注"待手动验证"）；用户确认后才置 `done`（issue-tracker 的 done 定义同源于本 skill）。

## 日志长什么样（字面示例）

"详细"由示例锁定，不以形容词为准。两类可指认的输出：

演示路径（Demo 叙述行，M1 范本）：

```
  [状态] GreetingClientPlugin: PENDING -> LOADING
  [demo] 消费者经视图获得: 你好, 世界!
  -> [错误] 工具 "echo" 执行被拒绝: 参数含敏感词（治理插件否决）
```

测试路径（套件叙述行，@BeforeAll 打出）：

```
=== 套件：LifecycleTest —— 六态与 epoch：状态迁移事件广播、依赖消失回 PENDING、服务回归/换实现自动重启、失败隔离（FAILED 兄弟无感）、DISPOSED 终态不复活（10 用例） ===
```
